# 设计：把上游规范并入 taihu spec 的方法

## 1. 核心问题

现有 spec 是从 taihu 自己的代码反推的，锚点天然真实但覆盖面由「踩过哪些坑」决定。三份上游补覆盖面，但它们是**外来输入**，直接搬运会引入两类破坏：

| 破坏 | 后果 | 本设计怎么防 |
|------|------|--------------|
| **规则无锚点** | spec 里出现「应当优先使用 `errgroup`」但仓库里没有 `errgroup` —— 读者无法验证，规则退化成口号 | 准入条件：指不到真实 `file:line` 的规则不写进 spec（见 §3.2） |
| **规则互相矛盾** | 同一主题两处规定（上一轮 `api-surface.md` 规则 4 与规则 5 就互相抵触过） | 归位原则：一个主题只有一个承载体，跨层需求用引用而非复述（见 §3.1） |

还有一类不能算「破坏」但必须显式处理：**taihu 刻意不遵守上游规则**。这类不写清楚，下一个人（或 AI）会「顺手修正」它，把有意的设计改成 bug。本设计给它专门的落点（§3.3）。

## 2. 数据流

```
三份上游原文 ──[research agent]──> research/*.md（逐条编号 uber-/ecc-/gbp-）
                                          │
taihu 代码 + spec ──[research agent]──> research/taihu-spec-inventory.md
                                          │
                                          ▼
                                    research/triage.md
                              （每条上游规则 → 适用 / 冲突 / 不适用）
                                          │
                    ┌─────────────────────┼─────────────────────┐
                    ▼                     ▼                     ▼
              适用 → 并入 spec      冲突 → conflicts.md      不适用 → 附录简表
                                          │
                                    ★ 人逐条裁决 ★
                                          │
                              ┌───────────┴───────────┐
                              ▼                       ▼
                    维持 taihu → 刻意偏离清单   改 taihu → 待办（本轮不改代码）
```

## 3. 关键设计

### 3.1 归位：一个主题只有一处规定

并入时先判断规则的**主题**，再决定承载体。承载体选择按「最一般优先」：

| 规则主题 | 承载体 | 例子 |
|----------|--------|------|
| Go 语言层（命名、注释、import、defer、panic 边界、切片预分配） | `architecture/code-style.md` | 新增小节，或补进已有小节 |
| 错误处理（包装、sentinel、传播、边界） | `architecture/error-model.md` | |
| 依赖方向 / 分层 | `architecture/layering.md` | |
| 包的对外面 | `architecture/api-surface.md` | |
| 测试形态 | `testing/unit-tests.md` / `index.md` | |
| 构建 / 平台分裂 / 构建约束 | `platform/*.md` | |
| 引擎层契约（并发、缓冲存活期、持久化语义） | `engine/*.md` | |
| CLI 行为 | `cli/*.md` | |
| 跨进程边界 | `transport/*.md` | |
| **元规则**（规则该怎么写、怎么改 spec 本身） | `guides/index.md` | 新增章节（见 §3.4） |

**跨层需求的写法**：如果一条规则同时属于语言层与引擎层，它写在**更一般**的那层，具体层用一句话**引用**过去，不复述内容。反例是现在的 `api-surface.md` 规则 4 与 5 —— 它们分别规定「对外面文件只放导出名」和「缓存上移到哪个文件」，本质是同一条约束的两半，写的时候才发现要互相引用。这次并入前先把这类「一对规则」识别出来，合并成一节。

**新开文件的唯一理由**：某个主题在 8 层里确实没有承载体。新开的是**文件**，不新开**层** —— 层是 `index.md` 决定的结构，加一层意味着加一份索引和一个上下文入口，代价远大于加一个文件。

### 3.2 准入：能指到真实锚点

每条准备并入的规则，写进 spec 前先做一次锚点验证：

```bash
# 规则文本里声明的每个 file:line 都要真实存在，且该行内容与规则陈述对得上
sed -n '<line>p' <file>
```

对不上就不写。这条直接继承自本仓库既有的 spec 立场（Trellis 原话：**错误模板比空模板危害更大**），也是上一轮 `api-surface.md` 修「io_uring 占 65%」那个假数字时确立的做法。

**推论**：如果一条上游规则在 taihu 代码里**找不到任何锚点**（既没有正例也没有反例），它属于「本仓库不涉及的领域」，进不适用附录，不进正文。

### 3.3 刻意偏离：让「不遵守」变成一等公民

裁决为「维持 taihu」的冲突，落成一条**刻意偏离**，格式三要素缺一不可：

```markdown
- **<上游主张一句话>** —— 上游见 <来源编号>。
  taihu 的做法是 <实际情况>（`file:line`）。
  **为什么偏离**：<理由>。
```

理由必须**具体到可检验**。参照现有最合格的写法：`bufpool` 否决 `sync.Pool` 时给的是实测数据（读路径冷分配占服务端 CPU 36%），不是「性能考虑」这种话。写不出具体理由的偏离，说明它可能根本不是刻意设计，而是疏漏 —— 那就不该记成「刻意偏离」，该记成「待办」。

**落点**：挂在对应主题的 spec 文件末尾统一一节（如 `## 刻意偏离上游规则`），不散在各处。

### 3.4 溯源：让规则能被追溯回上游

并入的每条规则尾部加一个轻量标记，指向上游编号：

```markdown
**（源自 uber-042）**
```

配一份**溯源表**放在 `guides/index.md` 的新章节里，反向索引：上游编号 → `spec 文件:节`。两个方向都要有 —— 读规则时想知道出处（尾部标记），盘覆盖时想知道某条上游规则收没收（溯源表）。

### 3.5 不适用附录：一行一条，说清为什么

```markdown
| 上游编号 | 规则 | 为什么不适用 |
|----------|------|--------------|
| gbp-003 | 用 Go-Kratos 组织微服务 | taihu 是单模块存储引擎，无 RPC 框架、无服务发现；`internal/transport` 是自己实现的二进制协议 |
```

判断「不适用」的依据是**项目形态**而非个人偏好：写应用/微服务的假设是什么，taihu 的实际形态是什么。这条对下一轮的人最有价值 —— 它免去重新判断的成本。

## 4. 与既有工作流的关系

- **spec 正文用中文**：这是本仓库的刻意约定，三份上游是英文，并入时要做术语翻译并保持既有译法（receiver / interface / sentinel 等在现有 spec 里已有固定译法，先查再写）。
- **本轮不产生代码改动**：所有裁决出「改 taihu」的，一律落成 spec 里的待办条目，附 `file:line` 与验收方式，交下一轮。
- **验证方式**：本轮唯一的机器可验证项是**引用完整性**（`path:line` 全有效）。语义质量靠评审门（冲突清单）与人读。

## 5. 风险

| 风险 | 应对 |
|------|------|
| 三份上游抓不全，导致三分类有系统性缺口 | 抓取结果里显式标注失败项；缺口在溯源表里标为「未取到，未参与对撞」 |
| spec 体量膨胀，规则密度被稀释 | 准入条件（§3.2）会自动筛掉无锚点的；若某类并入过多，优先保留有反例/有实测依据的 |
| 并入规则与既有规则矛盾未被发现 | 并入后跑一次跨文件主题扫描：同一主题关键词在多个 spec 文件出现即人工复核 |
| 冲突清单过长，裁决成本高 | 冲突按「是否影响真实行为」排序，只影响措辞的排在最后，用户可批量处理 |
