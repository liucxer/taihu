# O_DIRECT 直读共享内存改造（消除 shm 读路径 memcpy 损耗）

## Context

**问题**：taihu bench storage 进程内直连读 6.58 GiB/s，而 shm 单服务端单客户端读仅 5.78 GiB/s，损耗 12.2%。

**根因（服务端 pprof 实测）**：`runtime.memmove` 占 65.9% CPU —— [shmipc_server.go](file:///Users/liucx/gopath/src/github.com/liucxer/taihu/internal/transport/shmipc_server.go#L60-L79) 的 `shmWriteFrame` 把 `storage.ReadAt` 返回的 bufpool 缓冲 `copy` 进共享内存切片（每 4MiB 一次 memcpy），叠加磁盘 DMA / memcpy / 客户端读取三路内存流量竞争。

**目标**：O_DIRECT 直读共享内存切片，服务端数据面零拷贝，读带宽从 5.78 提升到接近直连的 6.58 GiB/s。

**核心机制**：让 shmipc 共享内存切片的 data 区起始地址 4K 对齐（O_DIRECT 缓冲要求），数据帧布局改为 `[5B 帧头][4091B pad][4K 对齐数据区]`，服务端 `device.ReadAt` 直接 DMA 进共享内存（免 memcpy），客户端跳过 pad 零拷贝取 payload。

## 改动清单

### 1. fork shmipc-go → third_party/shmipc-go（数据区 4K 对齐）

复制 `github.com/cloudwego/shmipc-go@v0.2.0` 到 `third_party/shmipc-go`，go.mod 加 `replace github.com/cloudwego/shmipc-go => ./third_party/shmipc-go`（同 netpoll fork 模式）。

**修改 `buffer_manager.go`（仅此文件为主战场）**：
- 新增常量 `alignSize = 4096` 与辅助函数 `align4K(n)`。
- `countBufferListMemSize`（L337-339）：步长从 `capPerBuffer + bufferHeaderSize` 改为 `align4K(capPerBuffer + bufferHeaderSize)`，即每个 buffer 之间 4K 对齐步进。
- `createBufferManager`（L259-297）：bufferNum 分母用对齐步长；`hadUsedOffset` 起始按 `alignListOffset` 对齐——保证 `bufferRegionStart + bufferHeaderSize ≡ 0 (mod 4096)`（buffer 起始 4K 对齐后，data 区 = 起始+20B 恰好 4K 对齐）。**mappingBufferManager（L299-335）必须做相同的起始对齐**，否则两端布局错位。
- `createFreeBufferList`（L341-391）：tail 初值与 next 链步长用对齐步长。
- 顺带修正 `mappingFreeBufferList`（L404）counter 偏移 `+24` → `+20`（与 createFreeBufferList L362 不一致的既有 bug）。

**不改**：buffer_slice.go（header 内字段偏移不变）、queue.go、session.go、buffer.go 的 Reserve/ReadBytes 逻辑（单切片命中时 data 首地址自动 4K 对齐，O_DIRECT 友好）。

### 2. internal/device/device.go —— 新增 ReadAtInto

```go
// ReadAtInto 读取段内 off 起 size 字节，直接 DMA 进调用方 dst（O_DIRECT 直读目标缓冲）。
// 要求 off/size 4K 对齐、dst 首地址 4K 对齐（bufAligned）且 cap ≥ size。
// 返回实际读入字节数（读到对象/设备末尾短读，不附错误）。
func (d *Device) ReadAtInto(ctx context.Context, segmentID, off, size int64, dst []byte) (int64, error)
```
- 镜像 `ReadAt`（L334-361）校验，`bufpool.Get` 改为使用调用方 dst：`d.submitRead(dst[:size], d.segmentBase(segmentID)+off)`，返回 `ev.Res`。dst 存活由调用方保证到 submit 完成（submitOp L160 约束，本函数同步等待）。

### 3. pkg/taihu/storage.go —— 新增 ReadAtInto

```go
// ReadAtInto 读取对象 [off, off+size)，直接读入 dst（要求 off 4K 对齐、dst 4K 对齐、cap ≥ align4K(want)）。
// 内部物理读区间 dlen = align4K(want)（skip==0），device.ReadAtInto 直读 dst，返回实际读入 want 字节。
func (s *Storage) ReadAtInto(ctx context.Context, key string, off, size int64, dst []byte) (int64, error)
```
- 镜像 `ReadAt`（L114-158）：GetMapping、RefSegment/UnrefSegment、want 截断；**仅支持 skip==0 快路径**（off 4K 对齐时 relStart 4K 对齐，dstart=relStart、dlen=align4K(want)），非对齐 off 由上层回退 memcpy 路径。

### 4. internal/transport/protocol.go —— 常量调整

- `shmSliceSize = chunkSize + 8KiB`（原 `chunkSize + 8`）：数据帧直读区 `pad(4096) + 数据(≤4MiB+4095)` 需要 cap ≥ 4MiB+8191。
- 新增 `shmDataPad = 4096`（数据帧对齐 pad 长度）。

### 5. internal/transport/shmipc_server.go —— 直读快路径 + 数据帧统一 pad

**`shmWriteFrame`**：op 为数据帧（opGetData/opGetDataFinal）时，Reserve 长度从 `5+len(payload)` 改为 `shmDataPad + 5 + len(payload)`，帧头写 `buf[0:5]`，payload（拷贝路径）写 `buf[shmDataPad:shmDataPad+len]`。控制帧不变。**保证直读/回退两条路径数据帧布局一致，客户端统一跳 pad**。

**`handleShmGet`**（L266-312）新增直读分支（off 4K 对齐时）：
1. `want = min(chunkSize, end-pos)`；`dlen = align4K(want)`
2. `Reserve(shmDataPad + dlen)` 拿对齐切片 → 数据区 = `buf[shmDataPad:shmDataPad+dlen]`（4K 对齐）
3. 写帧头 `[4B len=1+want][1B op]`
4. `n, rerr := s.storage.ReadAtInto(ctx, key, pos, want, 数据区)` —— 同步阻塞直读
5. 短读/EOF 时更新帧头 len = 1+n（n 为实际读入），`n==0` 时按 EOF 处理
6. `st.Flush(false)`；op 选择逻辑（opGetData/opGetDataFinal）沿用现有 pos+n/EOF 判断

非对齐 off 走原 memcpy 路径（Storage.ReadAt + shmWriteFrame）。

### 6. internal/transport/shmipc_client.go —— 数据帧跳 pad

`shmReadFrame`（共用函数，定义在 shmipc_server.go L41，客户端复用）改造：读到 op 为 `opGetData/opGetDataFinal` 时，先 `r.ReadBytes(shmDataPad - frameHeaderLen)` 丢弃 pad，再 `ReadBytes(n-1)` 取 payload（`frameHeaderLen=5`，protocol.go L37）。控制帧（opResp/opGetErr/opStatResp）不变。零拷贝 take 路径（payload 引用共享内存）不受影响。

## 验证

1. **本地编译**：`go build ./...` + `go vet ./...` 通过。
2. **交叉编译**：`GOOS=linux GOARCH=arm64 CGO_ENABLED=0` 构建 `taihu server` 与 `taihu bench cluster`，部署 128.13。
3. **性能复测**（单服务端 + 单客户端，128.13，p4m-s1 数据，预热）：
   - 读带宽预期从 5.78 GiB/s 提升至 ~6.4-6.5 GiB/s（接近直连 6.58）。
   - 服务端 `-pprof :6061` 采集：`runtime.memmove` 应从 65.9% 降到接近 0。
4. **正确性回归**：
   - 整对象读（4MiB 对齐，off=0）→ 直读快路径，数据校验（bench 已有短读/长度校验）。
   - 尾块（对象非 4MiB 整数倍、末块非对齐长度）→ 直读 + 帧头短读更新。
   - 子区间非 4K 对齐 off → 回退 memcpy 路径不回归。
   - 写路径（Put）不受影响；多客户端并发不回归。
5. **多盘/多节点**（可选）：恢复 3 服务端或三节点集群复测，确认聚合带宽提升。

## 备注

- 共享内存每会话 256MB 不变，大切片数量 ~42→41（步长含 4K pad），可忽略。
- 客户端数据帧跳 pad 仅影响 shm 路径；TCP 路径（conn.go 帧解析）不受影响。
- shmipc fork 保留原 LICENSE 与 go.mod（module 名不变，replace 指向 fork）。
