# 写路径零拷贝：服务端共享内存 Put 帧分段直写设备（消除 bufpool 汇集拷贝）

## Context

**问题**：写路径服务端 memmove 占 71.7% CPU（三节点集群实测 pprof）——[handleShmPut](file:///Users/liucx/gopath/src/github.com/liucxer/taihu/internal/transport/shmipc_server.go#L249-L262) 把共享内存 Put 数据帧 `copy` 汇集到 bufpool 整块缓冲后一次 `storage.Put` 写盘。

**目标**：复用读路径已建成的"共享内存切片 data 区 4K 对齐"基础设施（shmipc fork 布局），让服务端**逐帧 O_DIRECT 直写共享内存切片**（免汇集拷贝），仅尾块保留少量对齐缓冲。写带宽受单盘极限 2.5 GiB/s 约束不会提升，价值在**释放服务端 CPU**（支撑更高并发/多实例）与消除 bufpool 整对象分配。

**关键前提（探索确认）**：
- `device.Append` 路径1（[device.go](file:///Users/liucx/gopath/src/github.com/liucxer/taihu/internal/device/device.go#L275-L299)）已支持"4K 对齐地址直写主体 + 尾块 4K 临时缓冲补零"，天然适配分段直写
- `metastore.AllocateSegment` 返回 4K 对齐 off、单调不重叠（kv_pebble.go L261）；`PutMapping` 独立可调用
- **障碍**：客户端 `opPutData` 帧当前无 pad（payload 起始 = data区+5B 帧头，**非 4K 对齐**，探索结论 §6）→ 必须给 opPutData 对称加 pad（同 opGetData 的 `[5B头][4091B pad]` 布局，shmipc_server.go L69-72 已有先例）

## 改动清单

### 1. 协议：opPutData 数据帧加 pad（客户端/服务端对称）

**shmWriteFrame**（[shmipc_server.go](file:///Users/liucx/gopath/src/github.com/liucxer/taihu/internal/transport/shmipc_server.go#L73-L94)，客户端/服务端共用）：
- op 为 `opPutData` 时也设 `dataOff = shmDataPad`（当前仅 opGetData/opGetDataFinal），并同步累加 statTxData* 统计

**shmReadFrame**（[shmipc_server.go](file:///Users/liucx/gopath/src/github.com/liucxer/taihu/internal/transport/shmipc_server.go#L44-L66)）：
- 数据帧跳 pad 分支从 `opGetData/opGetDataFinal` 扩展 `opPutData`（服务端读 Put 请求帧时跳过 pad，payload 即 4K 对齐）

**影响**：客户端 Put 数据帧布局与 Get 对称；两端同 fork 同步生效，TCP 路径（server.go 帧解析）不受影响。

### 2. taihu.Storage 分段写 API（storage.go）

新增（保留原 `Put` 组合复用，供非 shm 调用方）：
```go
// PutBegin 分配段游标（4K 对齐 off），开始分段写。key 仅用于最终 PutCommit 建映射。
func (s *Storage) PutBegin(ctx context.Context, key string, size int64) (segmentID, off int64, err error)
// PutAppend 直写一段（data 首地址 4K 对齐时零拷贝直写设备；尾段非对齐由 Append 兜底）。
func (s *Storage) PutAppend(ctx context.Context, segmentID, off, size int64, data []byte) error
// PutCommit 写 key→(seg,off,size) 映射（先数据后映射，防"有映射无数据"）。
func (s *Storage) PutCommit(ctx context.Context, key string, segmentID, off, size int64) error
```
- 复用现有 `AllocateSegment`/`dev.Append`/`PutMapping`（storage.go L77-102 拆解）
- size==0：PutBegin + PutCommit（无 Append，Append 内部 aligned==0 直接返回）

### 3. handleShmPut 分段直写（shmipc_server.go L223-277）

**非零对象**（替换 bufpool 汇集）：
```
PutHeader → PutBegin(key, size) 得 (seg, off)
PutData 帧（payload 4K 对齐）：
    PutAppend(seg, off+已写, len, payload)   // O_DIRECT 直写共享内存切片，同步等待完成
    r.ReleasePreviousRead()                   // IO 完成后即时归还切片（不积累 pin）
PutEnd  → 校验 已写 == size → PutCommit(key, seg, off, size) → opResp
```
- 尾帧（非 4K 对齐长度）：`Append` 路径1 尾块 4K 临时缓冲自动处理，无需额外逻辑
- **帧 pin 生命周期**：每帧 `PutAppend` 同步完成后立即 `ReleasePreviousRead`（当前 L264 已有每帧释放，仅把 copy 换成直写）
- 错误路径：`shmRespErr`（段泄漏由 segment GC 兜底，与现有 Put 失败语义一致）

**size==0**：PutBegin + PutCommit（替代当前 `storage.Put(ctx,key,0,nil)` L243）。

## 验证

1. **本地**：`go build ./...` + `go vet ./...`。
2. **正确性回归**（128.13，taihu-shm-bench 直连 nvme1，写→读校验）：
   - 4MiB 整帧对象（直写路径）
   - 非 4MiB 整数倍对象（尾帧 4K 临时缓冲）
   - 空对象（size=0）
   - 多帧大对象（>4MiB，多次 PutAppend）
3. **性能复测**：单实例写带宽（预期 ~2.5 GiB/s 不变，盘极限）；服务端 `-pprof`：写 memmove 71.7% → ~0（仅尾块残留）。
4. **回归**：TCP 路径写（server.go handlePut 不受影响）、多客户端并发写、rpccluster 集群写（128.11/12/13 各写独立前缀）。

## 备注

- 写带宽不提升（单盘极限 2.5 GiB/s），收益 = 服务端 CPU 释放 + 消除 bufpool 整对象分配（4MiB×并发）。
- 客户端 API（Put 传 []byte）不变；协议帧布局变化对两端透明（同 fork）。
- 若后续做"客户端零拷贝写 API"（方案 3），本改造的 pad 布局为前置条件。
