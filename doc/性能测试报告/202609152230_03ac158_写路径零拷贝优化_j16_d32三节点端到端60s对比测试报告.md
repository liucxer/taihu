- **写带宽 7464 → 10871 MiB/s（+45.7%）**，C 组三次独立复测 10809 / 10963 / 10840（极差 1.4%），读数稳定。

## 2. 优化内容

改动仅两处，均在 **EFS_nefs 客户端**，服务端与本报告全部集群参数不动。

### 2.1 `pkg/chunk/cached_store.go`：暴露底层字节切片

```go
// bytesSourceReader 把 Page.Data 包成 io.Reader，同时暴露 Bytes() 供对象存储后端识别。
type bytesSourceReader struct {
	*bytes.Reader
	data []byte
}

func (r *bytesSourceReader) Bytes() []byte { return r.data }

func newBytesSourceReader(data []byte) *bytesSourceReader {
	return &bytesSourceReader{Reader: bytes.NewReader(data), data: data}
}
```

`cachedStore.put` 由 `bytes.NewReader(p.Data)` 改为 `newBytesSourceReader(p.Data)`。

### 2.2 `pkg/object/taihu/taihu.go`：Put 走零拷贝快路径

```go
// byteSource 暴露底层字节切片（chunk 层的 bytesSourceReader、*bytes.Buffer 等）。
type byteSource interface{ Bytes() []byte }

func (t *Taihu) Put(key string, in io.Reader) error {
	...
	var data []byte
	if bs, ok := in.(byteSource); ok {
		data = bs.Bytes()          // 零拷贝：直接引用 Page.Data
	} else {
		data, err = io.ReadAll(in) // 兼容其它 Reader
		...
	}
	return t.store.Put(context.Background(), key, int64(len(data)), data)
}
```

### 2.3 为什么直接引用 `Page.Data` 是安全的

taihu 数据面 `transport.shmWriteFrame` 是**同步** copy 进共享内存后 `Flush`，`Put` 返回时已不再引用 `in`；
`cachedStore.put` 侧 `defer p.Release()` 在 `Put` 返回后才归还 Page。故写入期间切片生命周期完整，无需额外拷贝。
§7 的一致性验证即针对这条前提。

### 2.4 与「预分配定长缓冲」方案的取舍

基线报告建议的预分配方案仍要**拷一次**（`Page.Data` → 定长缓冲），只是把 `growslice` 的反复扩容换成一次性分配。
零拷贝方案直接把这次拷贝整个取消，因此同时消掉了 memmove 与 GC 两项（见 §5、§6）。

## 7. 数据一致性验证（零拷贝正确性）

零拷贝引入「写入期间切片被外部持有」这一新前提，必须证明无别名 bug 与写后失效。

**方法**（128.11，4 个卷）：

1. 每卷写入 `512 MiB`（`dd bs=1M`，`conv=fsync`）**再追加 104857 B 非对齐尾巴**，覆盖非整 block/chunk 边界；
2. 记录 `stat` 大小与 `md5sum`；
3. `sync` + `echo 3 > /proc/sys/vm/drop_caches` 丢弃客户端与内核页缓存（`cache-size=0`，读必回后端 taihu）；
4. 重读 md5；再 `drop_caches` 重读一遍。

**结果**

| 卷 | 大小 | 写入 md5 | 重读1 md5 | 重读2 md5 |
|---|---|---|---|---|
| `/mnt/v11-1` | 536975769 | `ae7508e7…22a6` | 同 | 同 |
| `/mnt/v11-2` | 536975769 | `a14a8dec…efc` | 同 | 同 |
| `/mnt/v11-3` | 536975769 | `d8daae71…73a` | 同 | 同 |
| `/mnt/v11-4` | 536975769 | `71798054…27c` | 同 | 同 |

`INTEGRITY=OK (write==read1==read2)` —— **三处 md5 全等，零拷贝未引入数据损坏**。

## 8. 结论与后续

### 8.1 结论

1. **零拷贝把写带宽从 7464 MiB/s 抬到 10871 MiB/s（+45.7%），写延迟从 3.02 s/卷 降到 2.07 s/卷（−31.6%）**，
   C 组三次复测极差 1.4%，读数可信。
2. **零拷贝单独的贡献是 +22.2%（7464 → 9119）**，其机制已被 pprof/heap 双侧证实：
   `io.ReadAll` 的 3.07 TB/60s 分配与 `growslice`+`bytes.Reader.Read` 的 102.3 s 拷贝**全部归零**，
   带来 **GC 33.8% → 0.24%、客户端 CPU 78.67 → 30.59 核（−61%）**。
3. **`buffer-size` 300 → 2048 再贡献 +19.2%（9119 → 10871）**，主要作用是**消除卷间抢占抖动**
   （B 组存在 361/481/519 的离散步长，C 组最低 810）。
