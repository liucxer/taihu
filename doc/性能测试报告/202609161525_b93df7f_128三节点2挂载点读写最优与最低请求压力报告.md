## 1. 目标

1. 把每节点 **4 个挂载点压到 2 个**，看更少的客户端会话/挂载点能否打满同一批盘。
2. 给出 2 挂载点下的**最佳读、最佳写**数据。
3. 找出**最低请求压力**：达到平台带宽所需的最小「在飞请求数」与最小「并发流数」。

## 2. 方法与口径

### 2.1 为什么选 v-3 / v-4

| 挂载点 | 容量 | 备注 |
|--------|------|------|
| `/mnt/v{11,12,13}-1` | **100 G**（仅 v13-1） | 60 s 控时长轮每卷要写 384 GiB（768/2），会写满 → 必须避开 |
| `/mnt/v{11,12,13}-2` | ~1.0 T | |
| `/mnt/v{11,12,13}-3` / `-4` | ~1.0 T | 本轮选用 |

先用 iostat 逐盘核对：**2 个卷（v-3/v-4）依然覆盖 3 块数据盘**（nvme1/2/3 三块盘 `%util` 均为 87~90%，OS 盘 nvme0n1 仅 10~13%）——卷与盘不是 1:1 映射，所以"减挂载点"不会丢掉磁盘并行度。

### 2.2 命令

```bash
# 写侧扫描（60s/轮 + 落盘排空；--size 自动按 768GiB/节点 ÷ 2 个挂载点 ÷ nj 重算 = 128GiB/job）
python3 cluster_ops.py --cluster 128 --phase test --write-only --drain --runtime 60 --cpu \
    --mounts 3,4 --only-round "1,1 2,1 3,1 4,1" --ch proxy
python3 cluster_ops.py --cluster 128 --phase test --write-only --drain --runtime 60 --cpu \

    --read-runtime 60 --cpu --pprof --mounts 3,4 --only-round "8,8 8,16 12,16 16,16" --ch proxy
python3 cluster_ops.py --cluster 128 --phase test --total-per-node 49152 --runtime 0 \
    --read-runtime 60 --cpu --mounts 3,4 --only-round "16,4 16,8 24,8" --ch proxy

# 最优点确认轮（带 CPU + 双端 pprof）
python3 cluster_ops.py --cluster 128 --phase test --write-only --drain --runtime 60 --cpu --pprof \

python3 cluster_ops.py --cluster 128 --phase test --total-per-node 49152 --runtime 0 \
    --read-runtime 60 --cpu --pprof --mounts 3,4 --only-round "16,4" --ch proxy
```

### 2.3 术语

- **在飞/卷** = `numjobs × iodepth`（该挂载点上同时在飞的请求数）；**在飞/节点** = 在飞/卷 × 挂载点数。
- **稳态** = 逐秒样本剔除首末后按节点均值 ×3（集群口径），与"盘侧均值"并列给出。
- 盘侧列：写取 `wkB/s`/`w_await`，读取 `rkB/s`/`r_await`；所有轮的**盘侧样本积分与 fio I/O 量闭口**（写 +0.4~+1.0%、读 +0.2~+0.3%），客户端 FUSE 字节 = PUT 字节（1.00x）。

- **最优 = `j16_d4`（每卷 16 job × qd4，32 线程/节点，128 在飞/节点）**：应用层 52406（51.2 GiB/s）、稳态 **49347（48.2 GiB/s）**、`lat` 29.4 ms（p99 59 ms）——实测最干净的一点，确认轮复现（应用层 53240 / 稳态 49327）。
- **最低请求压力**：
  - 线程数是硬门槛：**16 线程/节点**时不管队列多深（64 或 128 在飞/卷）都只有 35.8~37.2 GiB/s；**32 线程/节点**才跳到 48 GiB/s 以上。
  - 在 32 线程下，**队列深度只需 qd4（128 在飞/节点）**即拿满；j16_d16 把在飞加到 4 倍（512/节点）只多 2.7%（50676 vs 49347），而 `lat` 从 29 ms 恶化到 114 ms。
  - 因此 **2 挂载点读侧最低请求压力 = 每卷 16 job × qd4 = 64 在飞/卷、128 在飞/节点**。

## 5. 与 4 挂载点对比（同为 b93df7f）

| 维度 | 4 挂载点（对照） | 2 挂载点（本轮） | 差异 |
|------|------------------|------------------|------|
| 写最优 | j3_d1（3 job/卷×qd1，12 在飞/节点）稳态 22355 | j6_d1（6 job/卷×qd1，12 在飞/节点）稳态 22124 | **-1.0%** |
| 写最低压力 | 12 在飞/节点 | 12 在飞/节点 | 相同 |
| 读最优 | j8_d16（8 job/卷×qd16，512 在飞/节点、32 线程）稳态 53007 | j16_d4（16 job/卷×qd4，128 在飞/节点、32 线程）稳态 49347 | **-6.9%**，但在飞请求少 **4 倍**、`lat` 从 112.6 ms 降到 29.4 ms |
| 读最低压力 | 512 在飞/节点 | **128 在飞/节点** | **-75%** |
| 客户端 CPU（写） | 38.4 核 | 36.5 核 | -5% |
| 客户端 CPU（读） | 60.9 核 | 45.2 核 | -26%（口径见第 6 节） |
| 服务端 CPU | 写 4.8 / 读 8.7 核 | 写 4.7 / 读 6.6 核 | 均 <10 核 |

**核心结论：决定性能的不是挂载点个数，而是"每节点总在飞请求数"和"每卷并发流数（线程）"。**
- 写：两侧都在 **12 在飞/节点** 达到平台（21.6~21.8 GiB/s），挂载点减半不影响写能力。
- 读：两侧都需要 **32 线程/节点**；2 挂载点因为每卷 job 数翻倍（8→16），**用 1/4 的在飞请求** 就拿到 93% 的带宽，代价是应用层带宽低 6.9%。

## 6. 异常与口径提醒

1. **读相位卡死现象在 2 挂载点复现**（与 4 挂载点 `nj=16` 同源）：`j16_d8`、`j24_d8` 在**节点 13** 中途停摆——盘侧样本只有 25/20 个、积分只到 364/262 GiB、应用层 `lat` max 40.8 s / 60.2 s、节点 13 应用层掉到 6170 / 2498 MiB/s。同批次的 `j16_d4`、`j16_d16` 正常收尾。**读扫参避开"每卷 16 job + qd8"及以上压力**；`j16_d4` 是当前最稳的高性能读点。
2. **读相位 CPU 窗口含较多非负载时间**：读相位 `cu0→cu1` 窗口实测 106~111 s，而 fio 负载只有 60 s（写相位窗口 67 s / 负载 60 s，基本贴合）。因此上表读侧 CPU 数值被稀释约 1.8×，**只能用于同族横向比较**；按纯负载折算，2 挂载点 `j16_d4` 客户端约 45.2×109/60 ≈ **82 核（上界估计）**，4 挂载点 `j8_d16` 的 60.9 核（窗口 88 s）折合约 89 核。**写侧 CPU 数值可直接使用。**
3. `--size` 随挂载点数自动重算（768 GiB/节点 ÷ 实际挂载点数 ÷ nj）：2 挂载点 + j6 时每 job 128 GiB、每卷 384 GiB / 60 s，**依然不回绕**（每轮实写 1314~1317 GiB 集群，fio `run=60.0s`）。
4. 本轮仍**未**触及 CPU 瓶颈：宿主 busy 写 26% / 读 25%，服务端 1.3~7.1 核，`iowait≈0`，`%util` 71~72% —— 瓶颈在盘与客户端数据搬运。
