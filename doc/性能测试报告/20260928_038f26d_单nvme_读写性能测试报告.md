## 1. 测试目标

1. `taihu bench storage`：Storage 层本地裸盘直写压测（-db/-dev 直连盘，不走网络）。
2. `taihu bench single --transport shm`：单机直通共享内存 IPC 压测（rpcclient 直连 taihu-server，不查 TiKV），**异步读（server 无 --batch，--shm-inflight 默认 8 生效）**。
3. fuse 客户端：fio 经 nefs.client.batcher 挂载点读写，端到端（fio → FUSE → 客户端 → rpc → taihu-server → Storage → 裸盘），**异步读**。
4. 三组均只测**一个 NVMe**（128.11 的 nvme1n1p1），并按约定给出 CPU 三维（物理机 busy%+usr/sys、客户端等效核数、服务端等效核数）。

| 采样 | iostat -x -t 1（盘侧稳态 + nvme2/3 隔离）、mpstat -P ALL 1、/proc/stat（物理机 busy%）、/proc/<pid>/stat 时间窗 Δ（等效核数，CLK_TCK=100） |

**单盘隔离机制**：
- storage / single shm：bench 直连裸盘/专属 TAIHU-SINGLE，不经过 nvme2/3。
- fuse：测试期间停 n11-nvme2 / n11-nvme3，node11 全部 IO 压到 n11-nvme1；测试后已按生产参数重启恢复。
- 全程 iostat 监控 nvme2n1/nvme3n1 为 **max=0.00 MiB/s**（见各段采样）。

**破坏性说明**（预期副作用）：storage 与 single shm 压测会销毁 nvme1n1p1 上的段表数据；fuse 测试前已 `rm -rf /var/taihu-db/nvme1` 并以全新 db 重启 n11-nvme1。旧 v11-* 卷中落在 nvme1 的对象作废；**nvme2/3 数据未受影响**（生产挂载 v11-1..4 全程在线）。

## 3. 测试方法

```bash
# ① storage 写（2t）/ 读（32t，读前 LoadCache 预热）
taihu bench storage --mode write --db /tmp/tdb4m --dev /dev/nvme1n1p1 \
  --size 4194304 --count 20000 --threads 2 --keys-prefix p4m-w2 --report-interval 5s --latency
taihu bench storage --mode read  --db /tmp/tdb4m --dev /dev/nvme1n1p1 \
  --size 4194304 --count 20000 --threads 32 --report-interval 5s --latency

# ② single shm（专用服务端，不带 batch，异步读 inflight=8）
taihu server --listen 100.71.128.11 --db /tmp/tdbsingle --dev /dev/nvme1n1p1 \
  --server-name TAIHU-SINGLE --pd '<三节点 PD>'
taihu bench single --mode write --transport shm --shm /dev/TAIHU-SINGLE \
  --size 4194304 --count 20000 --threads 2 --report-interval 5s --latency
taihu bench single --mode read  --transport shm --shm /dev/TAIHU-SINGLE \
  --size 4194304 --count 20000 --threads 32 --report-interval 5s --latency

# ③ fuse 客户端（nefs.client.batcher，卷 0bb21fb2，fio 定量不回绕；写 16j×4d×12G，读 16j×8d 整读）
fio --name=t11s --directory=/mnt/fuse-single --rw=write --bs=4M --direct=1 --ioengine=libaio \
    --numjobs=16 --iodepth=4 --size=12G --fallocate=none --group_reporting=1 --lat_percentiles=1
fio --name=t11s --directory=/mnt/fuse-single --rw=read  --bs=4M --direct=1 --ioengine=libaio \
    --numjobs=16 --iodepth=8 --size=12G --fallocate=none --group_reporting=1 --lat_percentiles=1
# 读相位排空后复测一次（确认稳态，防止写相位落盘排空干扰）
```

## 6. 结论

1. **单盘隔离验证通过**：三组测试全程 nvme2n1/nvme3n1 磁盘流量 max=0.00 MiB/s，所有 IO 仅落 nvme1n1p1。
2. **storage/single 与历史持平**：写 2568~2570、读 6240~6681 MiB/s，与 2026-09-27 基线差异 ≤0.6%，异步读路径带宽/延迟无回退。
3. **fuse 写大幅提升（674 → 1504 MiB/s，+123%）**：batcher 客户端写路径把盘 util 从 25.9% 提到 56.7%，应用带宽翻倍以上、平均延迟从 379ms 降到 170ms；瓶颈仍在 fuse 客户端（核 2.68），磁盘仍有约 43% 余量，继续优化客户端写路径仍可上探。
4. **fuse 读回退 13.6%（6240 → 5393 MiB/s）**：盘 util 93.1% 接近饱和但 r_await 升到 52.75ms（历史 2.6 倍）、峰值 6076 vs 历史 6393，客户端核（3.205）与物理机 sys（3.45%）均未升高 —— 表现为盘侧排队加重，疑似读请求在 batcher 客户端路径被切块或到达不均匀，**需要单独定位（iostat rareq-sz / 客户端读请求大小核对）**。
5. **CPU 三维结论**：越靠近用户态应用（fuse），等效核数越高（写 2.68 / 读 3.21）；服务端 Storage 侧始终极低（≤0.42 核）；storage/shm 裸路径 CPU 接近零（≤0.6 核）。降 CPU 的发力点仍在 fuse 客户端与读路径。
