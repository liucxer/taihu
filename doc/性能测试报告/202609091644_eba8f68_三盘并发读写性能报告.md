# eba8f68 三盘并发读写性能报告

> 对应提交：`eba8f68`（perf: 对齐缓冲 sync.Pool 分桶池化，消除读写路径高频大块堆分配）
> 测试方式：3 个独立 taihu bench storage 进程并发，各绑一盘（每盘独立 Pebble 元数据目录）
> 对比基线：单盘读写（461d092/eba8f68 报告：读 6.8 GB/s、写 2.5 GB/s）

## 1. 测试目标

- 验证 taihu 库在 **3 块 NVMe 盘并发**场景下的读写性能与线性扩展性。
- 测量三盘接入后的整体聚合带宽、每盘延迟（p50/p90/p99）。
- 采集三盘并发期间的整机 CPU（mpstat）、三盘真实磁盘带宽（iostat），以及每盘的 pprof CPU 热点，确认多盘并发是否引入额外 CPU 开销。
- 对比 **4MiB 与 1MiB 两种对象大小**下的读写性能与 CPU 使用（pprof），确认 CPU 开销与对象大小的关系。

## 2. 测试环境

| 项目 | 配置 |
|------|------|
| 服务器 | 128.12（96 核） |
| 编译产物 | `taihu bench storage`（eba8f68，Go 1.23.12，aarch64） |
| 数据设备 | `/dev/nvme1n1`、`/dev/nvme2n1`、`/dev/nvme3n1`（各 1.8T，均 O_DIRECT） |
| 元数据 | Pebble，目录 `/tmp/tdb1`、`/tmp/tdb2`、`/tmp/tdb3`（每盘独立） |
| 读对象 | 4 KiB 对齐，**4MiB 与 1MiB 两组**；4MiB 每盘 20000 个 key（80 GiB/盘），1MiB 每盘 80000 个 key（80 GiB/盘），共 240 GiB/组 |
| 部署方式 | 编译部署 skill（commit 不 push，打包同步 128.12 解压编译） |

## 3. 测试方法

- **三盘并发写**：`-mode write`，keys 前缀 `p3w2-1/2/3`（4MiB）、`p1m-1/2/3`（1MiB）隔离批次，`-latency`，每盘独立 `-cpuprofile`。
  - 4MiB 组：4 线程/盘 × 20000；1MiB 组：16 线程/盘 × 80000（各 80 GiB/盘）。
- **三盘并发读**：`-mode read`，每盘 16 线程读各自同批 key（每 key 只读一次），LoadCache 预热元数据剔除 pebble 干扰，`-latency`，每盘独立 `-cpuprofile`。
- 编排：3 个 bench 进程同时后台启动，`wait` 全部结束后停采样；期间并行采集 `iostat -d`（三盘）与 `mpstat -P ALL`（逐核）写入独立文件（**采样文件名与 -cpuprofile 文件必须错开**，避免交叉写污染）。

## 4. 测试结果

### 4.1 三盘并发写（4 线程/盘）

| 盘 | bench 带宽 | 延迟 p50 / p90 / p99 | iostat 实测写带宽 |
|----|-----------|----------------------|-------------------|
| nvme1n1 | 2556.59 MiB/s | 6.17 / 6.24 / 8.60 ms | avg 2475.9 / peak 2594.0 MiB/s |
| nvme2n1 | 2564.18 MiB/s | 6.15 / 6.24 / 7.83 ms | avg 2483.7 / peak 2601.8 MiB/s |
| nvme3n1 | 2544.20 MiB/s | 6.16 / 6.25 / 11.74 ms | avg 2464.9 / peak 2602.9 MiB/s |
| **合计** | **7665 MiB/s（≈7.5 GB/s）** | — | ≈7.4 GB/s（avg），31.3s 写满 240 GiB |

- 每盘 tps ≈ 20000，稳态写带宽 ~2.5 GB/s，与单盘写（~2.55 GB/s）一致。

### 4.4 4MiB vs 1MiB 带宽对比

| 指标 | 4MiB | 1MiB | 变化 |
|------|------|------|------|
| 写（三盘合计） | 7665 MiB/s | 7671 MiB/s | 持平（设备写上限） |
| 读（三盘合计） | 20339 MiB/s | **16842 MiB/s** | **-17.2%** |

- 读带宽下降根因：1MiB 时 ops 数 ×3.3（~16800/s vs ~5100/s），每字节的 syscall/驱动/队列开销占比上升，设备小 IO 读吞吐峰值降至 ~5.7–5.9 GB/s（4MiB 为 6.8）。

## 5. 资源占用

### 5.1 CPU（mpstat -P ALL 全程采集）

| 场景 | busy | idle | usr | sys | iowait |
|------|------|------|-----|-----|--------|
| 三盘并发写（4MiB，4 线程/盘） | 10.7% | 89.3% | 2.4% | 0.8% | 7.2% |
| 三盘并发写（1MiB，16 线程/盘） | 36.4% | 63.6% | 2.5% | 1.0% | 32.5% |
| 三盘并发读（4MiB，16 线程/盘） | 34.9% | 65.1% | 4.5% | 1.9% | 27.3% |
| 三盘并发读（1MiB，16 线程/盘） | 34.7% | 65.3% | 3.3% | 1.5% | 29.2% |

- 读 TOP 核（如 core47 busy 84.9%）中 iowait 占 70%，usr 仅 8.8%——设备等待主导，CPU 计算仅零头。
- 1MiB 写 busy 36.4% vs 4MiB 写 10.7%：差异全在 iowait（小对象+16 线程 IO 等待更碎），usr/sys 仅 3.5%，与 4MiB 写（3.2%）持平。
- **结论：CPU 均非瓶颈**；多盘并发相对单盘读（busy 12.4%）的 busy 上升全部来自 iowait（多盘 IO 等待叠加）。

### 5.2 磁盘（iostat 实测）

- 三盘 iostat 实测与 bench 吞吐吻合，每盘均达单盘设备上限，数据设备为各盘独立瓶颈。

### 5.3 网络

- 本机 O_DIRECT 测试不涉及跨主机传输，网络带宽≈0。

## 7. 4MiB vs 1MiB CPU 使用对比

### 7.1 整机 CPU（mpstat 实测，三盘并发）

| 指标 | 4MiB 写(4T/盘) | 1MiB 写(16T/盘) | 4MiB 读(16T/盘) | 1MiB 读(16T/盘) |
|------|---------------|-----------------|-----------------|-----------------|
| busy | 10.7% | 36.4% | 34.9% | 34.7% |
| **usr（用户态计算）** | **2.4%** | **2.5%** | **4.5%** | **3.3%** |
| **sys（内核）** | **0.8%** | **1.0%** | **1.9%** | **1.5%** |
| iowait（设备等待） | 7.2% | 32.5% | 27.3% | 29.2% |

### 7.2 按吞吐归一化（每 GB/s 的 CPU 消耗）

| 场景 | 总带宽 | usr+sys | CPU/GB/s |
|------|--------|---------|----------|
| 4MiB 读 | 19.9 GB/s | 6.4% | 0.32%/GB/s |
| 1MiB 读 | 16.4 GB/s | 4.8% | 0.29%/GB/s |
| 4MiB 写 | 7.5 GB/s | 3.2% | 0.43%/GB/s |
| 1MiB 写 | 7.5 GB/s | 3.5% | 0.47%/GB/s |

### 7.3 pprof 用户态热点结构对比

| 热点 | 4MiB 写 | 1MiB 写 | 4MiB 读 | 1MiB 读 |
|------|---------|---------|---------|---------|
| `memmove`（数据搬运） | 59–62% | 61–66% | 64–67% | 53–62% |
| `Syscall6`（O_DIRECT IO） | 34–37% | ~20% | 27–30% | 27–36% |
| `futex`/`stealWork`（调度） | <1% | 3–5% | <1% | <1% |
| GC（gcDrain 等） | <1% | <1% | <1% | <2% |

### 7.4 结论

1. **CPU 计算量由字节量决定，与对象大小无关**：归一化后 1MiB/4MiB 每 GB/s 成本一致（读 ~0.3%、写 ~0.45%）；ops 数 ×3.3 但每 op 变小，单位字节开销不变。
2. **busy 的差异全来自 iowait，非计算**：1MiB 写 busy 36.4% vs 4MiB 写 10.7% 主要因线程数（16 vs 4）与小对象碎等待，iowait 从 7.2% → 32.5%，usr/sys 始终只占 3–4%。
3. **pprof 结构基本不变**：写路径 1MiB 的 Syscall6 占比降（单次 syscall 时间短）、多出 ~4% 调度开销（写提高到 16 线程）；读路径两者几乎一致。GC 均 <2%。
4. 所有场景 usr+sys ≤ 6.5%，**CPU 始终不是瓶颈**；继续降 CPU 的空间在 `io.Copy` 消费拷贝与调度开销，与对象大小无关。

## 8. 结论

1. **线性扩展**：单盘写 2.5 GB/s × 3 = **7.5 GB/s** 写；单盘读 6.8 GB/s × 3 = **≈20 GB/s** 读。三盘并发无相互干扰，性能完全线性叠加，每盘 iostat 峰值均贴齐单盘设备上限。
2. **对象大小影响**：写带宽不随对象大小变化（1MiB/4MiB 均 7.5 GB/s，设备写上限）；读带宽 1MiB 为 16.4 GB/s（-17%，小对象 syscall/队列开销占比升），但读延迟 p50 降至 2.75ms。
3. **CPU 非瓶颈且无新增开销**：所有场景 usr+sys ≤ 6.5%（4MiB 写 3.2%、1MiB 写 3.5%、4MiB 读 6.4%、1MiB 读 4.8%）；三盘 pprof 热点结构与单盘完全一致（memmove+Syscall6 合计 ~90%+），GC/pebble/锁均 <2%。多盘并发与对象大小变化均不产生额外 CPU 成本。
4. 后续如需常态化多盘压测，可为 bench 增加 `-devs nvme1n1,nvme2n1,nvme3n1` 单进程多盘参数，替代多进程编排。
