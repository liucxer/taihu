# 461d092 写性能测试报告

> 对应提交：`461d092`（bench: 增加 -cpuprofile/-memprofile(pprof) 与 -latency 写延迟统计）

## 1. 测试目标

- 确定写操作达到 **2.5 GB/s** 所需的最低线程数。
- 测量写带宽、延迟（p50/p90/p99）。
- 采集测试期间物理机的 CPU、磁盘带宽占用，以及测试程序的 pprof CPU 热点。

## 2. 测试环境

| 项目 | 配置 |
|------|------|
| 服务器 | 128.12 |
| 编译产物 | `taihu bench storage`（Go 1.23.12，aarch64） |
| 数据设备 | `/dev/nvme1n1`（O_DIRECT） |
| 元数据 | Pebble，目录 `/tmp/tdb1` |
| 对象大小 | 4 KiB 整数倍，单对象 256 KiB 传输缓冲 |
| 部署方式 | 编译部署 skill（commit 不 push，打包 `taihu.<commit>.tar.gz` 同步 128.12 解压编译） |

## 3. 测试方法

- 使用 `taihu bench storage`，参数：`-mode write`、`-size 4M`、`-threads N`、`-keys-prefix bench`、`-db /tmp/tdb1`、`-dev /dev/nvme1n1`、`-latency`。
- 写入 count 个**不同 key** 的对象，避免读/写到相同 key。
- 写路径：游标分配下沉到 Pebble（`AllocateSegment`），设备写在分配锁之外并发执行；元数据 cursor/mapping 同步写。
- 写的 fd 使用 **O_DIRECT**：数据不经页缓存直接落到设备，等效同步刷盘（非异步批量刷盘）。
- 元数据（cursor/mapping）仍走 Pebble 同步写。

## 4. 测试结果

### 4.1 写带宽与最低线程数

| 线程数 | 写带宽 | 说明 |
|--------|--------|------|
| 4 | 2529.45 MiB/s（≈2.5 GB/s） | **达到 2.5 GB/s 阈值的最低线程数** |
| 16 | 2554 MiB/s（≈2.5 GB/s） | 大规模（80GB/20000×4M）稳定结果 |

- 结论：写操作**最低线程数为 4** 即可稳定达到 2.5 GB/s 目标。
- 写带宽已不再随线程数线性提升，说明已逼近设备写能力上限。

### 4.2 写延迟

| 指标 | 线程 4 | 线程 16 |
|------|--------|---------|
| p50 | 6.18 ms | ≈24.8 ms |

- 线程 4 时写延迟最低（p50 6.18 ms）。
- 线程 16 时因队列加深，p50 上升至约 24.8 ms（带宽基本不变）。

## 5. 资源占用

### 5.1 CPU

- 系统整体 **idle 95.09%**，近乎空闲。
- 96 核统计：最忙核的负载主要来自 **iowait**，计算占用仅个位数。
- 写线程=4 时，CPU 利用率最高不到 20%。
- **结论：CPU 不是写性能瓶颈。写性能由设备 IO 决定。**

### 5.2 磁盘

写测试期间用 `iostat -d` 逐秒采样 `/dev/nvme1n1`（30 个有效样本），实测真实磁盘写带宽：

| 项目 | 值 |
|------|-----|
| 磁盘写带宽（稳态逐秒） | ≈2550–2660 MiB/s |
| 磁盘写带宽峰值 | 2600.8 MiB/s |
| 磁盘写带宽（稳态平均） | ≈2560 MiB/s |
| 写 IOPS（tps） | ≈20000–20800 |
| 磁盘读带宽 | ≈0（纯写测试） |

- 实测磁盘写带宽与 bench 写吞吐 **2560.51 MiB/s** 吻合，说明写入瓶颈在设备端而非应用/元数据层。
- 写 IOPS 高达约 2 万 tps（串行小 IO 队列），数据设备为当前主要瓶颈。

## 6. 瓶颈分析与 pprof 热点

- 写路径瓶颈：**设备写 IO**（util ~79%），而非元数据或 CPU。
- 元数据层（缓存 cursor + mapping）通过 `AllocateSegment` 下沉后已在锁外并发写设备。
- pprof CPU 热点（写线程模式）：
  - `runtime.memmove`：22.8%
  - `runtime.memclr`：12.9%
  - `internal/runtime/syscall.Syscall6`：12.35%

### 6.1 写 CPU 热点的业务代码定位

与读测试 GC 主导不同，写测试 CPU 占用极低（idle 95.09%，线程4 最高不到 20%），**热点为「数据搬运 + 缓冲清零 + 写系统调用」三项，且无 GC 主导**。对应业务代码如下：

**1）`memmove`（22.8%）— `Device.append` 的 `io.ReadFull` 整块拷贝**

[device.go:L69](file:///Users/liucx/gopath/src/github.com/liucxer/taihu/device.go#L58-L87)：

```go
buf := alignedBuffer(int(aligned))
if _, err := io.ReadFull(data, buf[:size]); err != nil { ... }  // ← 4MiB 整块 memmove
```

把调用方 Reader（bench 的 `sliceReader`，[main.go:L222-L229](file:///Users/liucx/gopath/src/github.com/liucxer/taihu/cmd/taihu bench storage/main.go#L222-L229)）的 4MiB payload 整体搬入对齐缓冲；每 op 一次 4MiB 搬运，对应写吞吐 ~2.5 GiB/s 全部经 `memmove`。

**2）`memclr`（12.9%）— [alignedBuffer](file:///Users/liucx/gopath/src/github.com/liucxer/taihu/device.go#L98-L105) 每次写 `make` 清零 4MiB+4KiB**

```go
backing := make([]byte, n+int(BlockSize))   // ← 每次写分配并清零大对象
```

每次写分配一个 4MiB+4KiB 堆缓冲（640 ops/s × 4M ≈ 每秒堆分配 ~2.5GB），`make` 清零即 `memclr`；（size 恰为 4K 对齐时 [device.go:L72](file:///Users/liucx/gopath/src/github.com/liucxer/taihu/device.go#L72) 的 `clear(buf[size:])` 为空，非热点源）。

**3）`Syscall6`（12.35%）— `d.f.WriteAt`（O_DIRECT 写系统调用）**

[device.go:L76](file:///Users/liucx/gopath/src/github.com/liucxer/taihu/device.go#L74-L85) 与 L82 的两次 `WriteAt`，经 `Syscall6` 进入内核落盘。

**修复方向：** 写缓冲同样可复用 `sync.Pool` 降低 `memclr`/GC，但写带宽由设备写 IO（util ~79%）决定，**CPU 并非写瓶颈，此处优化对写带宽基本无收益**。

## 7. 结论与建议

- 写最低线程数 = **4**，可稳定达 2.5 GB/s；读最低线程数 = **16**，可稳定达 6.5 GB/s（读/写线程数可不同）。
- 写性能受设备写 IO（util ~79%）与 IO 队列限制，CPU 占用极低。
- 优化建议：
  - 写带宽已基本到达裸设备上限（dd O_DIRECT 约 2.1 GB/s，库内已达 2.5 GB/s），进一步提升需更换更高性能设备或使用多设备条带化。
  - 若需降低 CPU 占用，可用 `sync.Pool` 复用 4K 对齐缓冲，减少 `memmove`/`memclr` 的分配与清零开销。
