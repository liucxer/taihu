# segment 级 GC（对象删除驱动的段回收与复用）设计与测试方案

> 实现 commit：6c5297e（segment GC + 复用）
> 本文档对应代码：`internal/metastore/segments.go`、`internal/metastore/kv_pebble.go`、`pkg/taihu/storage.go`（Ref/Unref）
> 测试代码：`internal/metastore/segments_test.go`、`pkg/taihu/storage_test.go`

## 1. 背景与目标

对象删除后，其占用的段内空间不会立即释放（append-only 写模式）。长期运行会积累大量"孤儿段"：段内对象全部被删除，但物理空间仍被占用，无法写入新对象。

本文档的 GC 以 **segment 为回收粒度**：

- 目标 1：对象删除驱动的段回收——段内对象计数归零的段可被整体回收。
- 目标 2：回收段的复用——空闲段池供分配器在游标到顶时取用，保持"段内顺序写"的磁盘访问模式。
- 目标 3：并发安全——回收与在途读不产生竞态（读引用计数），计数与 mapping 原子一致（WriteBatch）。

## 2. 设计

### 2.1 段状态机

```
                    分配写入                游标写出段尾
  (首次)   ┌──────┐ ────────> ┌────────┐ ─────────────> ┌──────┐
           │ None │           │ Active │                │ Full │
           └──────┘           └────────┘                └──────┘
  (回收入池)                        ▲                       │
           ┌────────┐  ────────────┘                       │ 对象全部删除
           │ Free   │ <── GC 确认无在途读者                 ▼
           └────────┘      ┌──────────────────────┐   ┌────────────┐
             ▲  │          │    Reclaiming        │<──│  (计数归零) │
             │  └─ 复用     └──────────────────────┘   └────────────┘
             └─── 分配器取池
```

| 状态 | 含义 | 转换 |
|------|------|------|
| None（无记录） | 从未写入 | 首次分配 → Active |
| Active | 正在顺序写入 | 游标写出段尾 → Full；被写新对象保持 Active |
| Full | 已写满，仅读 | 计数归零 → Reclaiming |
| Reclaiming | 待回收（计数 0） | GC 确认 refCount==0 → Free |
| Free | 空闲可复用 | 被新对象写入 → Active（移出池）；被分配器选中 → Active |

### 2.2 存活计数 AliveCount

- 每段维护"现存对象数"，与 mapping 写在同一 pebble **WriteBatch 原子提交**（`putObject` / `delObject`），保证计数与映射要么同时生效、要么同时不生效。
- **覆盖写**（同 key 重复 Put）：新段计数 +1，旧段计数 −1；新旧同段则计数不变，不泄漏。
- 计数归零 → 立即置 Reclaiming。
- **启动恢复**：以 `seg/` 前缀恢复段状态，随后**全量扫描 mapping 重建计数（权威）**——持久化的 AliveCount 被丢弃，避免双重累加；若发现"段标记 Free 但 mapping 仍有对象"，以 mapping 为准回退 Active 并移出空闲池（不一致自愈）。

### 2.3 读引用计数 RefCount

防止竞态：GC 把 Reclaiming 段转 Free 并投入空闲池后，分配器可能立即复用并覆写数据，此时仍在途的读会读到错乱数据。

- `Ref(segmentID)`：读开始前调用；`Unref(segmentID)`：读结束后调用。
- `reclaimOnce` 只回收 `State==Reclaiming && refCount==0` 的段。
- 读路径接入点：`pkg/taihu/storage.go` 的 `ReadAt` 在 `device.ReadAt` 前后对称调用 Ref/Unref。
- 对未知段（从未写入）Ref/Unref 为空操作，不产生段记录。

### 2.4 空闲段池 Free Pool

- FIFO 队列 `free []int64`，内存态；回收时入池，复用时出池，状态变更随 pebble 持久化。
- 分配器滚动策略（`AllocateSegment`）：
  1. 段内放不下 → 旧段 markFull；
  2. 下一段未使用或 Free → **顺序滚动**（正常路径，保持磁盘顺序写）；
  3. 下一段已被占用（Active/Full/Reclaiming）或游标到顶 → **取空闲池复用**（游标回跳，段内仍顺序写）；
  4. 池空 → `ErrNoSpace`。
- 每次换段持久化游标，崩溃后游标不回退。

### 2.5 后台 GC goroutine

- `Open` 时启动，周期 `gcInterval = 1s`；
- 每轮 `reclaimOnce`：收集所有 Reclaiming 且 refCount==0 的段 → 置 Free、AliveCount=0、ReclaimSeq++、入池，批量 WriteBatch 持久化；
- `Close` 时 `stopGC` 停止并等待退出。

### 2.6 崩溃一致性

- mapping/计数/段状态三者在同一 WriteBatch，原子提交。
- 回收落盘失败：段留在内存 Free 态，下轮重试写入（可容忍，最终一致）。
- 启动 rebuild 的计数重建保证任何崩溃后计数自洽。

### 3.3 L3 端到端验证（真机 128.12 裸盘）

流程：
1. 启动 taihu-server（最新代码，含 GC），-db 指向 pebble 目录，-dev 指向裸盘；
2. 用 taihu-rpc-bench `-mode write` 写入 N×4MiB 对象（分多段）；
3. `-mode delete` 全量删除，触发段计数归零 → Reclaiming；
4. 观察 server 日志/`SegmentStats`：段转为 Free 并入池；
5. 再次 `-mode write` 灌入新对象，验证分配器复用 Free 段（游标回跳）、数据读写正确；
6. 重启 server 验证 rebuild 后状态一致（计数、空闲池、游标）。

## 4. 测试结果

### 4.1 本地（Windows amd64）功能测试

```
go test ./internal/metastore/ ./pkg/taihu/ ./internal/aio/ -count=1   → ok
```

- metastore 层 12 个用例全部通过。
- 修复了 Windows 平台 aio 兜底实现两个既有缺陷（非 GC 引入）：
  - `aio_other.go` submit goroutine 对 `os.NewFile` 包装句柄调用 `Close()`，关闭了调用方持有的底层句柄 → 后续提交 EBADF；改为不 Close（os.File 无 finalizer 关句柄，随 GC 释放）。
  - `ReadAt` 越界返回 `io.EOF` 未归一化为 0 字节（与 Linux pread 语义不一致）。
- pkg/taihu 的 Restart 用例在 Windows 上偶发 pebble MANIFEST 时序问题（Windows 平台 pebble 偶发），单独连跑 3 次通过，判定为平台噪声。

### 4.2 128.11（linux/arm64，gcc 10.3.1 + go1.25）`-race` 全绿

128.12/128.13 的 gcc 为 7.3.0，缺 aarch64 原子内建符号（`__aarch64_swp1_acq` 等）无法链接 TSan；128.11 为 gcc 10.3.1，可跑 `-race`。

```
cd /tmp/taihu-gc && CGO_ENABLED=1 go test -race -count=1 -v \
  ./internal/metastore/ ./pkg/taihu/ ./internal/aio/   → 26 个 --- PASS，0 个 FAIL，无 DATA RACE
ok  github.com/liucxer/taihu/internal/metastore  2.524s
ok  github.com/liucxer/taihu/pkg/taihu            5.798s
ok  github.com/liucxer/taihu/internal/aio         1.280s
```

注意：pkg/taihu 测试须设置 `TMPDIR` 到 xfs 文件系统（/root/tmp），因 /tmp 为 tmpfs 不支持 O_DIRECT 打开。

### 4.3 `-race` 发现并修复的竞态

- **TestBackgroundGCPeriodic 数据竞争**：测试辅助函数 `segState` 在 segmentManager 锁内返回内部指针，调用方解锁后解引用读 `meta.State`，与后台 GC goroutine 的 `reclaimOnce` 写入竞争。修复：`segState` 改为返回条目**深拷贝快照**，锁外读取安全。

## 5. 已知限制与后续优化

- 部分填充段（Full 但计数 > 0）暂不压缩：仅当整段对象删光才回收，可能存在空间空洞。后续可引入段内 compaction（存活对象搬移到新段）提升空间利用率。
- 空闲池为内存态，仅以段状态落盘；极端情况下（崩溃于回收落盘前后）由 rebuild 自愈。
- 聚合带宽上限受 loopback 限制（~16.5 GiB/s，见 loopback 标定报告），GC 为后台低频操作，对稳态读写带宽无影响。
