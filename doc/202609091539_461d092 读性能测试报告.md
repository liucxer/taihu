# 461d092 读性能测试报告

> 对应提交：`461d092`（bench: 增加 -cpuprofile/-memprofile(pprof) 与 -latency 写延迟统计）

## 1. 测试目标

- 验证读操作在 **16 线程**下是否稳定达到 **6.5 GB/s**。
- 测量读带宽、延迟（p50/p90/p99）。
- 采集测试期间物理机的完整 CPU 信息、真实磁盘带宽，以及测试程序 pprof CPU 热点。

## 2. 测试环境

| 项目 | 配置 |
|------|------|
| 服务器 | 128.12 |
| 编译产物 | `taihu-bench`（461d092，Go 1.23.12，aarch64） |
| 数据设备 | `/dev/nvme1n1`（O_DIRECT） |
| 元数据 | Pebble，目录 `/tmp/tdb1` |
| 读对象 | 4 KiB 对齐，单对象 4 MiB，20000 个不同 key |
| 部署方式 | 编译部署 skill（commit 不 push，打包 `taihu.<commit>.tar.gz` 同步 128.12 解压编译） |

## 3. 测试方法

- 使用 `taihu-bench`，参数：`-mode read`、`-size 4194304`、`-threads 16`、`-count 20000`、`-keys-prefix p4m-iostat`、`-db /tmp/tdb1`、`-dev /dev/nvme1n1`、`-latency`、`-cpuprofile /tmp/r.cpuprofile`、`-memprofile /tmp/r.mem`。
- 读的是先前写测试写入的**同一批 20000 个 key**（每个 key 全进程只读一次，不重复）。
- 读前 `LoadCache` 预热元数据，剔除 pebble 读对带宽的影响。
- 测试期间并行后台采集：`iostat -d`（真实磁盘带宽）、`mpstat -P ALL`（逐核 CPU）、`/proc/net/dev`（网络）；测试结束取 pprof。

## 6. 瓶颈分析与 pprof 热点

- 带宽已达 6.5 GB/s 且抵近设备读上限，但 **CPU 热点高度集中在 Go GC**，非数据拷贝本身：

| 热点函数 | flat% |
|----------|-------|
| `runtime.(*gcWork).tryGetFast` | 16.84% |
| `runtime.(*lfstack).pop` | 13.14% |
| `runtime.markBits.setMarked` | 10.43% |
| `runtime.memclrNoHeapPointers` | 9.84% |
| `runtime.memmove` | 8.42% |
| `runtime.gcDrain`（累计） | 64.29% |

- GC 主导（gcDrain 累计 64.29%）根因：**读路径每个 Get/读操作 `make` 新的 4K 对齐缓冲**，高频分配驱动 GC。
- `memclrNoHeapPointers`（9.84%）来自对齐缓冲清零；`memmove`（8.42%）来自 sliceReader→对齐缓冲的中转拷贝。

### 6.1 GC 热点的业务代码定位

**主因（GC 压力来源）：`Device.read` 每次读分配 4MiB 对齐堆缓冲**

[device_linux.go:L31](file:///Users/liucx/gopath/src/github.com/liucxer/taihu/device_linux.go#L23-L37)：

```go
buf := alignedBuffer(int(size))   // ← 每次读 make 一个 4MiB+4KiB 堆缓冲
n, err := d.f.ReadAt(buf, pos)
return bytes.NewReader(buf[:n]), nil
```

[alignedBuffer](file:///Users/liucx/gopath/src/github.com/liucxer/taihu/device.go#L98-L105) 实现为 `make([]byte, n+BlockSize)` 再对齐切片。

用量：bench 读测试 **1632 ops/s × 4MiB ≈ 每秒堆分配 ~6.5GB**。4MiB+ 属 Go 大对象，GC 标记阶段需单独处理（markBits/gcWork/lfstack 全被占用），直接对应 pprof 热点 `gcDrain 64.29%`、`gcWork.tryGetFast 16.84%`、`lfstack.pop/push ~20%`、`markBits.setMarked 10.43%`；`make` 清零即 `memclrNoHeapPointers 9.84%`，`ReadAt` 拷入 + `bytes.Reader` 被 `io.Copy` 拷出即 `memmove 8.42%`。

**次要分配（每 op 几个小对象，量级与 GC 无关）：**

- [storage.go:L106](file:///Users/liucx/gopath/src/github.com/liucxer/taihu/storage.go#L91-L116) `s.dev.read(...)` 返回的 Reader；[storage.go:L115](file:///Users/liucx/gopath/src/github.com/liucxer/taihu/storage.go#L110-L115) `io.NopCloser(io.LimitReader(...))` 每 Get 两个小包装对象
- [device_linux.go:L36](file:///Users/liucx/gopath/src/github.com/liucxer/taihu/device_linux.go#L36) `bytes.NewReader(...)`

**非原因：** [storage.go:L111](file:///Users/liucx/gopath/src/github.com/liucxer/taihu/storage.go#L110-L111) 的 `io.CopyN(io.Discard, r, skip)` 仅在非对齐 off 时触发，bench 整读（off=0）不执行。

**修复方向：** 用 `sync.Pool` 按 size 分桶复用对齐缓冲（读后归还），消除每秒 6.5GB 堆分配；GC 热点（gcDrain ~64%）基本消失，读带宽有望进一步贴齐设备上限。

## 7. 结论与建议

- **16 线程读稳定达 6.5 GB/s**（6529.44 MiB/s，p50=9.74ms），为读最低线程数。
- 读带宽受设备读能力与 GC 共同影响，CPU 整体空闲（idle 76.2%），非 CPU 满载瓶颈。
- 优化建议（针对 GC 热点）：
  - 用 **`sync.Pool` 复用 4K 对齐缓冲**，消除每次读的高频分配，可显著降低 GC（gcDrain ~64%）与 `memclr` 开销。
  - 减少 `sliceReader→对齐缓冲` 的中转拷贝（`memmove` 8.42%），例如按需对齐。
