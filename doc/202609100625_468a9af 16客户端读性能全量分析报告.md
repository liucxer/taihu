# 16 客户端读性能全量分析报告（CPU / 磁盘 / 网络 / pprof）

- 测试时间：2026-09-10 03:00~03:03（CST）
- 代码版本：468a9af（taihu-server 新增可选 pprof 端点）
- 测试环境：128.12 单机，client 与 server 同机走 lo 回环，96 核 aarch64
- 压测方式：16 个独立 `taihu-rpc-bench` 进程（各 16 线程 = 256 并发流），4MiB 对象 × 1500/客户端，`lim-16-c*` 前缀（共 96GB 数据）

## 五、Server pprof（CPU profile 15s，go tool pprof -top）

**总样本 441.37s（≈29.04 核满负荷），Top 平铺热点：**

| 函数 | flat | flat% | 性质 |
|---|---|---|---|
| `runtime.memmove` | 212.33s | **48.11%** | 数据拷贝 |
| `internal/runtime/syscall.Syscall6` | 89.85s | **20.36%** | 系统调用（socket/O_DIRECT） |
| `runtime.memclrNoHeapPointers` | 85.37s | **19.34%** | 缓冲清零 |
| `runtime.runqgrab` / `stealWork` / `schedule` | ~6s | ~1.5% | 调度 |
| grpc loopyWriter.processData / writeQuota | ~5s | ~1.2% | gRPC 发送循环 |

**内存拷贝合计：memmove(48.11%) + memclr(19.34%) ≈ 67.5%** —— server 每字节开销被数据搬运/清零主导。

**调用链（cum 视角）印证拷贝路径：**
- `main.Get` cum 54.79% → `SendMsg` cum 35.17% → `loopyWriter.processData` cum 38.24% → `bufWriter.Write` cum 20.01% → `FD.Write` cum 18.18% → `Syscall6`
- `proto.MarshalOptions.marshal` cum 14.44%（protobuf 编码拷贝）
- `mem.sizedBufferPool.Get` cum 19.62%（gRPC 缓冲池）

即：**Get 读盘 → 数据进入 GetChunk → proto.Marshal 拷入编码缓冲 → gRPC 帧缓冲 → 回环 socket**，全程多次 memcpy，全部落在 server 侧。

## 六、Client pprof（16 客户端中 2 个，各 ~250% ≈ 2.5 核）

| 函数 | flat% |
|---|---|
| `runtime.memmove` | 29~33% |
| `internal/runtime/syscall.Syscall6` | ~20% |
| `runtime.memclrNoHeapPointers` | 15~17% |
| 内存操作合计 | ≈45~50% |

客户端同样被 memmove/memclr/syscall 主导（Recv 反序列化 + `io.Pipe` 写入拷贝）。

## 七、瓶颈结论

1. **瓶颈 = server 侧每字节 CPU 拷贝成本**，非磁盘（80%）、非网络（回环充足）、非核数（仅 29/96 核）。
2. **server 侧 memmove 48% 是最大单项开销**：读路径中数据至少经历 2 次多余搬运——① `GetChunk` proto.Marshal 编码拷贝（cum 14.44%），② gRPC 缓冲池/帧缓冲与回环 socket 间的搬运（bufWriter + syscall）。
3. 客户端侧 memmove ~30% 对应 `io.Pipe` 写入 + 数据帧到调用方缓冲的拷贝。
4. **优化方向（按收益排序）**：
   - server `Get` 去掉 proto.Marshal 的额外拷贝（如 GetChunk.Data 直接复用读缓冲、或大块单帧直发）；
   - client `Get` 去掉 `io.Pipe` 双拷贝（边 Recv 边直写目标缓冲）；
   - 减少 memclr：缓冲池复用避免每 chunk 清零（gRPC `sizedBufferPool` 已部分覆盖，可再验证）。
   - 上述任意一项若砍掉 server 侧 ~48% 的 memmove，理论上可将 16 客户端读从 5.36G 推向磁盘极限 6.6G 附近。
