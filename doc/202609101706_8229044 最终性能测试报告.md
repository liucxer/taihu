# 8229044 最终性能测试报告（三服务端并行读）

> 对应提交：`8229044`（当前 HEAD；读路径优化链：939bf51 bufpool freelist → 9ab203d 桶错配修复 → b91974f 客户端 L90 池化 → cf40e0a 撤回收帧池注入）
> 测试：3 服务端 × 3 客户端并行 RPC 读（各 32T/16C/4M，loopback，客户端+服务端同机 128.12）

## 1. 测试目标

对当前最优形态（bufpool 自管理 freelist + 对齐桶修复 + 客户端 Get 返回池化缓冲，未做 gRPC 收帧注入）进行三实例并行读定界，汇总完整优化历程的收益与教训，作为读路径基准配置与未来优化依据。

## 3. 测试方法

`taihu-rpc-bench -mode read -size 4194304 -threads 32 -conns 16 -count 20000 -keys-prefix <p> -latency -cpuprofile <n.cpu>`；三端并行稳态 22.6s。

采集：`mpstat -P ALL 1`（整机+逐核）、`iostat -d nvme{1,2,3}n1 1`、`/proc/net/dev`（lo 差分）；服务端经 pprof 端口抓 10s；版本经 `md5sum` 校验、PID 经 `ss` 核对。CPU 实占 = usr+sys（iowait 计入可用）。

## 5. 优化历程与收益（读路径）

| 提交 | 改动 | 效果 |

单实例对照：32T×16C 单客户端 6.39 GB/s（2a0a2ec 时）；三实例聚合 10.3（线性度 54%，受整机 CPU/网络资源共享约束）。

## 6. 被否决方案与教训（已记入性能测试 skill）

1. **RawFrame.Take 零拷贝移交帧缓冲**：跳过 buffer.Free 致 gRPC 流控窗口不归还（16M/4 帧耗尽），高并发 RecvMsg 永久阻塞。→ 帧缓冲必须按 gRPC 生命周期 Free，CopyTo 聚合是保持窗口推进的必要代价。
2. **experimental.WithBufferPool 注入自定义收帧池**：16T8C 读从 1361 ops/s 暴跌至 ~20 ops/s（~60 倍）。gRPC 收帧热路径依赖默认 tiered pool。→ 只做应用层 L90 池化。

## 7. 结论与建议

1. **当前稳定基准**：三实例并行读 **10.3 GB/s**、整机实占 usr+sys 40.3%、客户端 8.7 核/实例、服务端 3.5 核/实例；服务端纯 syscall、客户端 memclr 归零，均无可削用户态开销。
2. **瓶颈归属**：整机 CPU（syscall 处理，busy 75.5%）+ loopback 吞吐（AVG 10.6 / PEAK 11.4 GB/s）；磁盘每盘 3.33 GB/s 相对单盘潜力 6.4 只用一半（被上游 CPU/lo 压住）。
3. **进一步方向**（收益递减排序）：
   - 客户端 handleData 收帧拷贝（~30%）与 CopyTo（~24%）的消除需深度 fork gRPC 收侧（wire 直写调用方缓冲），可行但工程量大、风险高；
   - 服务端 syscall（89%）已近纯 IO，仅批量 IO（io_uring 类）可能再降；
   - 若追求更高聚合带宽，跨机部署绕开同机 lo/CPU 共享是更直接手段（受物理网卡约束）。
4. 建议以 8229044 作为读路径基线配置（16T×16C/客户端亦可，见 9ab203d 报告向 6.0+ GB/s 的最小配置）。
