# 8abdf4d 三服务端并行读性能测试报告

> 对应提交：`8abdf4d`（feat: 接入 aio 设备 IO 与 netpoll fork 零拷贝，重构 device 与 transport）
> 测试：3 服务端 × 3 客户端并行 RPC 读（各 32T/16C/4MiB×20000，loopback，客户端+服务端同机 128.12）
> 测试时间：2026-09-10 22:09 ~ 22:11

## 1. 测试目标

验证传输层切换为 **netpoll+LinkBuffer 帧协议**、设备层接入 **aio（libaio 异步 IO）** 后的多实例部署聚合读能力：

- 3 个 taihu server（各绑一块 NVMe）× 3 个 taihu bench cluster 客户端（各 32 线程 / 16 连接 / 4MiB 对象）并行读的聚合应用层带宽、延迟；
- 物理机 CPU（整机 + 逐核）、三盘真实磁盘带宽（iostat 实测）、loopback 网络带宽；
- 3 客户端 + 3 服务端 pprof，定位聚合上限来源。

## 3. 测试方法

1. **数据准备**：3 客户端并行 `-mode write`（各 16 线程/16 连接，20000×4MiB=80GB/端点，前缀 p4m-s1/2/3），`-latency`；
2. **主读测**：3 客户端并行 `-mode read -size 4194304 -threads 32 -conns 16 -count 20000 -keys-prefix p4m-s{1,2,3} -latency -cpuprofile <c{n}.cpu>`，同批 key 各读一次；
3. 全程 `mpstat -P ALL 1`、`iostat -d nvme1n1 nvme2n1 nvme3n1 1`、`/proc/net/dev`（lo 差分）逐秒采样；
4. 读测期间抓 3 服务端 pprof（:6061/62/63 各 30s）；
5. 客户端 cpuprofile 与 pprof 拉回本地 `go tool pprof` 分析。

## 6. 瓶颈分析与 pprof 热点

1. **客户端（7.6~8.1 核/实例，瓶颈侧）**：memmove ~52% 中 `Conn.Get` 汇入拷贝占 69%（收帧逐段 copy 进 bufpool 对齐缓冲），`UnsafeLinkBuffer.Next` 占 31%（帧数据搬移）；Syscall6 ~43% 为 recv 收流。客户端仍是每 op 1 次对齐汇入拷贝 + 收帧拷贝，这是 gRPC 时代即存在的必要成本（netpoll 下无法免去，见 rpc-zerocopy-plan 结论）。
2. **服务端（2.4~2.5 核/实例）**：纯 syscall（sendmsg 99.8%），aio 读提交仅 ~8%；磁盘等待完全异步化，服务端用户态归零。
3. **磁盘**：每盘 4.3~4.4 GB/s，为单盘读极限（~6.6 GB/s）的 **65%**——三盘聚合 12.8 GB/s 已把整机 lo 带宽（AVG 12.6 / PEAK 13.8 GB/s）压到高位，磁盘非独立瓶颈。
4. **聚合上限来源**：客户端收帧处理（memmove+recv）与 loopback 吞吐共同构成聚合上限；物理机 CPU 尚有 ~60% 空闲但 lo 与应用层带宽已基本贴顶，继续加实例预期被 loopback/客户端 syscall 放大而非磁盘。

## 8. 结论与建议

1. **多实例聚合读 12.7 GB/s（3×3）**（gRPC 时代 10.3 → +23%），单盘 4.3~4.4 GB/s（+29~32%），服务端进程 CPU -29%，读延迟 p50 -44%。
2. **压力扩展 6×3 达 14.1 GB/s（+11%）**，但延迟 ~2.4x、服务端 CPU ~2x，lo 峰值 16.9 GB/s 近顶，边际收益递减。
3. **服务端形态健康**：纯 syscall（sendmsg+aio），无用户态拷贝，iowait 归零；磁盘异步化收益显著。
4. **客户端仍是聚合上限来源**：收帧汇入拷贝（CopyTo ~69% of memmove）+ recv syscall。进一步优化方向：客户端 Get 收帧直写调用方缓冲（需 netpoll 收侧深改）、或减小单帧往返开销。
5. 本机 lo（3×3 时 AVG 12.6 / PEAK 13.8 GB/s）已近顶；若需更高聚合带宽，跨机部署绕开同机 lo/CPU 共享是更直接手段（受物理网卡约束）。
