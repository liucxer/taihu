# taihu 三节点集群端到端读写性能测试报告（128.11/12/13 × 3 盘，直读共享内存版）

日期：2026-09-11
基线 commit：`fca9658`（O_DIRECT 直读共享内存：服务端读路径免 memcpy）
部署二进制（三节点一致）：`taihu-server.direct`（md5 fc466398）/ `taihu-rpc-bench.direct`（md5 cb041696），均 arm64

## 1. 测试目标

三节点 × 3 盘位（9 实例）taihu 集群端到端读写性能，采集：
物理机 CPU（mpstat）、客户端/服务端进程 CPU（pidstat）、网络带宽（/proc/net/dev 差分）、
客户端与服务端 pprof、客户端带宽与延迟（bench 输出）。

## 2. 测试环境

| 项 | 值 |
|----|----|
| 节点 | 100.71.128.11 / .12 / .13（各 96 核 aarch64） |
| 实例 | 每节点 3 × taihu-server（:50051-53，-shm 共享内存 IPC，-pprof :6061-63） |
| 数据设备 | 每节点 nvme1n1/nvme2n1/nvme3n1 |
| 元数据 | pebble（/tmp/taihu-db/nvme{1,2,3}）+ TiKV 索引（PD 三节点 2379） |
| 压测 | taihu-rpc-bench 集群模式（-node/-tikv-pd），客户端放各节点本机 |
| 对象 | 4 MiB × 40000/节点（各节点独立前缀 p4m-cl3a/b/c，避免覆盖写） |
| 线程 | 32/节点 |
| 采样 | mpstat -P ALL、pidstat、/proc/net/dev 差分、pprof（客户端 -cpuprofile / 服务端 :6061） |

## 3. 测试方法

三节点**并行**执行（各写/读本地盘，独立前缀互不干扰）：
- 写：`-mode write -node <N> -keys-prefix p4m-cl3{a|b|c} -size 4194304 -count 40000 -threads 32 -latency -cpuprofile`
- 读：`-mode read` 同批 key（各读自己前缀）
- 测试前用 idxquery 验证索引分布：p4m-cl3a→n11-*、p4m-cl3b→n12-*（各写本地 ✓）

## 7. 进程 CPU（pidstat 均值，%CPU 相对单核）

| 阶段 | 节点 | 客户端 bench | 服务端 server（×3） |
|------|------|-------------|---------------------|
| 写 | 128.11 | 204% | 30% / 进程 |
| 写 | 128.12 | 216% | 36% / 进程 |
| 写 | 128.13 | 233% | 35% / 进程 |
| 读 | 128.11 | 112% | 16% / 进程 |
| 读 | 128.12 | 110% | 14% / 进程 |
| 读 | 128.13 | 133% | 13% / 进程 |

写客户端 CPU 高（204-233%）：写路径 payload→共享内存 memcpy（固有）；读客户端 ~1.1-1.3 核（零拷贝）。

## 8. 网络带宽（/proc/net/dev 差分）

| 阶段 | 节点 | 数据面 | 说明 |
|------|------|--------|------|
| 写 | 全部 | **0**（bond0 仅 ~15MB） | 15MB = TiKV 索引写入（40000×3 节点 gRPC）；数据走 shm/本地 |
| 读 | 全部 | **0** | 专项验证：128.11 读 8000 key（32GB）bond0 增量 0MB；TiKV 索引查询 MB 级 |

**数据面零网络带宽**：同机实例走 shmipc 共享内存，跨节点仅 TiKV 元数据（MB 级）。

## 9. pprof 热点（128.11 代表性，各节点同构）

### 写
| 进程 | 热点 | 占比 | 说明 |
|------|------|------|------|
| 客户端 | runtime.memmove | 86.2% | 写路径 payload 拷贝进共享内存（shmWriteFrame） |
| 服务端 | runtime.memmove | 71.7% | Put 汇集：共享内存请求帧→bufpool 缓冲 |

### 读
| 进程 | 热点 | 占比 | 说明 |
|------|------|------|------|
| 客户端 | syscall.Syscall6 | 19.7% | shm 事件等待/调度；**无 memmove**（take 零拷贝） |
| 服务端 | syscall.Syscall6 | 80.5% | O_DIRECT 读（io_submit/io_getevents）；**memmove 0**（直读生效） |

**直读改造验证**：读路径服务端 memmove 从 65.9% → **0**，CPU 全部转为 O_DIRECT syscall。

## 10. 瓶颈分析

- **写**：单盘写极限 2.5 GiB/s/盘，每节点 3 盘聚合 7.3 GiB/s；三节点 21.4 GiB/s。写路径 memcpy（客户端 payload→shm、服务端 shm→bufpool）为服务端/客户端 CPU 主要来源，但物理机 busy 仅 ~2.5%，非瓶颈。
- **读**：每节点 3 实例聚合 17.2-17.4 GiB/s（每实例 ~5.8 GiB/s，单盘上限 6.58 的 88%，差距为 shm 协议往返+磁盘 IO）；三节点 51.7 GiB/s。服务端 CPU 完全释放（memmove 0），瓶颈在磁盘 IO。
- **网络**：数据面零占用（同机 shm），无网络瓶颈。

## 11. 结论

1. 三节点×3 盘位集群端到端：**写 21.4 GiB/s、读 51.7 GiB/s**，零拷贝 take 100%。
2. 直读共享内存改造生效：读路径服务端 memmove 65.9%→0，服务端 CPU 从读路径释放（busy ≤2%）。
3. 瓶颈分层：写=单盘写极限；读=单盘 IO + shm 协议往返（88% 盘利用率）；CPU/网络均非瓶颈。
4. 注意：三节点并行写须用**独立前缀**避免相同 key 覆盖（首轮同前缀测试出现 file does not exist）。
