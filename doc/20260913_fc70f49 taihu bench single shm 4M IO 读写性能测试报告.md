1. 用 **taihu bench single**（单机直通压测，rpcclient 直连 taihu-server，不查 TiKV）做 4 MiB IO 读写测试，`-transport shm`（同机共享内存 IPC，shmipc）。

3. 验证 shm 单帧传输的零拷贝命中（take/copy 帧统计）。

## 3. 测试方法

```bash

/tmp/taihu server --listen 100.71.128.13 --db /tmp/tdbsingle --dev /dev/nvme3n1 \
  --server-name TAIHU-SINGLE --pd 100.71.128.11:2379

# 写（2 线程，80 GiB）
/tmp/taihu bench single --mode write --transport shm --shm /dev/TAIHU-SINGLE \
  --size 4194304 --count 20000 --threads 2 --report-interval 5s --latency

# 读（32 线程，同批 key）
```

## 6. 结论

1. **shm 写几乎无开销（-0.96%）**：2 线程下 shmipc 传输开销可忽略，带宽仍打满磁盘写上限（磁盘 2539 MiB/s），p50 与裸盘完全一致（3.08ms）。
2. **shm 读 32 线程损耗 -7.3%**：带宽 6254.6 vs 6748.5 MiB/s，磁盘同样回落（6231.9 vs 6666.7），说明**损耗不在磁盘而在端到端链路**——32 线程高并发下共享内存单 socket 通道串行化成为次要瓶颈；延迟同步上升（p50 +1.2ms）。
3. **零拷贝验证通过**：读 20000 帧 TakeTry 全命中、copy=0，shm 单帧路径无拷贝；损耗来源是 shm 通道并发能力而非帧拷贝。
4. **瓶颈分层**：写=磁盘；读=shm 单通道并发（次要瓶颈）叠加磁盘接近上限。若追求更高读带宽，可改用 `-transport rpc`（多地址多连接并行）或 `bench cluster` 多实例汇聚，预期可追平裸盘基线。

## 7. 修订：1GiB 共享内存池配置复测（2026-09-13）

### 7.1 背景与配置变更

排查 32 线程读损耗时发现：共享内存大切片池容量按 `BufferCap × 大档百分比 / 4MiB` 计算，原配置（256MB × 70% ≈ 43 个 4MiB 切片）在 64+ 并发读时 Reserve 失败 → fallback 至 unix socket 拷贝 → **熔断崩溃**（`session is unhealthy`）。修复为池容量调整（[internal/transport/shmipc_client.go](file:///d:/workspace/nefs/taihu/internal/transport/shmipc_client.go#L31-L36)）：

| 配置项 | 旧值 | 新值 |
|--------|------|------|
| `shmBufferCap` | 256MB | **1GiB** |
| 大切片档占比（4MiB+8KB） | 70% | **95%** |
| 4MiB 切片数 | ≈43 | ≈240 |

- 1GiB ≈ 240 个 4MiB 切片 ≥ 128 并发在途需求，fallback 通道不再触发（复测 128t 0 fallback，带宽从崩溃 → 6474 MiB/s，见 §7.3）。
- memfd 稀疏分配，物理内存按实际写入页计，1GiB 虚拟映射基本无成本。

### 7.2 复测结果（新配置，同 4MiB / count=20000 / shm single）

| 模式 | 线程 | ops/s | 带宽 MiB/s | p50 | p90 | p99 | 磁盘稳态 | 磁盘峰值 |
|------|------|-------|-----------|-----|-----|-----|---------|---------|
| 写 | 2 | 633.19 | **2532.76** | 3.08ms | 3.18ms | 4.43ms | 2530.5 | 2579.6 |
| 读 | 32 | 1527.16 | **6108.62** | 20.10ms | 24.61ms | **64.17ms** | 6093.9 | 6366.4 |

- 读复测（同参数二次）：1532.39 ops/s / 6129.55 MiB/s，p50=20.11 / p90=25.08 / p99=66.76ms——带宽与 p99 均稳定，非单次抖动。
- 零拷贝维持：读 rx 20000 帧全 TakeTry（take=20000 / copy=0）；server 日志 fallback 计数 0。

### 7.3 与旧配置对比

| 指标 | 旧配置（256MB/70%） | 新配置（1GiB/95%） | 变化 |
|------|--------------------|-------------------|------|
| 写 2t 带宽 | 2541.14 MiB/s | 2532.76 MiB/s | **-0.33%**（持平） |
| 写 p50/p99 | 3.08/4.63 ms | 3.08/4.43 ms | 持平 |
| 读 32t 带宽 | 6254.58 MiB/s | 6108.62 MiB/s | **-2.33%** |
| 读 p50/p90/p99 | 19.98/24.53/29.03 ms | 20.10/24.61/64.17 ms | p50/p90 持平，**p99 +35ms** |
| 读磁盘稳态 | 6231.9 MiB/s | 6093.9 MiB/s | -2.2%（与应用同步回落） |

### 7.4 分析与结论

1. **池容量按 "并发流 × 4MiB" 估算，容量不足即熔断**：这是 64t/128t 崩溃的根因，非代码逻辑错误；调 `shmBufferCap` 只是抬高阈值，客户端若长期持有不 release 仍会耗尽崩溃，因此上层必须"用完即 release"（EFS 读路径已统一 release 回调归还）。
2. **写不受影响**（-0.33%）：2 线程并发低，池容量与传输均无压力，磁盘仍打满。
3. **读 32t 略降 -2.3%，磁盘同步回落**：新配置下 95% 容量归大切片档，控制帧/小切片池占比收窄，32 线程高并发下小切片分配竞争略增；应用带宽与磁盘稳态同步下降，说明磁盘侧调度节奏略微变缓，磁盘仍未打满（6366 vs 裸盘峰值 6666）。
4. **读 p99 劣化（29→64ms）待关注**：两次复测稳定，非抖动。可能与大切片池分布/分配竞争相关，需要 pprof 采样定位（服务端或客户端侧）；暂不影响 p50/p90 与均值带宽。
5. **128t 高并发场景新配置价值明确**：64t 由崩溃 → 6459 MiB/s，128t 稳定 6474 MiB/s（磁盘峰值 6735 ≈ 裸盘）——池容量修复消除了熔断，只余 32t 小切片竞争的 ~2% 代价，属可接受的工程取舍。若 32t 是主场景且在意 p99，可尝试把大切片档回调至 ~90% 观察。

### 7.5 增大线程读拓展测试（新配置，4MiB / count=20000 / shm single）

验证读带宽能否通过增加线程达到 6.5 GiB/s（6656 MiB/s）。复用 §7.2 已写入的 80GiB 数据，逐档测读：

| 线程 | 应用带宽 MiB/s | ops/s | p50 | p90 | p99 | 磁盘稳态 | 磁盘峰值 | 稳态样本 |
|------|---------------|-------|-----|-----|-----|---------|---------|---------|
| 32 | 6108.62 | 1527.16 | 20.10 | 24.61 | 64.17 | 6093.9 | 6366.4 | 13 |
| 64 | **6435.16** | 1608.79 | 38.09 | 42.55 | 109.99 | 6444.5 | **6735.4** | 36 |
| 128 | **6456.89** | 1614.22 | 76.51 | 80.91 | 183.51 | 6437.0 | **6715.1** | 12 |
| 256 | 熔断（见下） | - | - | - | - | - | - | - |

- **256t 触发 fallback → 熔断**：池容量 1GiB ≈ 240 个大切片 < 256 并发在途需求，`Reserve` 失败降级 unix socket 拷贝，`openCircuitBreaker` 熔断连接 → `run error: session is unhealthy`。排队中的 seqID 243~257 多帧同时 fallback 印证"并发在途超出池容量"。

### 7.6 增大线程测试结论

1. **64t 起带宽锁在 ~6.4 GiB/s 且磁盘打满**：64t（6435）与 128t（6457）仅差 0.3%，磁盘峰值 6735/6715 MiB/s 等于 storage 裸盘峰值（~6748）——**瓶颈已完全移到磁盘硬件上限**。
2. **6.5 GiB/s 目标评估**：处于"磁盘稳态均值 ~6440 / 峰值 ~6735"区间内。裸盘 32t 读均值本身为 6586.6 MiB/s（见 storage 报告），其稳态均值也仅 ~6.5 GiB/s 边缘；当前 single shm 128t 稳态 6437，距裸盘稳态 6586 差 ~2.3%（链路损耗，含小切片竞争），**峰值可达 6.5 但稳态均值在 6.44~6.46 GiB/s**。
3. **增大线程不再提升稳态均值**：64t→128t 仅 +0.3%（接近磁盘稳态上限），单纯加线程到 256 无法缓解；且因池容量（240 切片）< 256 在途直接在 256t 熔断，需把 `shmBufferCap` 提到 2GiB（覆盖 256 在途）才能继续。
4. **若要进一步逼近 6.5 GiB/s 稳态均值**：改 2GiB 池 + 256t，或调整小切片占比（95%→90%）削减 32t 竞争损耗，预期可把稳态从 6437 提到接近裸盘 6586。

## 8. 修订：服务端读路径多块并行 DMA（多帧流水线）实现与验证（2026-09-13）

### 8.1 背景

在 §7 基础上进一步定位读路径损耗（应用 16.9 GiB/s vs 磁盘峰值 19.5 GiB/s），将服务端 `handleShmGet` 对"单个大对象（>4MiB）的多 4MiB chunk"从**串行 DMA** 改造为**单请求内多块并行直读**（多帧流水线），目标提升磁盘队列深度、追平裸盘单盘 6.67 GiB/s。

### 8.2 实现（本次代码改动）

只改 transport 层，零改动第三方 shmipc-go 与 storage 层：

- `internal/transport/protocol.go`：新增 `shmMaxParallel`（单批并行在途切片上限）。
- `internal/transport/shmipc_server.go`：新增 `getSlot` 结构 + `shmWriteDataFramesDirect` 批量直读函数，三阶段：
  - **Phase A（串行按序 Reserve）**：主 goroutine 逐块 `Reserve(shmDataPad+dlen)` + 写占位 opGetErr 帧头，链序==块序（保序地基，严禁并发 Reserve）。
  - **Phase B（并行 DMA）**：每块 goroutine `storage.ReadAtInto` 直读各自切片数据区（无锁，已确认并发安全），成功后按 `pos+n>=end||EOF` 判 final 写帧头，失败写 opGetErr。
  - **Phase C（单次 Flush）**：整链一次 Flush；客户端 `shmReadFrame` 按 `[4B len]` 定界逐帧解析，天然保序。
  - 契约：无论成败，批内全部已 Reserve 槽填成合法帧并整批 Flush，保证流可复用、不污染下一请求。
- `handleShmGet` 改造：off 4K 对齐时收集连续整 4MiB 块走批量直读；非对齐 off 或不足整块的尾块走原串行回退路径。

### 8.3 首次验证（shmMaxParallel=16）与池耗尽问题

**16 = 失败**：96 线程并发流叠加 × 单请求 16 块在途 > 共享内存池大切片档（1GiB@95% ≈ 240），`allocShmBuffer` 失败自动降级 heap → `inFallbackState` → 触发 uds fallback 与客户端 session 熔断（`unhealthy`），16MiB 读失败。将 `shmMaxParallel` 降为 **2** 后 0 fallback，读取恢复正常。

### 8.4 大数据量稳态验证（shmMaxParallel=2，16MiB×4000 = 64GiB，3 盘汇聚）

| 模式 | 线程 | 应用带宽 MiB/s | p50/p90/p99 | fallback |
|------|------|---------------|-------------|----------|
| 写 | 16 | **6875.15** | 32.3 / 70.5 / 87.6ms | - |
| 读 | 96 | **16249.79** | 77.0 / 143.9 / 437.9ms | **0**×3 |

磁盘稳态（iostat，iostat-bw 规则）：

| 盘 | 写 avg/peak MiB/s | 读 avg/peak MiB/s |
|----|-------------------|-------------------|
| nvme1n1 | 2261 / 2383 | 5240 / 6708 |
| nvme2n1 | 2292 / 2535 | 5332 / 6323 |
| nvme3n1 | 2326 / 2570 | 5428 / 6446 |
| 聚合 | **6879** / - | **16000** / **19477** |

帧统计验证：写 dataFrames=16000（4000 对象 × 4 块）；读 dataFrames=16000 dataBytes=67108864000（= 16MiB×4000，字节精确），`take=0 copy=16000`（多帧响应走客户端既有"对齐汇入"路径，属既定行为）。

### 8.5 结论

1. **多块并行 DMA 正确性通过**：16MiB 对象（4 块）帧序/字节数完全正确，3 server 全程 0 fallback、0 崩溃，流可复用。
2. **性能与单块串行基线持平**：读 16250 vs 单块 4MiB 基线 16879 = **96.3%**，差异来自多帧汇入拷贝（copy=16000）而非并行损耗；写 6875 与磁盘聚合 6879 吻合（+0.06%），写瓶颈在磁盘。
3. **未再现"追平裸盘"的提升**：`shmMaxParallel=2` 被共享内存池强约束压得保守，单请求并行度有限；且 96 线程多流本已并行，读取瓶颈实际在**客户端消费 + 共享内存传输**，而非服务端单请求内串行 DMA。读磁盘峰值 19477 > 应用 16250，磁盘有富余，读吞吐仍受链路限制。
4. **本改造的价值**：单请求内多块并行避免了大对象串行 DMA 的队列深度不足风险，**正确性收益明确、性能无回退**；要继续追平裸盘需从客户端多连接（rpc）+ 池扩容（2GiB）方向突破，单请求内并行不是主瓶颈。

## 9. 修订：共享内存池扩容 2GiB + shmMaxParallel=8 复测（2026-09-13）

### 9.1 背景

§8.5 结论 3/4 指出：`shmMaxParallel=2` 被 1GiB 共享内存池（大切片档 ≈240 个 4MiB）约束得保守，读瓶颈在"客户端消费 + 共享内存传输"而非服务端单请求内串行 DMA，追平裸盘需**池扩容**方向。本修订按此落地并复测：

| 配置 | 改造前（§8.4） | 改造后（本节） |
|------|----------------|----------------|
| `shmBufferCap`（每会话共享内存容量） | 1GiB（≈240 个 4MiB 大切片） | **2GiB（≈480 个 4MiB 大切片）** |
| `shmMaxParallel`（单请求并行在途切片上限） | 2 | **8** |

负载安全后：16MiB 对象每请求 4 块 ≤ 8，96 并发流最坏在途 96×4=384 < 480，安全不触发池耗尽 fallback。

### 9.2 复测（16MiB×4000 = 64GiB/盘，3 server 汇聚，对齐 §8.4 结构）

服务端 3 实例：TAIHU-P1（nvme1n1，rpc=50002）、TAIHU-P2（nvme2n1，rpc=50000）、TAIHU-P3（nvme3n1，rpc=50004）；每盘独立 2GiB 池。写 2 线程/盘灌数据 → 3 进程并行读（各 32 线程 = 96 线程总数），每进程读各自 `/dev/TAIHU-P*` shm socket。

**应用带宽（两轮结果一致，可重复性良好）**：

| 进程 | 线程 | 带宽 MiB/s（轮 1） | 带宽 MiB/s（轮 2） | p50/p90/p99（轮 2） |
|------|------|-------------------|-------------------|---------------------|
| P1 | 32 | 6087.32 | 6111.88 | 75.7 / 83.1 / 305.5ms |

### 9.3 结论

1. **带宽显著提升**：3 盘汇聚读 16250 → **18326 MiB/s（+12.8%）**，稳定复现两轮（18326/18364，Δ<0.3%）。证实 §8.5 判断——此前读瓶颈确在客户端消费 + 共享内存池紧张（240 切片逼近 96×4=384 在途需求，Reserve 竞争串行化），池扩容直接释放并发度。
2. **应用逼近磁盘**：应用 18364 vs 磁盘聚合稳态 avg 18980 = **96.5%**（改造前 §8.4 应用/磁盘 = 101.6% 时瓶颈实为池容量而非磁盘；本次磁盘稳态也随负载抬升到 18980/20290，磁盘仍有 ~3.5% 富余，剩余差额来自多帧汇入拷贝 + 测试 ramp）。
3. **0 fallback、0 崩溃**：2GiB 池（480 切片 ≥ 384 在途最坏）全程无 uds fallback 与 session 熔断，流可复用，稳定性达标。
4. **单请求并行上限仍保守**：96 流 × 4 块 = 384 已贴近 480 池上限，若进一步推高并发（>120 流）或对象 ≥32MiB（单请求 ≥8 块 ×96 流 ≥768 在途）会再次触发池耗尽，届时需再扩容 BufferCap 或收紧 shmMaxParallel。
5. **写容量不变**：写瓶颈在磁盘（§8.4 写 6875 ≈ 磁盘聚合 6879），池扩容与并行系数不影响写带宽，无需复测。
