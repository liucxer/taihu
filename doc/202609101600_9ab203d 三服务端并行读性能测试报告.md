# 9ab203d 三服务端并行读性能测试报告

> 对应提交：`9ab203d`（fix: bufpool alignedBuffer 用三索引切片 cap==n，修复 Get/Put 桶错配导致零复用）
> 测试范围：**3 服务端 × 3 客户端并行 RPC 读**（各 32T/16C/4M，loopback，客户端与服务端同机）

## 1. 测试目标

验证 bufpool 桶错配修复（9193 提交链：freelist 常驻 + alignedBuffer cap==n）后，3 实例并行读的聚合能力与物理机资源表现，量化修复收益（修复前 2a0a2ec 聚合 9.0 GB/s、服务端 memclr ~18%）。

## 3. 测试方法

taihu-rpc-bench 参数：`-mode read -size 4194304 -threads 32 -conns 16 -count 20000 -keys-prefix <p> -latency -report-interval 2s -cpuprofile <clientN.cpu>`。

- 三服务端同时启动，三客户端**并行**读各自服务端，23s 稳态（80GB/客户端）。
- 采集：`mpstat -P ALL 1`、`iostat -d nvme1n1 nvme2n1 nvme3n1 1`、`/proc/net/dev` loopback 逐秒差分。
- pprof：三客户端 `-cpuprofile`（全程）；三服务端经各自 pprof 端口抓 `/debug/pprof/profile?seconds=10`。
- CPU 口径：实占 = usr+sys（iowait 计入可用）。
- 版本校验：部署后 `md5sum` 确认 server 二进制 2757b166；测试前 `ss -ltnp` 确认监听 PID 为新进程（规避 comm 截断导致误连旧二进制的坑）。

## 5. 资源占用

### 5.1 物理机 CPU（mpstat -P ALL，24-25 个逐秒样本）

- **整机均值 busy 82.4%**（min 44.0 / max 85.1）：usr 26.4 / **sys 39.4** / iowait 12.4 / idle 17.6；实占 usr+sys = **65.9%**。
- **逐核分布：96/96 核全部 busy > 75%**（全员参与）。TOP 忙核（94/72/62/64/54/66/58/52）busy 84-86%，分解 **usr 19-22% / sys 43-45% / iowait 12-18%**（syscall 密集）。
- 结论：整机接近饱和，**syscall 处理是主要占用**，iowait 12.4%（盘等待）为次。

### 5.2 磁盘（iostat 实测，三盘独立稳态）

| 盘 | 读均值 | 峰值 | tps |
| --- | --- | --- | --- |

| nvme2n1 | 3333.4 | 4128.4 | 26670 |
| nvme3n1 | 3331.8 | 4391.0 | 26663 |
| **聚合** | **~9.96 GB/s** | ~12.9 GB/s | ~79700 |

每盘稳态 3.3 GB/s，相对单盘读潜力（~5.9-6.4 GB/s）仍偏低——盘未被用满，被上游 CPU/网络压住。

### 5.3 网络（loopback /proc/net/dev 差分实测）

- **RX_AVG=10446.4 / TX_AVG=10446.4 MiB/s（PEAK 12394.3）**，双向对称，与应用层聚合一致。

## 6. 进程 CPU 与 pprof 热点

### 进程 CPU（pprof Duration 采样估核）
- 客户端 ×3：各 **~1338%（13.4 核）**；服务端 ×3：各 **~511%（5.1 核）**；合计 ~55.5 核，与物理机实占（65.9%×96≈63 核）量级吻合。

### 客户端（taihu-rpc-bench，同构 ×3）

**服务端用户态开销已清零**（无 memmove/makeslice/memclr 热点），读路径为纯 syscall 形态。

## 7. 修复收益对比（相对 2a0a2ec）

| 指标 | 2a0a2ec（修复前） | 9ab203d（本轮） |
| --- | --- | --- |
| 聚合带宽 | 9.0 GB/s | **10.4 GB/s（+16%）** |
| 每客户端带宽 | 3069-3078 MiB/s | 3449-3510 MiB/s |
| 磁盘/盘 | ~2956 MiB/s | 3297-3333 MiB/s |
| loopback | 9340 MiB/s | 10446 MiB/s |
| 服务端 memclr | ~18% | **0.02%（归零）** |
| 服务端 syscall | 73.2% | 92.3% |

根因与修复：bufpool `alignedBuffer` 返回 `backing[start:start+n]`，cap=(n+4096)-start > n，Put 按 cap 归一化后落入高一档桶、Get 永远取不到 → 复用率 0、每 op 冷分配+清零（memclr ~18%）。三索引切片 `backing[start:start+n:start+n]`（cap==n）修复后复用率 0→0.988，冷分配仅剩冷启动填充。

## 8. 瓶颈分析与结论

1. **达标**：聚合 **10.4 GB/s**，较修复前 +16%；服务端读路径达到"纯 syscall"形态（92.3%），用户态分配/拷贝/清零全部消除。
2. **当前瓶颈**：整机 CPU syscall 处理（busy 82.4%、sys 39.4%、96/96 核 >75% busy）与 loopback 吞吐（AVG 10.4 / PEAK 12.4 GB/s）；磁盘每盘 3.3 GB/s 相对潜力 6.4 仅用一半——盘在等 CPU 持续推进。
3. **客户端剩余开销**：memmove 43%（收流聚合，需连续返回缓冲，属必要拷贝）+ memclr 12.5%（返回缓冲清零）。后续优化方向：客户端 Get 返回缓冲池化复用并仅首末 4K 补零，或 gRPC 收侧深改造。
4. **线性度**：三实例聚合 10.4 vs 单实例 6.39×3=19.2 的理论值，线性度仅 54%——受整机 CPU/lo 共享约束；若需更高聚合，考虑跨机部署绕开同机 syscall/lo 共享。
