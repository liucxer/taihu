# taihu 集群支持设计文档（缓存场景）

> 版本：v1（初稿）
> 日期：2026-09-11
> 关联：kvcache 集群模式（TiKV 注册+心跳+索引路由）参考，见 `../kvcache/main.go`、`../kvcache/client/*`
> 现状：taihu 为单机版（`taihu-server` 单 Storage 实例 + `rpcclient` 直连），本次设计面向多节点水平扩展

## 1. 背景与目标

taihu 当前为单机架构：

```
应用 → rpcclient.Dial(addr) → taihu-server（netpoll RPC）→ Storage（O_DIRECT + libaio 裸盘 + pebble 元数据）
```

每台物理机部署独立实例，互不感知；`taihu-bench` 跨节点压测/三盘聚合均为手工编排，无统一发现与路由。

本设计目标：在不改动数据面（4MiB 帧、final 位、TakeTry 零拷贝、bufpool）的前提下，为 taihu 增加**多节点集群支持**：实例注册发现、key 定位路由、本地优先写入、回源兜底。

## 2. 需求约束

| 约束 | 说明 |
|------|------|
| 对象大小 | 0 ~ 4MiB 混合（最大 4MiB，存在小块），路由粒度始终为 key |
| 写入偏好 | **优先写入本地盘**（客户端与其数据实例同机/同节点时优先本地，避免跨机网络） |
| 副本 | **单副本**，不做数据复制 |
| 语义 | **缓存场景**：数据可丢，丢失后由上层应用从远端源回拉重建 |
| 性能 | 不破坏现有数据面优化；集群定位开销不得进入每次 IO 的同步关键路径 |

由约束可推导：**数据与索引均可"尽力而为"** —— 丢了就回源重拉，这是缓存场景与持久存储的本质区别，也是本方案与 kvcache 原案最大的不同点。

## 3. 总体设计：首写本地 + 索引锚定（异步尽力） + 回源兜底

```
┌─────────────────────────────────────────────────────────────┐
│                         应用（SDK）                           │
│  ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌─────────────────┐ │
│  │Registry  │ │ Picker   │ │ IndexMgr │ │ RouteCache(LRU) │ │
│  │ 发现/心跳│ │ 本地优先  │ │ 尽力索引 │ │  key→instance   │ │
│  └──────────┘ └──────────┘ └──────────┘ └─────────────────┘ │
│        │              │            │                        │
│        ▼              ▼            ▼                        │
│  ┌──────────────────────────────────────────┐               │
│  │ 数据面（现有 transport.Conn / 本地 Storage）│  ← 零拷贝不动 │
│  └──────────────────────────────────────────┘               │
└──────────────┬──────────────────────────────┬───────────────┘
               │                              │
       ┌───────▼────────┐            ┌────────▼───────┐
       │   TiKV 注册中心  │            │  远端源（回源）  │
       │ /taihu/instances│            │  SourceGetter  │
       │ /taihu/index    │            └────────────────┘
       └────────────────┘
```

三条核心原则：

1. **首写本地，位置锚定**：key 首次写入时选本地盘实例，此后该 key 的覆盖写跟随原归属实例 → 位置稳定、无随机漂移；
2. **索引异步尽力**：数据落盘即返回，索引后台异步写；索引丢失/不可用只影响"远端命中率"，不影响正确性（读 miss 回源）；
3. **回源兜底**：任何 miss（本地 miss、索引 miss、实例离线）最终都可回源重建，系统功能永远可用。

## 4. 服务端改动（taihu-server）

沿用 kvcache 骨架（`kvcache/main.go`），新增 3 个 flag 与注册/心跳/注销逻辑：

```bash
taihu-server -addr :50051 -db /tmp/tdb -dev /dev/nvme1n1 \
  --name a1 --node nodeA --tikv-pd 100.71.128.12:2379
```

| 改动点 | 说明 |
|--------|------|
| `--name / --node / --tikv-pd` | 必填（集群模式）；缺省走现有单机直连模式，向后兼容 |
| 注册 | 启动时 `Put /taihu/instances/{name}`，value 为 JSON：`{name, node, addr, capacity, available, used, start_time}` |
| 心跳 | goroutine 每 1s 重写同一 key，刷新容量（`statfs`）与活跃时间 |
| 注销 | SIGTERM/SIGINT 时 `Delete` 该 key（复用现有 `GracefulStop` 信号处理） |
| 容量上报 | `Storage` 增加 `GetDiskCapacity()`（statfs `Bavail`），异常时上报 0 不阻断注册 |

> 与 kvcache 差异：kvcache 用 `start_time` 充当心跳时间戳，语义错位。本设计**单独维护 `last_heartbeat` 字段**，SDK 以 `last_heartbeat` 判离线，`start_time` 仅作注册时间。

## 5. 客户端改动（rpcclient → 集群版）

新增独立包（建议 `pkg/rpccluster/`），保留现有 `Dial/DialPool` 直连模式不动。

### 5.1 实例发现（Registry）

- 启动时与定时器（默认 `refreshInterval=2s`）周期 `Scan /taihu/instances/` 前缀（limit 1000），解析 JSON；
- 以 `last_heartbeat` 与 `heartbeatTimeout`（默认 5s）比对判离线，整体替换原子快照（`atomic.Value`）；
- 提供 `LocalInstances()`（`node` 匹配本机）与 `RemoteInstances()` 分组，`GetActiveInstances()` 零拷贝快照。

### 5.2 选择器（Picker）

- **本地优先**：`LocalInstances` 中取健康实例（`used/capacity < usageThreshold`，默认 0.8）随机 → 无则 `RemoteInstances` 随机 → 兜底全量；
- 与 kvcache `picker.go` 一致，仅保留本地优先语义。

### 5.3 尽力索引（IndexManager）

- key 级索引 `key → instance`，存 TiKV `/taihu/index/{key}`；
- **写入异步**：数据面成功后通过批量通道攒批（对齐 taihu 写路径高吞吐，参考 kvcache `batch_writer` + `BatchPut`），失败仅记日志；
- 读侧 `Get`/`BatchGet` 支持 `WarmRouteCache` 批量预热。

### 5.4 路由缓存（RouteCache）

- 16 分片 FNV 哈希 LRU（复用 kvcache `route_cache.go` 设计），`key → instance`；
- 支持 `DeleteByInstance(instance)`：实例离线/注销时批量失效，避免读打到死实例。

### 5.5 回源接口（SourceGetter）

```go
// SourceGetter 由上层应用实现：从远端源拉取 key 的 value（数据丢失后重建缓存）。
type SourceGetter func(ctx context.Context, key string) ([]byte, error)
```

集群客户端构造时注入；命中回源路径时自动走"写路径入缓存"再返回。

## 6. 数据路由流程

### 6.1 写（Set）

```
1. key 归一化（沿用现有 key 规则，如 <prefix>/<seq>）
2. 查 RouteCache → 命中归属实例 → 步骤 5
3. 查 TiKV 索引（尽力，超时/失败跳过）→ 命中归属实例 → 步骤 5
4. 无归属 → Picker 本地优先选实例
5. 数据面写入（本地实例可走直连 Storage 零网络；远端走 transport.Conn）
6. 异步写索引 + 更新 RouteCache
7. 返回
```

### 6.2 读（Get）

```
1. 本地实例直查（无索引、零网络）→ 命中返回
2. miss → RouteCache → TiKV 索引定位远端实例 → 数据面读 → 命中返回
3. 全 miss 或实例离线 → SourceGetter 回源 → 按写路径入缓存 → 返回
```

### 6.3 覆盖写锚定

- key 已有归属 → 覆盖写原实例（位置稳定）；
- 原归属实例离线 → 视为新 key，本地优先重新锚定 → 旧实例数据成为孤儿，由 taihu 已有的 **segment 级 GC（commit 6c5297e）** 回收，无需迁移逻辑。

## 7. 故障与降级

| 场景 | 行为 | 影响 |
|------|------|------|
| 实例崩溃 | 5s 无心跳 → SDK 标记离线，RouteCache `DeleteByInstance` 失效 | 其 key 读 miss → 回源重建；写走重新锚定 |
| TiKV 不可用 | 注册/心跳失败（实例照常服务）；SDK scan 失败用旧快照；索引读写失败跳过 | 写仍成功（本地锚定）；读退化"本地 + 回源"，**功能不中断** |
| 网络分区 | 实例被 SDK 判离线；恢复后心跳续上重新被发现 | 期间回源兜底 |
| 索引丢失 | 异步写失败/被清理 | 读 miss 回源，重新锚定，自愈 |
| 磁盘满 | 容量上报 used≈capacity，Picker 跳过该实例 | 写落到其他健康实例 |

## 8. 与现有零拷贝读路径的接合

- **数据面零改动**：`transport.Conn` 的 4MiB 帧、final 位、`TakeTry` 零拷贝移交、`bufpool` 完全不动；
- 集群层只新增"定位"：最终仍落到 `transport.Conn`（远端）或 `pkg/taihu.Storage`（本地直连）；
- **本地实例直连是"优先写本地盘"的最佳形态**：客户端进程与应用同机时直接 `NewStorage` 本地落盘，数据面零网络、零拷贝，跨机才走 netpoll 链路；
- 定位层（Registry/Picker/Index/RouteCache）全部在数据面之外，不进入热路径同步等待（索引异步化保证）。

## 9. 小对象存储（与集群解耦）

对象大小混合（0 ~ 4MiB），路由粒度不变，但存储层需区分路径：

| 对象大小 | 存储路径 | 依据 |
|----------|----------|------|
| ≤ 阈值（建议 128KiB） | pebble / metastore（已有） | 避免裸盘 segment 空间碎片，小块适合 LSM 元数据存储 |
| > 阈值 | 裸盘 segment（O_DIRECT + libaio，现有） | 大块走既有高性能路径 |

阈值由存储层配置，客户端不感知；设计文档不展开（另行存储层设计）。

## 10. 配置与接口

### taihu-server 新增 flag

```text
--name string        实例名（必填，集群模式）
--node string        物理节点标识（必填，集群模式）
--tikv-pd string     TiKV PD 地址，逗号分隔（必填，集群模式）
--heartbeat-interval 默认 1s
```

### 集群客户端

```go
type ClusterConfig struct {
    PDAddrs          []string      // TiKV PD
    Node             string        // 本机节点标识（本地优先判断）
    RefreshInterval  time.Duration // 默认 2s
    HeartbeatTimeout time.Duration // 默认 5s
    UsageThreshold   float64       // 默认 0.8
    SourceGetter     SourceGetter  // 回源回调（缓存场景必填）
}

// 返回与 rpcclient.Storage / pkg/taihu.Storage 同签名的 *Storage，
// 调用方可无感切换本地/直连/集群。
func NewCluster(ctx context.Context, cfg ClusterConfig) (*Storage, error)
```

### 依赖引入

- 新增 `github.com/tikv/client-go/v2`（rawkv，同 kvcache）；
- 若无现成 TiKV 环境，可替换为 etcd v3（注册/索引语义一致）或 memberlist（纯 gossip 发现，需自实现索引），接口层保持不变。

## 11. 实施步骤

| 步骤 | 内容 | 验证 |
|------|------|------|
| 1 | server：`--name/--node/--tikv-pd` + 注册/心跳/注销/容量上报（含 `last_heartbeat` 字段） | 多实例注册，`tikv scan /taihu/instances/` 可见，kill 后 5s 消失 |
| 2 | client：Registry 发现 + Picker 本地优先 | 单节点多实例随机分布，节点内优先 |
| 3 | client：IndexManager（异步批量）+ RouteCache + 写锚定 | 同 key 重复写位置稳定；覆盖写跟随原实例 |
| 4 | 读路径 + 回源兜底 + 降级（TiKV kill 测试） | 本地命中、远端命中、回源三种路径正确；TiKV 挂后读写不中断 |
| 5 | 小对象存储路径（阈值路由） | 小块走 pebble、大块走裸盘，混合压测无回归 |
| 6 | 集群压测：多节点读写聚合带宽/延迟 + 故障注入报告 | 对比单机基线，量化定位层开销 |

## 12. 未决问题

1. **TiKV 环境**：128.12/128.13 等节点是否有可用 TiKV/PD 部署？无则需先部署或改 etcd/memberlist；
2. **本地实例直连判定**：SDK 与实例同机时，走本地 Storage 还是仍走 netpoll 回环（loopback 已有 16.5 GiB/s 能力，直连可省协议开销，需实测对比）；
3. **索引清理**：孤儿/过期索引（实例重建后 key 重新锚定）是否定期清理 `/taihu/index` 前缀，避免索引膨胀；
4. **回源限流与并发**：回源路径需防雪崩（大量 miss 同时回源），是否需要熔断/并发上限；
5. **容量均衡**：本地优先 + 随机可能导致节点间数据倾斜，缓存场景可接受（淘汰/回源兜底），是否补充周期性 rebalance 待定。
