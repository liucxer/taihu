# 2f96c69 读写性能测试报告

> 对应提交：`2f96c69`（fix: RawFrame 改为单缓冲持有，wire 多缓冲 bufpool 复用合并；含 `de625b8` RawFrame 延迟物化 + GetRaw 帧式零拷贝 API）
> 测试时间：2026-09-10 07:29 ~ 07:31

## 1. 测试目标

验证**客户端读路径二次减拷贝优化**（RawFrame 延迟物化 + GetRaw 帧式 API）后的端到端读写性能：

- 应用层带宽（写 / 传统读 / GetRaw 帧式读）与延迟（p50/p90/p99）；
- 物理磁盘带宽（iostat 实测）、网络带宽（lo 回环实测）、物理机 CPU（整机 + 逐核）；
- 客户端 / 服务端双端 pprof，**定位到消耗 CPU 的具体代码行**。

## 2. 测试环境

| 项目 | 配置 |
|------|------|
| 服务器 | 100.71.128.12（client 与 server 同机，网络走 lo 回环） |
| 架构 / CPU | aarch64，96 核 |
| 系统 | Linux 4.19.90-2107 bclinux（kernel 4.19.90） |
| 编译产物 | `/tmp/taihu-server.new`、`/tmp/taihu-rpc-bench.new`（go1.24，GOTOOLCHAIN=auto 补齐 go1.25.0） |

## 3. 测试方法

1. 先 `-mode write`（16 线程 × 16 连接）写入 20000 × 4MiB（80 GiB），记录写带宽/延迟；
2. 对同一批 key 分别跑 `-mode read`（传统 `Get` io.Reader 路径）与 `-mode rawread`（`GetRaw` 帧式路径），均 32 线程 × 16 连接；
3. 三轮全程并行采集 `iostat -d /dev/nvme1n1 1`（磁盘）、`mpstat -P ALL 1`（CPU 逐核）、`/proc/net/dev` 前后基线（lo 回环带宽）；
4. 双端 pprof：client 用 bench `-cpuprofile`（全量），server 用 `-pprof :6060` 抓 15~20s 窗口；
5. pprof 用 `go tool pprof -top / -list`（匹配 arm64 二进制）定位到具体代码行。

## 4. 测试结果

### 4.1 应用层带宽与延迟

| 模式 | 参数 | 吞吐 | 带宽 | p50 | p90 | p99 |
|------|------|------|------|-----|-----|-----|
| 写 | 16 线程 × 16 连接 | 640.35 ops/s | **2561.39 MiB/s（2.50 GiB/s）** | 24.71ms | 25.79ms | 30.02ms |
| 读 read | 32 线程 × 16 连接 | 1539.32 ops/s | **6157.29 MiB/s（6.01 GiB/s）** | 20.56ms | 23.91ms | 27.83ms |
| 读 rawread | 32 线程 × 16 连接 | 1559.50 ops/s | **6238.00 MiB/s（6.09 GiB/s）** | 20.29ms | 23.63ms | 27.16ms |

- 写 2.50 GiB/s 贴齐单盘写极限（~2.5 GiB/s），**单进程 DialPool 16 连接即打满**；
- 读 6.01~6.09 GiB/s 达单盘读极限（~6.6 GiB/s）的 **91~92%**（优化前 16 客户端读仅 5.36 GiB/s、80%）；
- rawread 较 read 略高 80 MiB/s（+1.3%），延迟一致——客户端读路径拷贝已基本消除，余量在磁盘访问模式。

## 5. 资源占用

### 5.1 物理磁盘带宽（iostat 实测，稳态帧）

| 写 | 2490.2 MiB/s | 2584.6 MiB/s | ~2.5 GiB/s | **100% 饱和** |
| 读 read | 5710.0 MiB/s | 6229.4 MiB/s | ~6.6 GiB/s | ~87% |
| 读 rawread | 5714.4 MiB/s | 6386.9 MiB/s | ~6.6 GiB/s | ~88% |

> 磁盘带宽为 iostat 实测（非写吞吐推算）。写方向盘 100% 饱和；读方向盘 ~87-88%，接近设备上限，余量来自访问模式（同区并发 IO 排队）。

### 5.2 网络带宽（lo 回环实测，/proc/net/dev 前后差值）

| 场景 | rx / tx | 对应应用层带宽 | 说明 |
|------|---------|----------------|------|
| 写 | 2569 / 2569 MiB/s | 2561 MiB/s | 回环承载全部数据，非瓶颈 |
| 读 read | 6171 / 6171 MiB/s | 6157 MiB/s | 同上 |
| 读 rawread | 6252 / 6252 MiB/s | 6238 MiB/s | 同上 |

> client/server 同机，数据走 lo 回环；回环带宽 > 应用层带宽，网络非瓶颈。跨物理网卡（10G 级）场景未测。

### 5.3 物理机 CPU（mpstat -P ALL，测试窗口均值）

| 场景 | 整机 busy | usr | sys | iowait | idle | 最忙核 |
|------|-----------|-----|-----|--------|------|--------|
| 写 | 11.2% | 3.6% | 2.0% | 5.1% | 88.8% | core=0 ~17.8% |
| 读 read | 43.0% | 14.3% | 9.3% | 17.7% | 57.0% | core=20 74.3%（iowait 46.4%） |
| 读 rawread | 41.7% | 13.2% | 9.3% | 17.6% | 58.3% | core=22 76.8%（iowait 45.1%） |

- 写方向 CPU 极低（busy 11.2%），磁盘先饱和，**CPU 非瓶颈**；
- 读方向 busy ~42%，最忙核 ~75%（其中 iowait 占 ~45%）——**仍有 ~58% 空闲核，CPU 非硬瓶颈**；带宽受磁盘访问模式（iowait 占比高）与每字节 CPU 成本共同限制。

## 6. pprof 热点分析（关键：哪一行代码消耗 CPU）

### 6.1 客户端（rawread，12.92s，总样本 156.22s ≈ 12 核）

**Top（flat）：**

| 函数 | flat | flat% | 说明 |
|------|------|-------|------|
| `internal/runtime/syscall.Syscall6` | 47.79s | 30.59% | socket 读（gRPC 接收） |
| `runtime.memmove` | 32.12s | 20.56% | 数据拷贝 |
| `runtime.memclrNoHeapPointers` | 16.26s | 10.41% | 缓冲清零 |
| 调度/锁/原子合计 | ~12s | ~8% | — |

**消耗 CPU 的具体代码行（应用层）：**

1. **[rpc/codec.go#L95 `data.CopyTo(buf)`](file:///d:/workspace/taihu/rpc/codec.go#L85-L98) — flat 21.53s（13.78%）**
   客户端最大单点开销。`materializeFrame` 的**多缓冲合并**分支：gRPC 1.69 接收端把 1MiB 数据帧拆成多个 16KB wire 缓冲，本函数用 bufpool 缓冲合并（1 次整块 memmove）。这是 `runtime.memmove` 20.56% 的主要来源。
2. **[pkg/rpcclient/storage_rpc.go#L205 `g.stream.RecvMsg(&f)`](file:///d:/workspace/taihu/pkg/rpcclient/storage_rpc.go#L201-L227) — cum 26.69s（17.08%）**
   `getStream.pump` 接收循环，整条 Recv 链（含 codec Unmarshal）归因于此。
3. `RawCodec.Unmarshal` [codec.go#L151](file:///d:/workspace/taihu/rpc/codec.go#L142-L155) — cum 21.70s（13.89%），全部经 `materializeFrame`。

**结论：** 优化后客户端已无每帧 1MiB 的分配+清零（memclr 从优化前 15.13%→10.41%），但 **gRPC wire 多缓冲导致 `materializeFrame` 的合并 memmove（13.78%）成为客户端残留最大拷贝点**；socket 读系统调用（30.59%）次之。

### 6.2 服务端（rawread，20s，总样本 39.04s ≈ 2 核）

**Top（flat）：**

| 函数 | flat | flat% | 说明 |
|------|------|-------|------|
| `internal/runtime/syscall.Syscall6` | 21.41s | 54.84% | socket 写（gRPC 发送） |
| `runtime.memmove` | 11.19s | 28.66% | 发送路径拷贝 |
| `runtime.memclrNoHeapPointers` | 0.88s | **2.25%** | 优化前 19.34% |
| `loopyWriter.processData` | cum 29.10s | 74.54% | gRPC 发送主循环 |

**消耗 CPU 的具体代码行（应用层）：**

1. **[internal/rpcserver/rpcserver.go#L126 `s.storage.ReadAt(...)`](file:///d:/workspace/taihu/internal/rpcserver/rpcserver.go#L120-L134) — flat 2.23s（5.71%）**
   服务端应用层最大单点：O_DIRECT 磁盘读（含读系统调用 + 拷入 bufpool 缓冲）。
2. **[internal/rpcserver/rpcserver.go#L129 `stream.SendMsg(&rpc.RawData{...})`](file:///d:/workspace/taihu/internal/rpcserver/rpcserver.go#L129) — flat 0.23s**
   发送零拷贝（RawCodec.Marshal 直接引用 bufpool 缓冲，不再 proto.Marshal 整块拷贝）。
3. 传输层：`loopyWriter.run` cum 80.2% → `bufWriter.Write` cum 50.1% → `Framer.endWrite` cum 50.2% → `Syscall6`（socket 写 54.84%）；`mem.(*sliceReader).Read` cum 16.65%（gRPC 把 mem.Buffer 拷入 bufWriter 的用户态 memmove，发送路径 2 次 memmove 之一）。

**结论：** 服务端内存操作从优化前的 memmove 48.11% + memclr 19.34%（≈67.5%）降到 **memmove 28.66% + memclr 2.25%（≈30.9%）**；剩余开销主要是 **socket 发送系统调用（54.84%）与 gRPC loopyWriter 的两次用户态 memmove**（gRPC 传输层固有，[lessons learned]）。

## 7. 结论与建议

1. **写方向**：磁盘饱和型。单进程 DialPool 16 连接即达 2.50 GiB/s（盘写极限），CPU busy 仅 11.2%，无优化收益空间。
2. **读方向**：6.09 GiB/s（盘读极限 92%），残余瓶颈为 **① 客户端 `materializeFrame` 多缓冲合并 memmove（13.78%）+ socket 读（30.59%）；② 服务端 gRPC 发送路径 socket 写（54.84%）+ loopyWriter 固有 2 次 memmove（28.66%）**。磁盘 iowait 占比高（~45% 忙核），访问模式（同区并发）亦限制上限。
3. 若继续提升读带宽：
   - 消除客户端 `materializeFrame` 合并拷贝：推动 gRPC 接收端同消息单缓冲化，或改 client GetRaw 直接消费多缓冲切片；
   - 服务端发送减拷贝：loopyWriter/bufWriter 属 gRPC 传输层固有（用户态 2 次 memmove），需自研数据面（方案 A，0 拷贝）或 io_uring + MSG_ZEROCOPY 降低发送 syscall 成本；
   - 磁盘访问模式：增大 IO 粒度 / 分散访问区域 / 降低同区域并发，冲击盘读极限 6.6G 以上。
4. **延迟**：写 p50 24.71ms、读 p50 20.29ms，远优于优化前（写 ~100ms / 读 ~187ms，多进程排队所致）。
