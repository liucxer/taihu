# 2a0a2ec RPC 端到端读性能测试报告

> 对应提交：`2a0a2ec`（perf: device Append 地址对齐零拷贝快路径、读写帧限制 4M、客户端 Get 整对象同步聚合）
> 测试范围：**gRPC 端到端读路径**（taihu-rpc-bench → taihu-server，loopback，客户端与服务端同机）

## 1. 测试目标

在 128.12 上对提交 `2a0a2ec` 的 RPC 端到端读路径做性能定界，回答三个问题：

1. 读 4M 对象能达到的最高带宽，以及接近 **6.5 GB/s** 目标所需的最小线程 × 连接组合；
2. 各配置的延迟与物理机 CPU 实占（iowait 计入可用）；
3. 客户端/服务端读路径的用户态热点（pprof），定位 6.5 目标的差距来源。

配套采集：物理机 CPU、应用层带宽、延迟、loopback 网络带宽、磁盘带宽（均实测）。

## 2. 测试环境

| 项目 | 值 |
| --- | --- |
| 服务器 | 100.71.128.12（客户端 + 服务端同机，loopback 127.0.0.1:50051） |
| CPU | 96 核 ARM aarch64（BCLinux 4.19，mpstat -P ALL 逐秒采样） |
| 内存 | 约 756 GiB |
| 数据设备 | /dev/nvme1n1，1.92 TB NVMe SSD（RP2A21T9RK004LX，O_DIRECT 直读） |
| 元数据 | /tmp/tdb（pebble，tmpfs） |
| 服务端 | /tmp/taihu-server.new，`-db /tmp/tdb -dev /dev/nvme1n1 -addr 0.0.0.0:50051 -pprof :6061` |
| 客户端 | /tmp/taihu-rpc-bench.new，`-addr 127.0.0.1:50051` |
| 对象 | 4 MiB（4194304 B），20000 个（前缀 q1-4m，写测试已灌入，读不重复 key） |
| 通信参数 | chunkSize=4MiB，http2MaxFrameLen=4MiB+16，recv/send 上限 8MiB |

## 3. 测试方法

taihu-rpc-bench 参数：`-mode read -size 4194304 -threads T -conns C -count N -keys-prefix q1-4m -latency -report-interval [2|3]s [-cpuprofile]`。

- **矩阵扫描**：`(threads × conns)` = 8×1、8×2、16×2、16×4、16×8、32×8、32×16、32×32、48×16、48×24、64×16（count=10000），及 24×24、32×16（count=20000 长稳态），收敛读写带宽曲线与最高点。
- **全量样例**：32 线程 × 16 连接（count=20000，80GB，约 12.6s 稳态），采集环回网络 + 客户端/服务端 pprof。
- **采集**：`mpstat -P ALL 1`、`iostat -d /dev/nvme1n1 1`、`/proc/net/dev` loopback 每秒差分；稳态样本剔除首行累计均值。
- **pprof**：客户端 `-cpuprofile`；服务端经 `:6061` 抓 `/debug/pprof/profile?seconds=10`（读测试短，入稳态 2s 后即抓）。
- **CPU 口径**：物理机实占 = `usr+sys`（iowait 时内核未占用算力，计为可用）。

## 4. 测试结果

### 4.1 带宽与并发扩展（threads×conns 矩阵，4M 读）

| threads | conns | 带宽 MiB/s | ops/s | CPU 实占 usr+sys | 达标 |
| --- | --- | --- | --- | --- | --- |
| 8 | 1 | 1922.28 | 480.57 | 3.8% | — |
| 8 | 2 | 2984.69 | 746.17 | 7.3% | — |
| 16 | 2 | 3159.74 | 789.94 | 6.6% | — |
| 16 | 4 | 4668.85 | 1167.21 | 11.1% | — |
| 16 | 8 | 5464.93 | 1366.23 | 14.5% | — |
| 32 | 8 | 6116.64 | 1529.16 | 18.7% | ✗ |
| **32** | **16** | **6386.46** | 1596.62 | **20.4%** | ≈98% |
| 32 | 32 | 6319.87 | 1579.97 | 20.6% | ≈97% |
| 48 | 16 | 6184.41 | 1546.10 | 19.6% | ✗ |
| 48 | 24 | 6092.97 | 1523.24 | 18.7% | ✗ |
| 64 | 16 | 5831.63 | 1457.91 | 16.9% | ✗ |
| 24 | 24 | 6101.55 | 1525.39 | 18.4% | ✗ |

- **最高带宽**：`threads=32, conns=16` = **6386 MiB/s（6.39 GB/s）**，为目标 6.5 GB/s 的 **98%**；32×32 持平，48/64 线程过配后下降（排队竞争加剧）。
- **增长规律**：同样以**连接数（流数）为主杠杆**——16T 时 c2→c4→c8→c16 带宽 3.16→4.67→5.46→6.39 持续放大；连接不再涨时加线程带宽回落。
- 6.5 目标的最后 ~2% 缺口在服务端读路径用户态开销与设备稳态读取能力（见 §6/§7），非配置所能补齐。

| --- | --- | --- | --- |
| 8T 1C | 16.24ms | 18.97ms | 23.18ms |
| 8T 2C | 10.30ms | 14.23ms | 17.46ms |
| 16T 4C | 11.60ms | 22.49ms | 29.80ms |

延迟随并发上升而增加（更多请求共享设备读取带宽），达到最高带宽配置时 p50≈20ms。

## 5. 资源占用（全量样例实测：32T×16C）

### 5.1 CPU（mpstat -P ALL）

- idle **58.8%**，实占 usr+sys = **19.6%**（usr 9.0 + sys 10.5），iowait 20.4%（计入可用）。
- 忙核 ~55-70%，以 iowait 与 sys 为主；整机仍余近 6 成空闲被占用能力。

### 5.2 磁盘（iostat 实测 /dev/nvme1n1）

| 项 | 值 |
| --- | --- |
| 读均值 | **5851.7 MiB/s** |
| 读峰值 | 6601.1 MiB/s |
| 应用层 | 6337.2 MiB/s（此次样例，与矩阵 6386 一致） |

多流交叉 O_DIRECT 顺序读，稳态读取能力 ~5.9-6.4 GB/s，与应用层带宽吻合；**设备读取是主约束**。

### 5.3 网络（loopback /proc/net/dev 差分实测）

- **RX_AVG=6410.0 MiB/s / TX_AVG=6410.0 MiB/s**（PEAK 6677.7），双向对称，与应用层带宽一致，环回无瓶颈。

## 6. pprof 热点（全量样例：32T×16C 读）

### 客户端（taihu-rpc-bench，进程 CPU ≈ 12.6 核）

| 热点 | flat | 说明 |
| --- | --- | --- |
| runtime.memmove | 41.67% | Get 收流聚合 `f.CopyTo(out[pos:])` 单帧搬运 |
| syscall.Syscall6 | 30.68% | socket 读（数据收帧） |
| runtime.memclrNoHeapPointers | 14.63% | `make([]byte, size)` 返回缓冲清零 |

### 服务端（taihu-server，进程 CPU ≈ 6.3 核）

| 热点 | flat | 说明 |
| --- | --- | --- |
| syscall.Syscall6 | 65.86% | O_DIRECT 设备读 + wire writev 推流 |
| runtime.memclrNoHeapPointers | 21.77% | bufpool 对齐缓冲复用前清零（4MiB/块） |
| pebble getInternal | 2.26% | 元数据读（已 LoadCache 预热，占比小） |

读路径最突出的是**服务端 21.8% 的 memclr**（bufpool 对齐缓冲逐块清零）与客户端的 memclr（Get 返回缓冲清零）——读取方向存在大量 4MiB 缓冲的初始化清零；叠加 O_DIRECT syscall 与收/推流拷贝，构成 6.39GB/s 上限的微观来源，而磁盘实测峰值 6601 表明物理设备还有 ~3% 余量被该开销吃掉。

## 7. 达标分析与最低资源

- **最高实测 6.39 GB/s（`32T×16C`）** = 目标 6.5 的 98%，物理机实占 ~20%（约 19 核/96 核）。
- **达标 6.0+ GB/s 的最低资源**：`32T×8C`（6116 MiB/s，18.7%）——若以 6.0 为口径，32T8C 足够。
- **6.5 缺口归属**：服务端读路径（bufpool 清零 memclr + O_DIRECT syscall）与设备稳态读取（AVG 5851 < PEAK 6601）共同决定；线程/连接在 ≥32T×16C 已无放大空间（48/64T 反而退化）。
- **杠杆规律**：读路径同样**连接数主导**（16T：c8→c16 带宽 5.46→6.39），线程过冲（64T）会因请求排队与窗口竞争降低吞吐。

## 8. 结论与建议

1. **近达标**：RPC 端到端读最高 **6.39 GB/s**（32T×16C），为 6.5 目标的 98%；物理机实占 ~20%，其中 sys 与 iowait 为主，非 usr 紧张。
2. **最低资源**：读 6.0+ GB/s 需 `32T×8C`；摸 6.39 需 `32T×16C`。连接数（流数）是主杠杆，线程过冲（48/64）退化。
3. **与写对比**：写 2.5GB/s 已达标并封顶设备写极限；读受设备读取能力 + 读路径零初始化开销双重约束，未达 6.5。
4. **优化方向**（读路径，按收益排序）：
   - **消除 bufpool 对齐缓冲清零**（服务端 memclr 21.8%）：对 O_DIRECT 读取，整块 4MiB 数据会被写满，可在 ReadAt 后仅补零尾块而非全量 clear；或按需延迟清零（首块/末块才清）。
   - **客户端 Get 返回缓冲清零**（memclr 14.6%）：配合 bufpool 复用 + 首末块补零策略。
   - 若目标必须 6.5+，需上述用户态削减叠加更高稳态读盘能力（当前 AVG 5851 vs PEAK 6601 尚有盘侧抖动）。
