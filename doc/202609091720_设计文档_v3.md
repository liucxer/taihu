# taihu 远程访问层（Server / Client / RPC Bench）— 设计文档 v3

> 本文档只描述 **v3 新增内容**：基于 v2 对象存储库（`Storage` 库接口与存储语义见 设计文档_v2.md）的
> **gRPC Server / rpcclient / CLI / rpc-bench**。存储层、缓存、段布局等均沿用 v2/v1，本文不重述。
>
> v3 结论（已确认）：gRPC 传输；**单 server 单盘**（不要求多 NVMe）；rpcclient 与本地库**同接口**（调用方无感切换本地/远程）。

## 1. 系统架构

```
┌──────────────┐   gRPC (streaming)   ┌───────────────────┐        ┌────────────────────┐
│ 跨节点 Client │ ───────────────────► │   taihu-server    │ ─────► │  Storage (v2 库)    │
│  taihu-client │                      │   (单 Storage)    │        │  Pebble + O_DIRECT  │
│  rpcclient    │ ◄─────────────────── │   4 个 RPC 方法    │      │  NVMe 盘            │
│  taihu-rpc-bench│                     └───────────────────┘        └────────────────────┘
└──────────────┘
```

- client 只依赖 `rpcclient` 库（内部是 gRPC stub），不感知存储语义细节——语义收敛在 server 端。
- server 只有一个 `Storage` 实例（v3 不做多盘路由；预留未来扩展 `-devs`）。
- 库本身不变，v3 全部为新增代码。

## 3. gRPC 协议定义

### 3.1 proto

```proto
syntax = "proto3";
package taihu.rpc;
option go_package = "github.com/liucxer/taihu/rpc";

service ObjectStore {
  // Put：client 流式上传。首帧携带 key+size，其后为数据块。
  rpc Put(stream PutChunk) returns (PutResp);
  // Get：server 流式下发。off/size 为对象内区间（size=-1 表示读到对象结尾）。
  rpc Get(GetReq) returns (stream GetChunk);
  rpc Delete(DeleteReq) returns (DeleteResp);
  rpc Stat(StatReq) returns (StatResp);
}

message PutChunk {
  PutHeader header = 1;   // 仅首帧非空；其余帧 header 为空
  bytes     data   = 2;   // chunk 数据（≤ 256KB）
}
message PutHeader {
  string key  = 1;
  int64  size = 2;        // 对象逻辑大小（字节），必须 0<=size<=SegmentSizeBytes
}
message PutResp {}

message GetReq {
  string key = 1;
  int64  off = 2;         // 相对对象起始偏移，>=0
  int64  size = 3;        // -1 = 读到结尾；否则 0<=size 且 off+size<=对象 Size
}
message GetChunk { bytes data = 1; }

message DeleteReq { string key = 1; }
message DeleteResp {}

message StatReq { string key = 1; }
message StatResp { int64 size = 1; }
```

### 3.2 本地接口 ↔ RPC 语义映射

| 本地 `Storage`（v2） | RPC | 说明 |
|----------------------|-----|------|
| `Put(ctx, key, size, in io.Reader)` | `Put` client-streaming | 首帧 `PutHeader{key,size}`（服务端校验 size），数据流后续帧；`in` 读完即 `CloseSend` |
| `Get(ctx, key, off, size) io.ReadCloser` | `Get` server-streaming | `off/size` 原样透传，`size=-1` 全量；返回流式数据+EOF |
| `Delete(ctx, key)` | `Delete` 一元 | — |
| （新增便利） | `Stat` 一元 | 返回对象 `Size`，供客户端决定读区间/预检 |

> `LoadCache` 是 server 内部行为（缓存是 server 进程内 read-through 加速层），**不对 client 暴露**；
> server 启动后按需内部预热即可，client 无需感知。

## 4. Server 设计

### 4.1 进程结构

```go
type server struct {
    s  *taihu.Storage   // 单实例，v3 不引入多盘
    ...
}
// 启动：NewStorage(dbDir, devPath) → 注册 gRPC 服务 → 监听 -addr
```

- 参数：`-addr`（默认 `:50051`）、`-db`（pebble 目录）、`-dev`（裸设备）。与本地库 `NewStorage` 一一对应。
- 认证：内网 v1 用 insecure；TLS/`X-Token` 预留接口。

### 4.2 四个 RPC 实现要点

| 方法 | 实现 |
|------|------|
| `Put` | recv 首帧解析 `PutHeader`，校验 `0<=size<=SegmentSizeBytes`（违例→`ResourceExhausted`/`InvalidArgument`）；后续 chunk 经 `io.Pipe` 流式喂给 `s.Put(ctx, key, size, pipeReader)`（独立 goroutine 消费，避免整对象驻留内存——对象上限 8GB）；`Recv` 返回 `io.EOF` → 关闭写端，等待 `Put` 完成 |
| `Get` | `s.Get(ctx,key,off,size)` 返回池化 `io.ReadCloser`；循环 `Read` 到 256KB buf→`Send`；EOF 后 `Close()` 归还池缓冲 |
| `Delete` | 一元，直接透传 |
| `Stat` | `s.db.GetMapping` 返回 `meta.Size` |

- **零对齐负担**：client 上传的流直接交给 `Storage.Put`，4K 对齐由库内部 `append` 吸收（v2 §6）；Get 同理。
- **块大小**：`chunk = 256KB`（对齐友好、平衡网络头开销与延迟）。

### 4.3 gRPC 流控与性能参数（必须设置）

```
grpc.MaxRecvMsgSize / MaxSendMsgSize：4MB（≥ chunk，避免默认 4MB 边界抖动）
grpc.InitialWindowSize：1MB（提升单连接并发流）
grpc.InitialConnWindowSize：4MB
```

- 每 RPC 一个 goroutine；`Storage` 并发安全（v2 §7：Get 并行、Put 游标分配串行），多流读写可同时进行。
- 保留 `-cpuprofile`/`-memprofile` 与延迟统计，便于按现性能测试流程采集 server 端 CPU 热点。

## 5. rpcclient 设计（对外库，与本地同接口）

### 5.1 公共接口（与 `Storage` 签名一致，调用方可无感切换）

```go
// 远程实现，方法签名与 taihu.Storage 完全一致
type Storage struct { conn *grpc.ClientConn; ... }

func Dial(ctx context.Context, addr string) (*Storage, error)      // 连接管理
func (s *Storage) Put(ctx context.Context, key string, size int64, in io.Reader) error
func (s *Storage) Get(ctx context.Context, key string, off, size int64) (io.ReadCloser, error)
func (s *Storage) Delete(ctx context.Context, key string) error
func (s *Storage) Stat(ctx context.Context, key string) (int64, error) // 便利方法
func (s *Storage) Close() error
```

### 5.2 实现要点

- **Put**：`NewStream` → 首帧 `PutChunk{header:{key,size}}`；循环 `in.Read(256KB buf)` → `Send(PutChunk{data})`；`CloseSend` → 回收 `PutResp`。
- **Get（流式返回关键点）**：`GetReq{key,off,size}`；返回对象用 `io.Pipe`：recv goroutine 把每个 `GetChunk` 写入 Pipe 写端，对外暴露读端 `ReadCloser`。
  - `Close()` 语义与本地一致：**必须 Close**——内部 cancel ctx 终止流、释放连接资源（本地是归还池化缓冲）。
  - 越界/不存在错误由 server 端 `Storage.Get` 判定，经错误映射（§6）还原为 `ErrInvalidRange`/`ErrNotFound`。
- **错误映射**：`status.Code` → 库错误，见 §6。
- **连接**：`grpc.NewClient(addr, insecure, keepalive)`；断线重连由 gRPC 底层 subconn 处理；多 goroutine 共享一连接（HTTP/2 多路复用）。

## 6. 错误映射

| 库错误（v2 error.go） | gRPC status | 还原 |
|----------------------|-------------|------|
| `ErrInvalidRange` | `codes.OutOfRange` | server / client 双向还原 |
| `ErrNotFound` | `codes.NotFound` | 同上 |
| `ErrTooLarge` | `codes.ResourceExhausted` | 同上 |
| 其他内部错误 | `codes.Internal` | 包装为通用错误 |

## 7. taihu-client CLI

```
taihu-client -addr :50051 put   -key K -size N -file F      # 上传
taihu-client -addr :50051 get   -key K [-off O -size N] -o F  # 下载（支持区间读，缺省全量）
taihu-client -addr :50051 delete -key K
taihu-client -addr :50051 stat  -key K
```

- 功能：连通性验证 + 人工调试（等价一个"远程文件工具"）。
- 实现直接复用 `rpcclient`，是它的一层薄壳。

## 8. taihu-rpc-bench（rpcclient 压测工具）

> 目的：测**跨节点端到端**读写带宽/延迟/CPU（server 端），与本地 `taihu-bench`（v2 §9）对照，量化网络与协议开销。
> 与本地 bench 的区别：**无 `-db`/`-dev`**，增加 `-addr`；数据读写全部走 rpcclient。

### 8.1 参数

| 参数 | 说明 | 默认 |
|------|------|------|
| `-addr` | server 地址（必填） | — |
| `-mode` | `write` \| `read` | 必填 |
| `-size` | 对象大小（字节，任意整数，对齐由服务端处理） | 4096 |
| `-threads` | 并发 goroutine 数（共享同一连接） | 1 |
| `-count` | 对象总数；write=写入数，read=读取 key 数 | 1000 |
| `-keys-prefix` | key 前缀（`<prefix>/<seq>`） | `rbench` |
| `-latency` | 采集每 op 延迟分位 p50/p90/p99 | false |
| `-report-interval` | 进度打印间隔 | 2s |

命令示例：

```bash
# 跨节点顺序写：先写入 n 个对象（首帧 size 透传，流式上传）
taihu-rpc-bench -addr 100.71.128.12:50051 -mode write -size 4194304 -threads 16 -count 20000 -keys-prefix rp4m -latency

# 跨节点随机读：读同一批 key（每 key 只读一次，整对象读）
taihu-rpc-bench -addr 100.71.128.12:50051 -mode read  -size 4194304 -threads 16 -count 20000 -keys-prefix rp4m -latency
```

### 8.2 与本地 bench 相同的语义

- Key 集合 = `<prefix>/<seq>`，写读同规则；读模式区间切分保证**每 key 全进程只读一次**（防缓存/重复 IO 污染）。
- 读为整对象 `off=0, size=<size>`；`size=-1` 走协议默认全量亦可。
- 指标：总对象数/字节/耗时、吞吐（MiB/s、ops/s）、`-latency` 时输出 p50/p90/p99。
- 可选 `-cpuprofile`（client 侧）；server 侧 CPU 用其自带 pprof 采集。

### 8.3 关注点

- **网络即新瓶颈**：本地读 6.8 GB/s，25GbE ≈3 GB/s；预期端到端带宽受网卡限制，CPU 热点应集中在 client 的发送循环与 server 的流收/发。
- 对比矩阵：本地(Storage) vs 远程(rpcclient) × 写/读，量化 gRPC 开销占比。
- 前置：`read` 前必须先用相同前缀 `write` 灌数据（server 端已有数据时跳过）。

## 9. 部署与验证路径

1. 本机验证：`taihu-server -db /tmp/tdb_s -dev /dev/... -addr :50051` → `taihu-client` 连通 + 区间读/越界用例。
2. 跨节点压测：server 部署 128.12 → 本地 `taihu-rpc-bench` 灌 4MiB 数据并读回，采集 server CPU/网络。
3. 链路验证：单测（rpcclient fakeserver 模拟）+ 集成（真机）。

## 10. 已知权衡 / 后续扩展（预留，不实现）

- 多盘：v3 单盘；`-devs` + key 路由留给后续。
- 多节点集群：元数据面/数据面分离、peer 路由——接口层已隔离（client 只认 `ObjectStore`），后续加节点不影响 client。
- 认证：insecure → TLS/Token 可插拔接入。
- `Get` 大数据别的高层 API（如 range 到文件）可作为后续便利接口。
