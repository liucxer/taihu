## 1. 评审范围与方法

评审结论不靠阅读印象，每条均以可复现的命令或编译实验为依据：

| 手段 | 用于确认 |
|------|----------|
| 逐包 `go list -f '{{.Imports}}'` + 模块前缀过滤 | 依赖边、是否成环、分层是否单向 |
| 外部模块实测（在 `/tmp` 建独立 module 消费本仓库） | `pkg/` 是否真能被外部 import |
| `GOOS=linux go build / go vet / go test -c` | 平台切分是否完整（macOS 编得过、linux 编不过是本仓库的经典坑） |
| `wc -l` 分文件统计 | 包与文件规模、测试分布 |
| `git check-ignore -v` / 实际 `git add` | `.gitignore` 规则的实际生效范围 |

### 2.2 分层与依赖方向

```
cmd/taihu/cmd (2419)                    CLI（cobra）
      ↓
pkg/rpccluster (982) · pkg/rpcclient (353)      集群客户端 / 传输客户端
      ↓
internal/rpcserver (17) · internal/transport (2913)   服务端入口 / 帧协议
      ↓
pkg/taihu (750)                                  Storage 核心
      ↓
internal/device (672) · internal/metastore (1099)      设备层 / 元数据层
      ↓
internal/aio (1466) · bufpool (198) · layout (40) · ierr (22) · version (47) · cluster (593)
```

**结论：依赖严格单向，无环，无反向引用**（用 `go list` 逐包核对，非目测）。`cmd → pkg → internal → 叶子` 的层次清晰，叶子包职责单一。

### 2.3 平台切分

12 处 `_linux` / `_other` 配对，`!linux` 侧提供可编译的降级实现：

```
internal/aio/       aio_linux.go + aio_other.go · aio_uring_linux.go · probe_linux.go + probe_other.go
internal/device/    device_linux.go + device_other.go · info_linux.go + info_other.go · putwriter_linux.go + putwriter_other.go
internal/transport/ shmipc_server.go(linux) + shmipc_server_other.go
pkg/rpcclient/      shmipc.go(linux) + shmipc_other.go
```

这套切分让工程**在 macOS 上可编译、可跑单测、可起服务端**（本次评审即借此在 macOS 上完成验证）。命名上有一处不一致：`aio`/`device` 用 `_linux` 后缀，`transport`/`rpcclient` 用 build tag 而非文件名后缀。两种都合法，但同一个仓库里混用会让「哪些文件是平台专有」需要靠 grep 而非文件名判断。建议统一为 `_linux` 后缀（`shmipc_server.go` → `shmipc_server_linux.go`）。

## 3. 问题清单

### P0-1：模块对外不可消费，`pkg/` 承诺的公开 API 实际是虚构的

`go.mod` 用**相对路径 `replace`** 挂了两份 fork：

```go
replace github.com/cloudwego/netpoll   => ./third_party/netpoll
replace github.com/cloudwego/shmipc-go => ./third_party/shmipc-go
```

而 **`replace` 只在主模块生效，不传递给下游**。实测：在 `/tmp` 建独立 module `import github.com/liucxer/taihu/...`，构建直接失败：

```
# github.com/liucxer/taihu/internal/transport
conn.go:28: undefined: netpoll.SetAlignedAllocator
conn.go:29: undefined: netpoll.SetInputAlignedAllocator
conn.go:30: undefined: netpoll.SetInputNodeSize
```

下游拿到的是上游 netpoll（无 fork 新增的三个可插拔分配器 API），**连依赖树都构建不起来**。

影响：

- 任何外部模块都无法 import 本仓库 —— 无论 `pkg/` 还是别的。
- 但 README 与 `pkg/rpccluster/keepalive.go` 明确存在「SDK 客户端保活注册」「`taihu client list` = SDK 客户端清单」这一契约。**若确有跨仓库 SDK 消费方，这条路现在是断的。**
- 顺带一个体量事实：`third_party/` 共 **14,120 行**，比主模块源码（11,917 行）还多。仓库的「有效体积」有一半是 fork。

建议（三选一，按推荐序）：

1. **把 fork 的 patch 收进主模块**（改动的文件放进 `internal/` 或 `vendor/`），`replace` 仅保留在开发期 —— 彻底消除对外阻碍；
2. **fork 发布到可解析的私有模块路径 + 版本**（内部 GitLab 等），`replace` 换成正常 `require`；
3. **若确认无外部消费方**：把 `pkg/*` 降级为 `internal/*`，停止维护 API 兼容性（`pkg/taihu/error.go` 里「保证对外 API 不变」的注释随之失效）。

**这是本次评审唯一需要先做决策、不能直接动手的一项**，因为方向取决于是否真有外部 SDK 消费方。

### P1-1：`pkg/` 导出签名泄漏不可命名的 `internal/` 类型

`internal/` 无法被外部 import，因此出现在导出签名里的这些类型，**调用方无法命名** —— 不能声明该类型的变量、不能写字面量、不能存进自己的字段。给消费方补上 `replace` 以隔离出该问题后，报错为：

```
./main.go:12:30: undefined: taihu.ModeIOUring
./main.go:15:19: undefined: rpccluster.NewMemKV
```

完整清单（9 处签名 + 2 处结构体字段）：

| 位置 | 泄漏类型 | 后果 |
|------|----------|------|
| `pkg/taihu/storage.go:30` `NewStorage(..., l layout.Layout, ...)` | `layout.Layout` | **SDK 主构造函数无法被调用**（消费方造不出该参数） |
| `pkg/taihu/storage.go:59` `Layout() layout.Layout` | 同上 | 返回值无法接住 |
| `pkg/taihu/storage.go:368` `SegmentStats() map[metastore.SegmentState]int` | `metastore.SegmentState` | 同上 |
| `pkg/taihu/options.go:23` `WithAIOMode(m aio.Mode)` | `aio.Mode` | 只能用裸常量 `WithAIOMode(0)` 调用 |
| `pkg/taihu/admin.go:17` 字段 `State metastore.SegmentState` | 同上 | 无法读该字段做判断 |
| `pkg/rpccluster/registry.go:54` `NewInstanceRegistry(kv cluster.KV, ...)` | `cluster.KV` | 构造函数不可调用 |
| `pkg/rpccluster/index.go:36` `NewIndexManager(kv cluster.KV)` | 同上 | 同上 |
| `pkg/rpccluster/config.go:43` 字段 `KV cluster.KV` | 同上 | 无法作为字段赋值 |
| `pkg/rpccluster/registry.go:114` `Lookup() (cluster.InstanceInfo, bool)` | `cluster.InstanceInfo` | 返回值只能靠类型推导 |
| `pkg/rpccluster/picker.go:34` `Pick() (cluster.InstanceInfo, bool)` | 同上 | 同上 |

关键点：**仓库已经知道正确做法，只是没做全。** `pkg/taihu/error.go` 与 `pkg/taihu/meta.go` 用的是 type alias re-export：

```go
// pkg/taihu/meta.go —— 正确
type ObjectMeta = metastore.ObjectMeta

// pkg/taihu/options.go —— 漏了
func WithAIOMode(m aio.Mode) Option
```

建议：按 `error.go`/`meta.go` 的模板机械补齐 —— 每个泄漏类型加 `type X = internal.Y` 别名，常量组整体 re-export。注意顶层入口 `rpccluster.NewFromTiKV(ctx, TiKVOptions)` 是**干净**的，说明设计意图是让消费方从这个入口进；那就更该把其下的类型补齐，否则入口之下的构造器全部不可用。

### P1-2：`.gitignore` 的 `taihu` 无锚点 —— **已导致仓库里缺文件，干净检出无法编译**

`.gitignore:6` 的 `taihu` 没有前导 `/`，于是匹配**任意层级**名为 `taihu` 的路径：

```
$ git check-ignore -v internal/taihu
.gitignore:6:taihu    internal/taihu
```

`pkg/taihu/` 与 `cmd/taihu/` 整个目录命中该规则。**这不是潜在风险，而是已经造成实际损坏**：

`pkg/taihu/options.go` 定义了 `Option` 类型、`defaultOptions()`、`WithAIOMode()`、`WithAIOIOPoll()`，
而**已被提交的** `pkg/taihu/storage.go:30`（`opts ...Option`）、`:31`（`defaultOptions()`）、`:41` 与
`cmd/taihu/cmd/root.go:123-124` 都在引用它们。但该文件因忽略规则从未入库。
把 `16fa969` 的全量内容按 `git archive` 导出（等价于 fresh clone）后编译：

```
# github.com/liucxer/taihu/pkg/taihu
pkg/taihu/storage.go:30:92: undefined: Option
pkg/taihu/storage.go:31:7: undefined: defaultOptions
```

补齐这**一个文件**后即 `BUILD_OK` —— 即**已推送的 HEAD 对任何新克隆者都是编译不过的**，
本地之所以一直正常，纯粹因为那个文件还躺在工作区里。

三个后果：

1. **已提交的代码缺依赖文件**（上述），必须尽快补一次提交。
2. **新文件会无声消失**：`git status --short` 根本不显示它（被忽略），只有 `git ls-files --others --ignored` 才看得到。`pkg/taihu` 恰是 SDK 包，未来新增文件默认进不了版本库。
3. **`git add` 对这两个目录会报「ignored」**：

   ```
   $ git add pkg/taihu/meta.go
   The following paths are ignored by one of your .gitignore files:
   pkg/taihu
   ```

   已跟踪文件仍能加进去，但报错会打断批量 `git add`（本次提交时即因此中断了 `&&` 链），新人也会被误导。

建议：改为 `/taihu`（仅锚定仓库根目录下的构建产物），并把 `pkg/taihu/options.go` 补入版本库。
**这是全清单里投入产出比最高的一处**，且是本评审唯一一条「不修就有实际损坏」的问题。

> 教训：仓库里没有任何检查能发现「已提交文件依赖未提交文件」——Go 编译器只看工作区。
> 建议把「干净检出能否编译」纳入 CI 或至少纳入发版前检查（`git archive HEAD | tar -x` 后构建）。

### P2-1：`internal/transport` —— 最大的包、零测试、四种职责

2913 行分布：

| 文件 | 行数 | 职责 |
|------|-----:|------|
| `shmipc_server.go` | **795** | 服务端 shm（全仓最大文件） |
| `protocol.go` | 520 | wire codec（纯函数编解码） |
| `conn.go` | 506 | **客户端** TCP 连接 |
| `shmipc_client.go` | 417 | **客户端** shm |
| `server.go` | 320 | **服务端** TCP |
| `client_admin.go` / `server_admin.go` | 142 / 127 | admin RPC |
| `stats.go` | 56 | 统计 |

两个问题：

1. **客户端与服务端混在一个包**：只想用客户端的 `pkg/rpcclient`、只想用服务端的 `internal/rpcserver`，都会拖进整包（及其 netpoll/shmipc 依赖）。
2. **零测试**，而其中 `protocol.go` 是 520 行纯函数编解码 —— 这是仓库里**最容易测、也最该测**的部分。

建议（分两步，先做便宜的）：

1. **抽出 `internal/transport/protocol`**：纯 codec、无 I/O、不需要 build tag，补表驱动单测（各帧类型的编解码往返、边界长度、畸形输入）；
2. 之后视需要再拆 `transport/tcp` + `transport/shm`。

**为什么优先做这个**：macOS 侧测试出现随机 `bad file descriptor` 时，排查成本很高，正是因为传输/设备层只有经过 `pkg/rpcclient` 的集成测试间接覆盖 —— 随机失败时无法定位到层。`internal/aio` 的「tagless 契约测试 + 平台提供 backend 切片」是本仓库**最好的测试实践**（见 §5），值得复制到 transport。

### P2-2：`internal/rpcserver` 是 17 行纯转发包，仅 1 个调用点

```go
func New(storage *taihu.Storage) *transport.Server { return transport.NewServer(storage) }
```

其注释称「薄封装以保持生命周期接口不变」，但它**返回的就是 `transport.Server`** —— 抽象没有建立起来，只多了一个名字，且调用点只有 `cmd/taihu/cmd/server.go` 一处。建议删除该包，调用点直接写 `transport.NewServer(storage)`。

### P2-3：最该测的包没有测试

见 §2.1。可接受零测试的有 `internal/ierr`(22) / `internal/version`(47) / `internal/rpcserver`(17)（P2-2 建议直接删）；`cmd/taihu/cmd`(2419) 是 CLI 装配层，靠端到端验证。**`internal/transport`(2913) 零测试是最大的风险面**，见 P2-1。

### P3-1：文档膨胀，缺「哪份是现行」的索引

```
doc/  共 56 个文件
├── 性能测试报告/  46 篇
├── 设计文档/       9 篇
└── 部署记录/       1 篇
```

设计文档的现状：`设计文档_v1/v2/v3` 三代并存 + 4 篇专题（segment 级 GC ×3、集群支持 ×1）+ 2 篇架构文档（20260914）。性能报告中同一 commit 号反复重测：`50ebbe4` 与 `2a0a2ec` 各 5 篇，`8abdf4d` 与 `468a9af` 各 3 篇。

**问题不是文档多，而是没有索引标明哪份代表当前结论。** 新人打开 `doc/设计文档/` 面对 9 个文件无法判断该读哪份 —— `v3` 是否一定最新？`20260914_taihu项目架构设计文档.md` 与 `v3` 是什么关系？（实际关系是前者为项目级总体架构、后者为远程访问层专题，但文档本身没说。）

建议：

1. 新增 `doc/README.md` 索引，每篇标注 **【现行】/【已被 X 取代】/【历史存档】**；
2. 性能报告按阶段收进子目录（如 `doc/性能测试报告/202609/`），并抽出一份汇总表（日期 / commit / 场景 / 关键数字 / 结论），让单篇报告降级为附件。46 篇散篇的价值远低于一张按场景可比的汇总表。

### P3-2：操作知识散落三处

`.trae/skills/`（14 个 skill）、`doc/部署记录/`、`.claude/` 三个位置都承载「怎么部署 / 怎么压测 / 怎么巡检」。没有单一归属，同一条流程容易存在两个版本。建议明确边界：可执行的 skill 归一处，给人读的文档归 `doc/`。

### P3-3：Makefile 只有 3 个目标

现有 `all` / `build` / `clean`。但本仓库有大量「macOS 编得过、linux 编不过」的经典坑（`unix.POLLIN` 仅 linux 存在、`Syscall6` 参数个数、结构体 size/offset 断言、`_test` 后缀必须排在 GOOS 之后）。本次评审中这些检查是手工逐条跑的。

建议加一个目标，把这类检查自动化：

```make
check-linux:
	GOOS=linux GOARCH=amd64 go vet ./...
	GOOS=linux GOARCH=arm64 go build ./...
	GOOS=linux GOARCH=amd64 go test -c -o /dev/null ./...
```

这能拦住一整类「只在真机验收时才暴露」的低级错误 —— 而真机验收的成本远高于本地一条命令。

## 5. 值得保留的做法（正面清单）

评审不应只有问题。以下几条达到了「可直接作为团队规范」的水平：

1. **依赖方向严格单向且无环**，`cmd → pkg → internal → 叶子` 层次清晰，叶子包职责单一（`ierr` 22 行、`layout` 40 行、`version` 47 行）。这是 12k 行项目里少见的整洁度。
2. **平台切分用「tagless 契约测试 + 平台提供 backend 切片」**（`internal/aio/aio_test.go` + `aio_backends_linux_test.go` / `aio_backends_other_test.go`）：同一组断言在两个后端上参数化跑，且不可用时 `t.Skipf` 必须带 errno —— 避免「静默跳过」看起来和「通过」一样。**这是本仓库最好的测试实践，建议推广到 transport 与 device。**
3. **`!linux` 兜底实现让工程在 macOS 上可编译、可跑测试、可起服务端**：显著降低了开发与排障门槛（本次 macOS 侧随机 `bad file descriptor` 的根因定位，正是靠能在 macOS 上反复跑单测）。
4. **fork 收在 `third_party/` 并用 `replace` 指向本地**：在「必须改上游才能落地」的场景下，这是隔离改动、保留上游同步能力的合理做法（P0-1 只针对其对外分发的副作用，不否定这个选择本身）。
5. **用 `unsafe` 的结构体布局断言**（`aio_uring_linux.go` 的 `Sizeof`/`Offsetof` 编译期断言）把「布局写错」从运行期踩内存变成编译失败。
6. **提交信息按类型分点**（`type(scope): 中文标题` + `-` 要点），且说明了「为什么」而非只记「改了什么」，对后续 bisect 与追溯友好。
