# io_uring 可行性分析与改造方案

> 日期：2026-09-14
> 范围：磁盘 IO、RPC（TCP）、同机共享内存（shm）三条 I/O 路径
> 状态：**需求已确认（见 §6），方案待评审，尚未落地任何代码**

## 1. 结论摘要

| 域 | io_uring 是否有意义 | 判断 | 优先级 |
|---|---|---|---|
| **磁盘 IO**（`internal/aio`，libaio） | **有**，收益在**注册缓冲**与 **IOPOLL** | 做 | 高 |
| **RPC / TCP**（netpoll fork） | **有条件**，收益在 syscall 开销与异步流水 | 做（**但先做一个便宜的判定实验，见 §3.2**） | 中 |
| **shm 通信**（shmipc fork） | **无意义** | 数据面零 syscall + 零拷贝，已是理论最优形态 | **不做** |

### 1.1 运行环境：两种内核并存

io_uring 自 **Linux 5.1** 引入。当前存在**两类**节点：

| 节点 | 内核 | io_uring | 说明 |
|---|---|---|---|
| 现有测试/部署节点 | BCLinux **4.19.90**，aarch64 96 核 | ❌ **不可用** | RHEL8 系内核，未 backport。`internal/aio/aio.go:3` 已记录此事 |
| **新增机器** | **5.10** | ✅ **可用** | 5.10 完整覆盖本方案所需能力 |

**5.10 的能力覆盖情况**（均满足，无需降级）：

| 能力 | 引入版本 | 5.10 |
|---|---|---|
| `IORING_OP_READV/WRITEV`、`REGISTER_BUFFERS`、`IOPOLL`、`SQPOLL` | 5.1 | ✅ |
| `IORING_OP_READ/WRITE`（非向量化）、`IORING_OP_SEND/RECV` | 5.6 | ✅ |
| `IORING_FEAT_FAST_POLL`（socket 快速轮询） | 5.7 | ✅ |

**结论：本特性在 5.10 新机器上是活的，不再是预留死代码。** 但**现有 4.19 节点仍会走 libaio 回退**，因此：

1. **双后端必须长期并存**，libaio 不可删除；
2. **验收基线在 5.10 新机器上建立**，4.19 节点只验证"能正常回退"。

## 2. 现状勘察

### 2.1 三条 I/O 路径的实际形态

| 路径 | 数据面机制 | 实际 syscall | 关键位置 |
|---|---|---|---|
| **磁盘** | O_DIRECT 裸盘直读直写 | `io_submit` / `io_getevents`（libaio） | `internal/aio/aio_linux.go` |
| **RPC / TCP** | netpoll + LinkBuffer（epoll） | `readv`（收）/ `sendmsg`（发） | `third_party/netpoll/net_io.go:25`、`connection_impl.go:531` |
| **shm** | **mmap 共享内存 + 内存屏障发布** | **数据面零 syscall** | `internal/transport/shm_frame.go:38/67` |

三点值得单独记录：

- **全仓没有 splice/sendfile 路径**（grep 无命中）。既有零拷贝全部是「散射聚集 + 缓冲所有权移交」。
- **shm 的控制面**才走 unix socket（握手 + `SCM_RIGHTS` 传 memfd，`protocol_manager.go:373-380`），量极小。
- **shm 服务端确有 O_DIRECT 直读进共享内存**（`server_shm.go:524` `shmWriteDataFrameDirect` → `storage.ReadAtInto`），即免 memcpy 的全链路 DMA —— 但它走的是**同一个 `aio.Ring`**，属磁盘路径而非 shm 路径（详见 §3.3）。

### 2.2 磁盘层现状细节

`internal/aio/aio.go:47` 定义 `Ring` 接口；`aio_linux.go` 为其 Linux 实现：

| 项 | 现状 |
|---|---|
| 底层 | libaio 四系统调用 `io_setup/io_submit/io_getevents/io_destroy` |
| 结构体 | `iocb`/`io_event` 按 `linux/aio_abi.h` 手工声明（**无 cgo，纯 Go**） |
| 批量 | `SubmitReadBatch` 一次 `io_submit` 提交多条（`aio_linux.go:118`） |
| 队列深度 | `aioDepth = 256`（`internal/device/device.go:33`） |
| 完成泵 | `device.pump()` 单 goroutine 串行 `Wait`，按 seq 分发（`device.go:128`） |
| 非 Linux | goroutine + 同步 `ReadAt/WriteAt` 兜底（`aio_other.go`） |

## 3. 逐域分析

### 3.1 磁盘 IO：有意义，但收益点不在"省 syscall"

io_uring 能在此处提供的四种手段，按对本项目的实际收益排序：

| 手段 | 收益机理 | 本项判断 | 前提 |
|---|---|---|---|
| **① 注册缓冲**<br>`REGISTER_BUFFERS` + `READ_FIXED/WRITE_FIXED` | 现在每次 `io_submit`，内核都要 `get_user_pages` pin 住 buf 再放掉。bufpool 是**有限个常驻 4K 对齐缓冲**，注册一次后内核不再重复 pin/unpin，消除固定 per-op 开销 | **最实在的收益**。与单次 IO 大小无关，IOPS 越高占比越大 | 需管理注册/注销生命周期 |
| **② IOPOLL**<br>`SETUP_IOPOLL` + `RWF_HIPRI` | NVMe 用轮询收完成、消中断，降 sys 时间与尾延迟 | **可能显著**。96 核富余，且单盘只用一半带宽 | 需 `/sys/block/nvmeXn1/queue/io_poll=1`；占一个核空转 |
| **③ SQPOLL**<br>`SETUP_SQPOLL` | 内核线程代为提交，提交路径 0 syscall | 需特权，与 IOPOLL 组合有讲究 | 需 `CAP_SYS_ADMIN` 或放开 `io_uring_disabled` |
| **④ 提交/完成合并** | 一次 `io_uring_enter` 同时处理提交与收割，省掉 `io_getevents` 那次 syscall | **收益最小**（见下） | — |

#### 为什么"省 syscall"这条最弱

常被宣传的第 ④ 条，在**本项目的 I/O 粒度下占比很薄**：

- 每 4 MiB 块目前约 **1 次 `io_submit`（批量摊薄后更少）+ 摊薄的 `io_getevents`**，相对 4 MiB 的 DMA 传输时间是极小的一块；
- 报告里「服务端 syscall 89%」是**整机 40.3% usr+sys 内部**的分布（`:85`），不是整机 89%；
- 该报告的结论已经把瓶颈归给**整机 CPU + loopback 吞吐**（`:82`），而非 syscall 数量本身。

**结论**：应把注意力放在 **① 注册缓冲** 和 **② IOPOLL**，而不是把"减少 syscall 次数"当作主要卖点来做方案设计。

### 3.2 RPC / TCP：需求已确认要做 —— 但先看数据

**需求侧结论**：TCP 路径 CPU 消耗高（sys 占比 90%+），**确认做 io_uring 化**。

#### 先摆事实：现有测量与"CPU 是瓶颈"不一致

引自 `doc/性能测试报告/202609131228_d57edf9_四模式_4M_IO_读对比（storage-shm-rpc）.md`（rpc 4 conns 读峰值期，128.13 单机）：

| 指标 | 实测 | 含义 |
|---|---|---|
| sys 占比 | rpc **90%+**（server 2.34 核 sys 95%；bench 3.49 核 sys 89%） | ✅ **"CPU 消耗高"成立** |
| 两进程合计 | 5.8 核，其中 sys 91%+ | sys 绝对量**随带宽线性增长、占比不变** |
| **整机 CPU** | **idle 88.3%**，仅 ~12% 核活跃 | ❌ **CPU 不是瓶颈** |
| **单连接带宽** | **2345 MiB/s**（磁盘 avg 2346，峰值 2539 未跑起来） | ⚠️ **这才是真实天花板** |

该报告原文归因（`§5.1`）：

> **rpc 单连接（conns=1）64t 仅 2345 MiB/s**：**单 TCP 连接成为链路瓶颈** —— 磁盘 avg 2346 ≈ 应用 2345，连盘峰值 2539 都没跑起来；每帧 4MiB 的 TCP 收发包 + **拷贝开销**把上限钉在 ~2.3 GiB/s。

服务端发送路径的 CPU 归属（`202609100847_1a9fea5_服务端发送零拷贝优化验证报告.md:57`）：

> `internal/runtime/syscall.Syscall6` | 84.01% | socket 写（writev）

#### io_uring 能治什么、不能治什么

| 项 | io_uring 能否改善 | 说明 |
|---|---|---|
| syscall entry/exit 开销 | ✅ 能 | 90% sys 时间中的一块；批量提交 + `SQPOLL` 可大幅削减 |
| **同一连接多请求在途（异步流水）** | ✅ **可能** | netpoll 的写路径是排队式；`IORING_OP_SEND` 可让同一 socket 上多个 send 同时在途，**可能抬高单连接天花板** |
| **4 MiB 帧的内核 skb 拷贝 / 分片** | ❌ **不能** | 这是报告归因的天花板主因；只有 MSG_ZEROCOPY 能削 |
| 整机 CPU 瓶颈 | — | 当前**不存在**该瓶颈（idle 88.3%） |

**⚠️ 关键未知数**：单连接 ~2.3 GiB/s 的天花板，究竟是

- **(A) syscall 串行化**造成的 —— 那么 io_uring 的异步流水**能抬高它**；
- **(B) 内核拷贝带宽**造成的 —— 那么 io_uring **抬不动**，只有 MSG_ZEROCOPY 有效。

**方案里把 (A) 当作可验证假设，而非既定前提。**

#### 建议先做的判定实验（成本很低）

在写任何 io_uring 代码之前，用一个下午判定天花板归属：

1. 固定单连接，把帧长从 4 MiB 降到 256 KiB / 64 KiB，看单连接上限是否显著上升 —— **上升 → 倾向 (A)**（大帧串行化），持平 → 倾向 (B)；
2. 单连接下并发发起多个 `sendmsg`（不等完成），看吞吐是否随在途数上升 —— **上升 → (A)**；
3. 直接开 `SO_ZEROCOPY` + `MSG_ZEROCOPY` 打到这个连接，看上限是否被抬高 —— **上升 → (B)**。

#### 可行性与改动面

改动落点在 fork 内部，**`internal/transport` 零改动**：

- netpoll 的 epoll 实现在 `third_party/netpoll/poll_default_linux.go:89/99` 与 `sys_epoll_*.go`；
- `internal/transport` 只使用公开 API（`EventLoop`/`Connection`/`Reader`/`Writer` + fork 新增的可插拔分配器与 `TakeTry`），**从不直接触碰 epoll**。

**需要一并解决的三件事**（否则改动会卡住）：

1. **唤醒语义**：netpoll 用 eventfd 唤醒（`poll_default_linux.go:137/223`），而 **shmipc fork 的 dispatcher 连 eventfd 都没有** —— `event_dispatcher_linux.go:37` 的 `init()` 里写死包级 `defaultDispatcher`，`post()` 只入队 lambda，靠 epoll 循环 **1s 超时轮询** `runLambda()`。换 io_uring 必须连带重做唤醒；
2. **抽象层无注入口**：netpoll 的 `Poll` 接口（`third_party/netpoll/poll.go:20`）由 `poll_manager` 内部 new，上层无法注入替代实现 —— 需要先在 fork 里开一个注入口；
3. **回归风险**：要动的是 fork 的 event loop 核心，该层是无锁 + 零拷贝设计，语义微妙。

#### MSG_ZEROCOPY 与 io_uring 的关系

`202609100759_2f96c69_读写性能测试报告.md:150` 把方向写成「io_uring + MSG_ZEROCOPY」，**这是两件可拆开的事**：

- **MSG_ZEROCOPY** 消的是发送路径的 skb 拷贝（上表第 3 行，io_uring 治不了的那块），**用普通 `sendmsg` + `SO_ZEROCOPY` 即可开启，不依赖 io_uring**；
- **io_uring** 治的是 syscall 开销与异步流水（上表第 1、2 行）。

**建议：两者都做，但不是同一件事。若判定实验指向 (B)，应先做 MSG_ZEROCOPY —— 它更可能直接抬高天花板。**

### 3.3 shm：io_uring 对它没有意义

这是本报告中最明确的否定结论，理由分三层：

**① 数据面根本没有可异步化的对象。**

shmipc 数据面是 **mmap 共享内存**，两端读写同一块内存，发布靠内存屏障 `Flush`：

- 读：`shm_frame.go:38` `shmReadFrame()` → `BufferReader().ReadBytes()` 直接从共享内存切片取帧（零拷贝引用）；
- 写：`shm_frame.go:67` `shmWriteFrame()` → `BufferWriter().Reserve()` 拿共享内存可写区 + `copy` + `Flush`。

**整个搬数据过程一个 syscall 都没有。** 而 io_uring 的本质是「把 syscall 变异步」——**没有 syscall，就没有可异步化的对象**。

**② 控制面不值得。**

socket 只出现在握手与 `SCM_RIGHTS` 传 memfd，量极小、频率极低，epoll 已完全够用。

**③ 唯一沾边的地方属于磁盘路径，不属于 shm 路径。**

`server_shm.go:524` `shmWriteDataFrameDirect()` → `storage.ReadAtInto(ctx, key, pos, want, buf[shmDataPad:...])` 把 O_DIRECT 一次 DMA 直接读进共享内存的 4K 对齐数据区（免 memcpy）。但这条调用链的终点是 **`internal/aio` 的 `Ring`** —— 它会**自动受益于 §3.1 的磁盘层改造**。这是「磁盘路径受益」，**不是「shm 通信受益」**。

**结论：shm 这条链路（零 syscall + 零拷贝）已是理论最优形态。在其上加 io_uring 是负收益** —— 只增加复杂度和维护面，不换来任何延迟或带宽改善。

## 4. 改造方案（以磁盘层为主）

### 4.1 落点：`Ring` 接口就是现成的接缝

`internal/aio/aio.go:47` 的 `Ring` 接口可以**原样复用**：

| `Ring` 方法 | io_uring 映射 |
|---|---|
| `SubmitReadBatch` | 填 SQ ring（多条 SQE，一次 `io_uring_enter`） |
| `SubmitWrite` | 同上，`IORING_OP_WRITE` |
| `Wait` | `io_uring_enter(GETEVENTS)` 读 CQ ring |
| 序号关联（`Event.Data`） | `sqe.user_data` |
| `Close` | munmap + close(fd) |

**接口不需要改** —— 这本身就说明当年这个抽象放对了位置。

需要注意的差异点：

- **并发生产者**：SQ ring 写入非线程安全，但现有 `r.mu` 已经串行化了提交路径，可直接沿用；
- **ring 尺寸**：SQ/CQ entries 必须为 2 的幂，与现在 `aioDepth = 256` 的语义要重新对齐；
- **`ErrFull` 语义**：必须保持「部分提交 `submitted < len(specs)`」的行为，与 `aio_linux.go:118` 一致；
- **`Close`**：需 munmap 三块映射 + close ring fd，比 `io_destroy` 复杂。

### 4.2 依赖现状：需手写结构体与常量

`golang.org/x/sys v0.30.0` **只有 `SYS_IO_URING_SETUP` 等 syscall 号，没有任何 `IORING_*` 常量或结构体**（已核实）。因此需要：

- 手工声明 `io_uring_params`、SQE/CQE 结构体与 `IORING_*` 常量；
- 全部走裸 syscall。

这与 `aio_linux.go:26-40` 手工声明 `iocb` 的做法一致，**符合项目「纯 Go、无 cgo」的既定风格**。

### 4.3 后端选择与注入

**选择点**：`internal/device/device.go:75` 的 `aio.New(aioDepth)`。

**调用链**：`cmd/taihu/cmd/server.go:137` → `pkg/taihu/storage.go:29 NewStorage` → `device.NewDevice`。

**约束**：`NewStorage` 有 **10+ 个调用点**（`bench_storage.go`、`rpccluster`、`rpcclient`、`taihu` 自身与各测试文件）。因此**必须用 variadic option**（如 `taihu.WithAIOMode(...)`）扩展，**不得改签名**，否则大范围破坏调用方。

### 4.4 OS / 内核识别：必须用探测，不能只比版本号

**版本比较不足够**，至少三类情况会被误判为"支持"：

| 情况 | 后果 |
|---|---|
| RHEL 9.4+ 用 `/proc/sys/kernel/io_uring_disabled` 对非特权用户禁用 | 内核版本够新，但 `io_uring_setup` 返回 `EPERM` |
| 容器 seccomp（Docker 默认 profile）拦截 io_uring 系统调用 | 返回 `EPERM` / `ENOSYS` |
| 发行版 backport 差异 | 版本号无法反映实际能力 |

**正确做法**：

1. **直接尝试 `io_uring_setup(2)`，按 errno 判定** —— 天然覆盖 seccomp / sysctl / backport 全部情况；
2. 成功后读 `io_uring_params.features` 取**能力位**（如 `IORING_FEAT_SINGLE_MMAP` 决定 mmap 需要几次），而非解析版本号；
3. `unix.Uname()` **仅用于**日志与给出人类可读原因（"内核 4.19 < 5.1"）；
4. 探测结果**缓存**，启动日志明确打出「使用哪个后端 + 为什么」。

**编译期**：现有 `//go:build linux` / `!linux` 拆分（`aio_linux.go` / `aio_other.go`）已处理平台差异；**内核版本只能运行期判定**。

**版本门槛建议**：以 **5.6** 为最低（非向量化 `IORING_OP_READ/WRITE` 与 socket `SEND/RECV` 在此引入）；若用 socket 快速轮询（`IORING_FEAT_FAST_POLL`）需 **5.7**。

### 4.5 命令行参数：三态，不是 bool

需求原文「增加参数（非必传参数），是否启动 io_uring，以命令行为准」推导出：

- **非必传** → 有默认值，缺省可运行；
- **以命令行为准** → 显式传入时命令行优先，未传时走自动探测。

因此参数应当是**三态**：

```
-io-uring=auto|on|off     # 默认 auto
```

**为什么不能用 bool**：`-io-uring=false` 无法区分「用户显式关闭」与「默认值」，会丢失"命令行优先"的语义。若坚持 bool，**必须**配合 `cmd.Flags().Changed("io-uring")` 判定。

**`on` 但内核不支持时**【已确认】：**启动直接失败并报明确错误**，不静默降级 —— 这才符合"以命令行为准"。`auto` 则正常探测并日志说明。

**命名与落点**：沿用现有 `-batch` / `-batch-workers` 风格 → `-io-uring`。

**挂载范围**【已确认：`server` + `bench` 都要】：压测命令（`bench storage/single/cluster`）同样创建 `Storage`（`bench_storage.go:104` 等），对比 libaio 与 io_uring 必须能切换。因需同时覆盖 server 与 bench，**倾向于挂在 `rootCmd.PersistentFlags()` 的 `global` 结构**（`cmd/taihu/cmd/root.go:22`）而非 `serverCmd.Flags()`。

### 4.6 落地顺序

| 阶段 | 内容 | 4.19 节点 | 5.10 节点 |
|---|---|---|---|
| **⓪** | **RPC 天花板归属判定实验**（§3.2，不写生产代码） | ✅ | ✅ |
| **①** | 探测框架 + `-io-uring` 三态开关 + 后端注入（option 打通 server/bench） | ✅ 走 libaio | ✅ |
| **②** | 磁盘层 io_uring 后端（`Ring` 实现 + 注册缓冲 + IOPOLL） | ❌ 回退 libaio | ✅ |
| **③** | MSG_ZEROCOPY（服务端发送路径，**不依赖 io_uring**） | ✅ | ✅ |
| **④** | TCP io_uring 化（需先给 netpoll fork 开 `Poll` 注入口 + 重做唤醒语义） | ❌ | ✅ |
| — | shm 的 io_uring 化 | **不做**（§3.3） | **不做** |

## 5. 风险与边界

| 风险 | 说明 | 缓解 |
|---|---|---|
| **RPC 收益可能不达预期** | 天花板若源于内核拷贝（§3.2 情形 B），io_uring **抬不动**它；且当前整机 idle 88.3%，CPU 并非瓶颈 | **阶段 ⓪ 判定实验先行**，数据说话再决定 ④ 是否继续 |
| **两种内核并存** | 4.19 走 libaio、5.10 走 io_uring，行为差异需同时维护 | 双后端共享 `Ring` 接口与完成泵；4.19 节点回归验证"能正常回退" |
| **改动面扩散** | `NewStorage` 签名若变更会波及 10+ 调用点 | **强制 variadic option**，不得改签名 |
| **netpoll fork 无注入口** | `Poll` 接口由 `poll_manager` 内部 new，上层无法注入 | 阶段 ④ 前先在 fork 内开注入口 |
| **唤醒语义** | shmipc dispatcher 无 eventfd，靠 1s 超时轮询 | 阶段 ④ 一并重做，避免忙等或延迟劣化 |
| **特权与容器限制** | SQPOLL 需特权；容器 seccomp 可能直接拦截 `io_uring_setup` | **探测式判定**（按 errno）；SQPOLL/IOPOLL 设计为可选增强而非必需 |
| **IOPOLL 占核** | 轮询方式独占 CPU 空转 | 96 核富余下可行，但需实测确认净收益为正 |
| **版本门槛与能力位不一** | 5.6 引入 `READ/WRITE`，5.7 才有 `FAST_POLL` | 用 `features` **能力位**判定，不硬编码版本号 |

## 7. 第一步（磁盘层）落地与真机验收结果

**日期**：2026-09-14　**范围**：仅磁盘层（TCP / shm 未动，见 §4.6）

> ⚠️ **本节 7.2 的验收机 192.168.210.180 是内核 5.10 的虚拟机，只能用于功能测试，不能用于性能测试**（其磁盘为半虚拟化盘，见 §7.5）。因此 **§7.5 的性能数字仅为「当时观测到的现象」记录，不构成任何性能依据**，不得用于选型、默认值决策或对外引用。需要性能数据请另找物理机 / NVMe 机器。

### 7.1 落地内容

| 文件 | 说明 |

`Ring` 接口未改动；`aio.New()` 仍固定 libaio，生产路径（`device` → `NewStorage`）默认 `auto`。

### 7.2 验收环境（重要前提）

验收机 `192.168.210.180`：**openEuler 22.03 SP4，内核 5.10.0-216**，`CONFIG_IO_URING=y`，6 核。

该内核的 io_uring **不是 5.10 主线版本，而是约 5.13 的 backport**：

```
features = 0x7ff   （含 EXT_ARG 1<<8、NATIVE_WORKERS 1<<9、RSRC_TAGS 1<<10）
kernel 回填的 sq_off：head=0 tail=64 ring_mask=256 ring_entries=264 flags=276 dropped=272 array=576
kernel 回填的 cq_off：head=128 tail=192 ring_mask=260 ring_entries=268 overflow=284 cqes=320
```

两点后果，都已在实现中体现：

1. **ring 布局是缓存行填充过的，与 5.10 主线不同** —— 这印证了「必须用内核回填的偏移，不能照抄某版 UAPI 硬编码」；本实现所有指针都从内核给的偏移派生。
2. **`sq_off.*` / `cq_off.*` 里每个字段都是「字节偏移」，不是字段取值**（`sq_off.ring_mask = 256` 是掩码所在偏移，掩码本身是 7）。首版实现把偏移当值比较，导致在真机上**全部 6 个契约测试的 io_uring 分支直接失败**；已改为「偏移 + 宽度落在段内」+「按偏移读出掩码/条目数并与 `entries` 自洽」两级校验。这个 bug 在 macOS 上完全测不出来（非 Linux 走 `!linux` 分支），只能靠真机验收发现。

> 该内核 `IORING_FEAT_EXT_ARG` 已置位（即 `io_uring_enter` 支持带超时）。本实现仍用 `poll(ring fd)` 做超时，因为要兼容无 EXT_ARG 的 5.10 主线；这是有意的可移植取舍。

### 7.3 功能验收：通过

契约测试（`Test{...}` 各跑 libaio 与 io_uring 两个后端）在真机全绿：

| 项 | 结果 |
|---|---|
| `TestRoundTrip` / `TestMultipleInflight` / `TestReadBeyondEOF` | 双后端 PASS |
| `TestWaitTimeout`（零超时）/ `TestWaitTimeoutExpires` | 双后端 PASS |
| `TestRoundTripODirect`（ext4，非 tmpfs） | 双后端 PASS |
| 重复 20 轮 | 无 flake |
| 强制 `checkptr=2` | PASS（验证「不用 `base+uintptr(off)` 做指针运算」这条约束成立） |
| CLI 后端选择 | `-io-uring=off` → `backend=libaio (forced off)`；`auto` → `backend=io_uring sq=256 cq=512`；`bogus` → 报错拒绝 |
| 跨编译 | linux/amd64、linux/arm64、darwin 均 clean，`go vet` clean |

### 7.4 IOPOLL：本机**无法验证**，保持默认关

验收机三块盘（`sdb`/`sdc`/`sdd`）均 `rotational=1`，且**没有 NVMe**。`io_poll` 写 1 直接 `EINVAL`：

```
sdb: before=0 after=0 err=write error: Invalid argument
```

即该硬件不支持块层轮询，IOPOLL 无法在此评测。前置校验按设计**硬失败并给出开启命令**，而不是让请求停在 `iopoll_list` 上挂死：

```
aio: IOPOLL 需要 /sys/class/block/sdb/queue/io_poll 为 1（当前为 "0"），
     请先执行: echo 1 > /sys/class/block/sdb/queue/io_poll
```

**结论**：IOPOLL 保留开关、默认关，待 NVMe 机器实测后再决定是否默认开或永久关闭。

### 7.5 性能对比（**现象记录，不可作为性能依据**）：本机上 io_uring 不快，写还更慢 —— 差距来自提交路径争用

> 验收机是虚机、盘是半虚拟化盘，**本节数字不能用于任何性能判断**（见本节开头警告与本节末的说明）。保留本节只因为它是「提交路径存在争用」这一**实现层面**结论的证据链 —— 该结论由「threads=1 时差距消失」这一相对比较得出，不依赖盘有多快；但**14% 这个幅度是硬件相关的，同样不可引用**。

`taihu bench storage`，4 MiB 对象 × 512（2 GiB），每轮之间 `wipefs` 重置 `/dev/sdb`，每后端 5 轮：

| 后端 | write (MiB/s) | read (MiB/s) |
|---|---|---|
| libaio（`-io-uring=off`） | min 3765 / **med 3914** / max 4127 | min 9608 / **med 11481** / max 12375 |
| io_uring（`auto`） | min 3287 / **med 3382** / max 3693 | min 6288 / **med 9879** / max 11442 |

写路径 5 轮区间**不重叠**，io_uring 稳定慢约 14%。

**定位实验**：把线程数拉开，看差距是否随并发变化：

| threads | libaio (med) | io_uring (med) | 差距 |
|---|---|---|---|
| 1 | 2221 | 2234 | **≈0%（区间重叠）** |
| 8 | 3914 | 3382 | ~14% |
| 32 | 3611 | 3421 | ~5% |

**线程数=1 时差距消失，随并发增大而出现** → 这是**实现层面的提交路径争用**，不是 io_uring 的固有代价：当前 `submit` 在 `r.mu` 内填 SQE **并持有锁调用 `io_uring_enter`**，N 个线程因此在「锁 + 系统调用」上完全串行化。libaio 侧的临界区更窄。

**后续优化项（本步未做）**：把 `enter` 移出锁（锁内只填 SQE 并发布 `sq_tail`，锁外 `enter` 踢一次），需要重新设计「部分提交的条数归属」——单环多提交者时，消费条数是全局的，无法直接归到某个调用方。备选是每线程一个 ring。

**另需注意**：该机 `sdb` 读达 11 GiB/s，与 `rotational=1` 严重不符，实为**半虚拟化盘**。因此上述绝对值既不代表生产 NVMe，也不足以体现 io_uring 的典型优势场景（高 IOPS、低队列深度）。**不要据这张表决定生产默认值**；`auto` 作为默认是依据需求（「支持就用」）而非依据性能收益。
