# 88b315e 读路径零拷贝优化验证报告（对比 468a9af 基线）

> 对应提交：`88b315e`（P0-P3 四级零拷贝优化）+ `991e25c`（server 传输缓冲 32KB→1MiB）
> 测试时间：2026-09-10
> 基线版本：`468a9af`（详见 `468a9af RPC端到端读写性能全量测试报告.md`）

## 1. 优化内容

| 级别 | 变更 | 目的 |
|------|------|------|
| P0 | 数据帧 256KB → 1MiB；流控窗口 InitialWindow 4MB / ConnWindow 64MB | 降低帧数与 RTT 开销 |
| P1 | rpcclient.Get 去 io.Pipe，单槽握手 reader（条件变量背压） | 读路径少一次拷贝 |
| P2 | 自定义 RawCodec 数据帧裸字节零拷贝透传（server/client 同步升级） | 去掉 proto.Marshal/Unmarshal 整块 memmove |
| P3 | Device.ReadAt / Storage.ReadAt 直读调用方缓冲，server Get 直读直发 | 消除 Storage 层多余搬运与系统调用 |
| P4 | server WriteBufferSize/ReadBufferSize 32KB → 1MiB | 削减 socket write syscall 次数 |

## 2. 测试环境（与基线一致）

- 100.71.128.12 单机，client/server 同机走 lo 回环，96 核 aarch64，`/dev/nvme1n1`（1.8T O_DIRECT），`/tmp/tdb-rpc`（pebble）
- 压测：16 个独立 `taihu-rpc-bench`（各 16 线程 = 256 并发流），4MiB 对象 × 1500/客户端，读同一 `rbench/1-1500` 区域（6GB）

## 3. 优化效果对比

## 4. 带宽瓶颈再定位

优化后 server CPU（29→7.4 核）与 client CPU（2.5→0.9 核）均大幅下降，但 16 客户端读带宽持平 5.35G，说明 **带宽不再受 RPC 层 CPU 限制**。为定位新瓶颈做本地直读对照（不经 gRPC，O_DIRECT）：

| 访问模式 | 带宽 | 说明 |
|----------|------|------|
| 本地 16 线程直读同区域 | **6449 MiB/s（6.3G）** | 低并发，磁盘能力充足 |
| 本地 256 线程直读同区域 | **5414 MiB/s（5.29G）** | 与 RPC 16 客户端（256 流）一致 |
| RPC 16 客户端读 | 5352 MiB/s（5.35G） | ≈ 磁盘 256 并发模式极限 |

**结论：磁盘在同一 6GB 热区上的高并发（256 并发 IO）访问模式极限为 ~5.4 GiB/s**，RPC 端到端带宽已打满该极限（本地 256 线程直读也只有 5.29G）。磁盘 iostat 实测 avg ≈ 5.4G 佐证。继续提升读带宽需改变访问模式（更大 IO、分散区域、或减少同区并发），而非 RPC 层优化。

## 5. 结论

1. **零拷贝优化达成目标**：消除 server 侧 proto.Marshal 编码拷贝与 Storage 层搬运后，server CPU 从 29 核降至 7.4 核（-74%），client 从 2.5 核降至 0.9 核（-64%）；单客户端读写分别 +4.9% / +9.3%。
2. **16 客户端读带宽 5.36G → 5.35G 持平**：基线已触及磁盘 256 并发访问模式极限（~5.4G），带宽提升空间在磁盘访问模式而非 RPC 层。
3. **新瓶颈**：磁盘高并发同热区读极限；当前 RPC 层 CPU 余量充足（server 仅 7.4/96 核）。
4. wire 格式不兼容旧版（RawCodec），server/client 须同步升级。
