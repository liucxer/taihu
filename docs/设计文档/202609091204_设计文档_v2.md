# Object Storage on Raw NVMe + RocksDB — 设计文档 v2

## 1. 概述

对外提供 key 粒度的 object 读写接口。数据写在一块裸 NVMe 上，key 与存放位置的映射保存在 RocksDB，并在启动时加载进内存永久缓存。

接口签名沿用 v1：

```go
// 外部接口（Storage 层）
func NewStorage(ctx context.Context, rocksdbDir, nvmePath string) *Storage
func (s *Storage) Get(ctx context.Context, key string, off, size int64) (io.ReadCloser, error)
func (s *Storage) Put(ctx context.Context, key string, size int64, in io.Reader) error
func (s *Storage) Delete(ctx context.Context, key string) error
func (s *Storage) LoadCache(ctx context.Context) error // 预热缓存：全量扫描 mapping 载入内存缓存

// 底层接口（Device 层）
func NewDevice(ctx context.Context, nvmePath string) *Device
func (d *Device) append(ctx context.Context, segmentID int64, off int64, size int64, data io.Reader) error
func (d *Device) read(ctx context.Context, segmentID int64, off int64, size int64) io.Reader
func (d *Device) delete(ctx context.Context, segmentID int64) error
```

## 2. 物理布局

- 16TB 裸设备划分为 2048 个 segment，每个 8GB。
- segment i 的物理区间：`[ i*8GB, (i+1)*8GB )`。
- 单个 segment 内合法 offset：`0 ~ 8GB-1`。
  - > 修正：v1 中「offset 0~67485760」为笔误，改为 0~8GB。
- 所有写入 offset / 长度均需 4K 对齐。

每个 segment 首地址 = `i*8GB`，是 4K 整数倍，天然对齐；段内再做 4K 对齐即可。

## 3. 约束（沿用 v1，已确认）

- 单个 object 必须完整落在一个 segment 内，**不允许跨段**（上限 8GB）。
- 顺序写入：先用第 1 个 segment，写满后切第 2 个，以此类推。

## 4. Model 层（存储 / 内存）定义

> Model 层 = RocksDB 中的具体键 + 各自含义 + 值的结构体编码。所有 KV 用 **Column Family** 隔离命名空间，值用二进制 little-endian 固定字段编码（保证紧凑与可寻址）。

### 4.1 RocksDB Column Family 一览

| Column Family | Key | Key 编码 | Value 结构体 |
|---------------|-----|----------|--------------|
| `mapping` | `userKey`（原始字节） | 用户 key 原样 | `ObjectMeta` |
| `state`   | `"cursor"` | 固定字符串 | `WriteCursor` |
| `state`   | `seg/<segmentID>` | `"seg/" + int64 LE` | `SegmentMeta` |

### 4.2 Value 结构体定义

```go
// ColumnFamily: mapping
// key = 用户 key；value = object 存放位置 + 大小
type ObjectMeta struct {
    SegmentID int64 // 所在 segment，>=0
    Offset    int64 // object 在 segment 内的起始偏移，恒 4K 对齐
    Size      int64 // object 逻辑大小（原始字节数，不含 4K 填充）
}

// ColumnFamily: state, key = "cursor"
// 全局唯一写游标（persist，支持重启续写）
type WriteCursor struct {
    SegmentID int64 // 下一个写入的 segment
    Offset    int64 // segment 内下一个写入偏移，4K 对齐
}

// ColumnFamily: state, key = "seg/<segmentID>"
// 每个 segment 的状态机 + 存活计数（用于 GC / 空闲段池）
type SegmentMeta struct {
    State      uint8 // 见 SegmentState
    AliveCount int64 // 该 segment 中仍被引用的 object 数
    ReclaimSeq int64 // 回收代数（预留）
}

type SegmentState uint8

const (
    SegmentStateFree     SegmentState = iota // 空闲，可分配
    SegmentStateActive                       // 正在顺序写入
    SegmentStateFull                         // 已写满，仅读
    SegmentStateReclaiming                   // 待回收
)
```

### 4.3 Key 语义说明

- **`mapping / <userKey>`**：核心映射。`Put` 时写入、`Delete` 时删除。上层通过该值与内存缓存（§5）定位 object 的物理位置与大小。
- **`state / cursor`**：全局顺序写游标。记录下一个 object 的落点。只有「换 segment」时才落盘，段内推进不必每次写盘（可容忍重启后少量对齐浪费）。
- **`state / seg/<id>`**：segment 生命周期状态。用于：启动时初始化 2048 个 segment 的 `SegmentMeta`、判断是否有空闲段、以及 Delete 后递减 `AliveCount` 判断整段可回收。

### 4.4 序列化

所有结构体用固定字段 binary LE 编码（int64 占 8 字节），不采用 gob/protobuf，保证可直接按 offset 解析、便于与 C 层 RocksDB 共用。为便于版本演进，每个 value 头部可预留 `version uint8`（v1 设为 0）。

## 5. 内存缓存（有界 LRU，上限 1GB）

> v2 变更：v1 的「永久缓存全部映射直到退出」在 4K 对象场景下需要数百 GB RAM（见容量评估），改为**有界 LRU + 字节级预算**。RocksDB 仍为真实源，缓存为 read-through 加速层。

### 5.1 语义

- 缓存 `key → ObjectMeta`（值固定 24B）。
- 命中读 / 写 upsert → 移到 MRU 端；超预算 → 从 LRU 端淘汰。
- 未命中 → 回查 `mapping` CF，读回后插入（read-through）。
- 启动时**不自动预加载全量**（会打爆上限），仅在显式调用 `LoadCache` 时按需预热。

### 5.1.1 缓存预热 LoadCache

> 用途：bench 或已知 key 集合场景，把元数据全部载入内存，使后续 Get 命中缓存、
> 不再读 pebble，从而**把元数据读从被测读写带宽中剔除**。

```go
func (s *Storage) LoadCache(ctx context.Context) error {
    return s.db.IterMapping(ctx, func(key string, m ObjectMeta) error {
        s.cache.put(key, m) // 受同一 LRU 预算约束，超 1GB 自动逐出
        return nil
    })
}
```

- 全量扫描 `mapping` 命名空间，逐条 `cache.put`，复用现有 LRU 预算：条目超过 1GB 时正常逐出（不会内存失控）。
- Get 因 read-through 语义，正常路径下即使不预热也能正确读取；`LoadCache` 只是**消除元数据未命中回查**的一次性开销，用于测纯设备带宽。

### 5.2 容量模型

```
perEntryCost(key) = len(key) + overhead   // overhead ≈ 92B（key 头 16 + value 24 + map/节点 ~52）
usedBytes = Σ perEntryCost(所有在缓存条目)
```

| key 长 | 单条成本 | 1GB 预算可缓存 |
|---|---|---|
| 16B | ~108B | ~1,000 万条 |
| 32B | ~124B | ~860 万条 |

### 5.3 结构 & 方法（无锁分片）

> v3 变更：去掉单一全局锁，改为 **N 个分片（shard）**。每个 shard 独立一把锁 + 本地 LRU + 本地字节预算，读写只锁命中 shard，并发提升 N 倍。精确 LRU / 精确 1GB 上限退化为**分片级近似**。

```go
const (
    ShardCount      = 256           // 分片数，可按 CPU/并发规模调整（2 的幂）
    MaxCacheBytes   = 1 << 30       // 全局预算 1GB
    perShardLimit   = MaxCacheBytes / ShardCount // ≈4MB/分片
    PerEntryOverhead = 92           // 估算，可在 runtime 校准
)

type shard struct {
    mu        sync.Mutex
    entries   map[string]*list.Element // O(1) 命中；key 存于 entry，复用字节数组
    ll        *list.List               // 本地 LRU：Front=MRU, Back=LRU
    usedBytes int64
}

type metaCache struct {
    shards [ShardCount]shard
}

// 哈希寻片：无锁阶段（定址），随后仅在命中 shard 上加锁
func (c *metaCache) shardFor(key string) *shard {
    h := fnv64a(key) % ShardCount
    return &c.shards[h]
}

func (c *metaCache) get(key string) (ObjectMeta, bool) {
    s := c.shardFor(key)
    s.mu.Lock(); defer s.mu.Unlock()
    if e, ok := s.entries[key]; ok {
        s.ll.MoveToFront(e)
        return e.Value.(*cacheEntry).meta, true
    }
    return ObjectMeta{}, false
}

func (c *metaCache) put(key string, meta ObjectMeta) {
    s := c.shardFor(key)
    s.mu.Lock(); defer s.mu.Unlock()
    if e, ok := s.entries[key]; ok {
        e.Value.(*cacheEntry).meta = meta
        s.ll.MoveToFront(e)
        return
    }
    s.ll.PushFront(&cacheEntry{key: key, meta: meta})
    s.usedBytes += int64(len(key)) + PerEntryOverhead
    s.evictLocked()
}

func (c *metaCache) del(key string) {
    s := c.shardFor(key)
    s.mu.Lock(); defer s.mu.Unlock()
    if e, ok := s.entries[key]; ok {
        s.ll.Remove(e)
        delete(s.entries, key)
        s.usedBytes -= int64(len(key)) + PerEntryOverhead
    }
}

// evictLocked：分片内逐出，直到该分片重新 ≤ perShardLimit
func (s *shard) evictLocked() {
    for s.usedBytes > perShardLimit && s.ll.Len() > 0 {
        back := s.ll.Back()
        entry := back.Value.(*cacheEntry)
        s.ll.Remove(back)
        delete(s.entries, entry.key)
        s.usedBytes -= int64(len(entry.key)) + PerEntryOverhead
    }
}
```

**容量保证**：每个分片硬上限 `4MB`，256 分片合计 ≤ 1GB。最坏情况下总额最多超出「每分片单条最大成本」×分片数，属可接受软上限。

**并发模型**：
- 哈希定址 `fnv64a(key)%N` **无锁**；实际读写只锁映射目标 shard。
- 不同 key 分落不同 shard → 读完全并行，提升至 ~N 线程粒度。
- 单一热点 key 仍串行（被其 shard 锁保护），这是无锁化不可避免的最小串行点。

### 5.4 读写路径接入

```go
// Get：命中即用；未命中回查 RocksDB，读回后插入
meta, ok := s.cache.get(key)
if !ok {
    meta, err = s.db.GetMapping(key) // 读 mapping CF
    if err != nil { return err }
    s.cache.put(key, meta)
}

// Put：写设备 + 游标推进后，write-through 更新缓存
s.cache.put(key, meta)

// Delete：删 RocksDB 映射并移出缓存
s.cache.del(key)
```

### 5.5 说明与一致性

- 访问不改变 `usedBytes`（LRU 仅是移动链表节点），成本只在插入/淘汰/删除时变化。
- 并发：锁粒度收敛到单个 shard（分片锁），与全局写游标锁完全解耦；读写互不相扰，跨 shard 并行。
- 一致性：Write-through；缓存任何时刻都可由 RocksDB 重建，淘汰/崩溃不丢持久性。
- 近似性：LRU 与 1GB 上限为分片级近似（每分片 ≤4MB）。对 `key→meta` 冷热明显的场景命中率损耗可忽略。
- 与 RocksDB 自身 block cache 是两层：本缓存按用户 key 索引，RocksDB block cache 面向底层 block。

## 6. 主要流程

### Put(key, size, in)
1. 由入参得到 `size`，计算 `alignedLen = align4k(size)`（无需预读 `in`）。
2. 若 `currentOff + alignedLen > 8GB`：推进 `currentSegmentID++`，`currentOff = 0`，持久化游标；若 `size > 8GB` 或无空闲 segment 则报错。
3. `device.append(currentSegmentID, currentOff, size, data)`，末尾填 0 补齐到 4K，返回实际写入 `alignedLen`。
4. 写入 RocksDB 映射（`meta.Size = size`）并更新缓存。
5. `currentOff += alignedLen`，持久化游标。

> 顺序保证：先写设备数据，再写 RocksDB 元数据，避免出现「有映射无数据」。
> `size` 由调用方对对象长度负责；`in` 读到少于 `size` 字节视为写入错误。

### Get(key, off, size)
1. 查缓存得 `meta`。
2. 校验 `off`、`size`，`size` 截断到 `meta.Size - off`。
3. `device.read(meta.SegmentID, meta.Offset + off, size)` 返回。
   - 读响应 byte 级偏移，无需 4K 对齐。

### Delete(key)
1. 删除 RocksDB 中映射，并从缓存移除。
2. 物理空间不立即回收（append-only），由 segment 级回收处理：所有映射失效的 segment 标记为可回收，整体归还空闲段池。

## 7. 并发

- 所有 Put 的「分配游标 + 写设备 + 写元数据」用一把锁串行化，保证游标单调、互不覆盖。
- Get 走随机读，可并行。
- 设备层按多文件句柄 / `ReaderAt` 支持并发读（区别于单 O_APPEND 写句柄）。

## 8. 边界情况

- object > 8GB → Put 报错。
- 剩余空间不足 → 换 segment；无空闲段 → ErrNoSpace。
- 非 4K 倍数写入 → 填充对齐。
- key 不存在 → Get/Delete 返回 NotFound。
- 重复 Put 同一 key → 视为覆盖，旧数据变孤儿交 GC。

## 9. Bench 性能测试工具

独立的命令行工具，用于压测 Storage（底层裸设备 O_DIRECT + pebble 元数据）。支持两种模式：顺序写、随机读。

### 9.1 参数

| 参数 | 说明 | 默认 |
|------|------|------|
| `-mode` | `write` \| `read` | 必填 |
| `-size` | 每个 object 的大小（字节，任意整数） | 4096 |
| `-threads` | 并发 goroutine 数 | 1 |
| `-count` | 参与测的 object 总数（write 时写入数量；read 时预生成读取的 key 数） | 1000 |
| `-keys-prefix` | 生成 key 的前缀（`<prefix>/<seq>`） | `bench` |
| `-db` | pebble 元数据目录 | 必填 |
| `-dev` | 裸设备路径 | 必填 |
| `-report-interval` | 进度打印间隔（秒） | 2 |

命令示例：

```bash
# 顺序写：4 线程，各写入 count/threads 个 64KB object
taihu bench storage -mode write -size 65536 -threads 4 -count 10000 -db /data/meta -dev /dev/nvme0n1

# 随机读：8 线程，读取 count 个互不重复的 key（整对象读，size 4K 对齐）
taihu bench storage -mode read -size 65536 -threads 8 -count 10000 -db /data/meta -dev /dev/nvme0n1
```

> `write` 与 `read` 用相同的 `-keys-prefix` 描述同一批 key：先 write 造数据，再 read 测读。

### 9.2 Key 集合与"读不重复"保证

- **Key 生成**：预置 n = `-count` 个互不相同的 key，形如 `<prefix>/<0..n-1>`。
- **写模式**：把 n 个 key 按线程均分为不相交的段，线程 i 只写自己的区间。Put 在 Storage 层由全局写游标锁串行化，故并发写实际串行，`threads` 决定的是**键分派方式**（用于对比单线程与多上下文的开销）。
- **读模式（关键）**：同样把 n 个 key 按线程切成不相交区间；线程 i 读取 `[start(i), end(i))` 内的 key。由于区间互不相交，**整个进程内每个 key 恰好只被读取一次，无任何重复**——避免缓存命中与重复 IO 污染读吞吐，测的是纯底设备随机读带宽。
  - `read` 不需要先写：它只认 key 集合，读取前由调用方先用 `write` 模式灌好数据。
  - **预热缓存**：创建 `Storage` 后先调 `LoadCache`（见 §5.1.1），把元数据载入内存，Get 全程命中缓存、不碰 pebble，确保测得的是纯底设备读带宽。
- **读长度**：整对象读，`off=0, size=<size>`。bench 面向 **Storage 层**而非 device 层，Storage 层处理 4K 对齐细节，因此 `-size` 为任意整数，无对齐约束。

### 9.3 指标收集

- **Write**：总对象数、总字节、总耗时、吞吐（`MiB/s`、`ops/s`）。
- **Read**：按 key 判重的实际 IO 字节（`n × size`，排除任何重复读）、总时长、吞吐（`MiB/s`、`ops/s`）、每请求耗时 P50/P90/P99（分位统计）。
- 均输出 `threads` / `size` 以便横向对比。

### 9.4 实现要点

```go
// 生成 n 个互不相同 key（写与读共用同一生成规则，保证可对齐）
func benchKeys(prefix string, n int) []string

// 读模式：把 [0,n) 切成 threads 个不相交区间，保证全进程每个 key 只读一次
ranges := partitionRanges(n, threads) // [[s0,e0), [s1,e1), ...]
for i := 0; i < threads; i++ {
    go func(s, e int) {
        for k := s; k < e; k++ {
            rc := s.Get(ctx, keys[k], 0, size) // Storage 层读整对象，size 任意整数（对齐由 Storage 内部处理）
            io.Copy(io.Discard, rc); rc.Close()
        }
    }(ranges[i][0], ranges[i][1])
}
```

- 读路径直接对设备做 O_DIRECT 随机读，不写 pebble；写路径依赖 Storage.Put。
- 分位统计用 p50/p90/p99 直方图（固定桶）或近似分位，避免海量样本存内存。

### 9.5 注意事项

- 本工具是**内部压测**工具，不在公共 API 面；可编译为独立 `cmd/taihu bench storage` 二进制。
- 面向 Storage 层接口（`Storage.Get/Put`），对齐细节由 Storage 内部处理，参数不含 offset/对齐概念。
- `-size` 建议 ≥64KB 时读吞吐才贴近设备上限；小 size 测的是 IOPS 与 syscall 开销。
- 运行 `read` 前必须先用相同前缀 `write` 灌好数据，否则读到 NotFound 计入失败。
