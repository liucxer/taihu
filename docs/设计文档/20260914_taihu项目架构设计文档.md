# taihu 项目架构设计文档

> 版本：v1（2026-09-14）
> 定位：基于 [README](../../README.md) 与源码梳理的**项目级架构设计文档**，覆盖分层架构、核心组件、接口约定与读写路径。
> 演进历史：单机对象库（v1/v2）→ 远程访问层（v3，netpoll 取代 gRPC）→ 共享内存 IPC → 多节点集群。本文描述当前实现（即 v2 存储核心 + v3 远程访问层 + shmipc + TiKV 集群）的总体架构。

---

## 1. 概述

`taihu` 是一个面向裸盘（NVMe）的高性能**对象存储引擎**：

- **数据模型**：对象（object）= `key → 任意字节序列`，单对象上限 = 段大小（8 GiB），key 不可变（无覆盖写，更新语义 = Delete 后重建）。
- **唯一对外 SDK**：业务访问必须走集群模式——`pkg/taihu-client`（TiKV 承担注册/路由/索引）是唯一外部接口；直连客户端 `internal/rpcclient` 仅供服务端/命令行内部使用。服务端与存储引擎（`internal/storage`，数据直落本机裸盘）同样在 `internal/` 下，不对外暴露。
- **性能取向**：O_DIRECT 裸盘直写直读 + libaio 异步 IO + 全程零拷贝（bufpool 对齐缓冲、netpoll LinkBuffer、shmipc 共享内存），追求端到端读写带宽。

## 2. 设计目标与原则

| 目标 | 落实方式 |
|------|----------|
| 高读写带宽 | O_DIRECT 直通页缓存；异步批 IO 摊薄系统调用；零拷贝避免 memcpy/堆分配 |
| 低 GC 压力 | 4K 对齐 bufpool（自管理 freelist），热路径零分配、零清零 |
| 元数据高性能 | Pebble 持久化 + 有界 LRU 分片缓存（read-through，可随时重建） |
| 空间可回收 | append-only 写入 + segment 级 GC + 后台 Compaction 搬移 |
| 同机/跨节点统一接口 | `ObjectStore` 接口 + `rpcConn` 抽象，调用方无感切换直连/集群（各自再选 TCP/shm） |
| 少依赖、可移植 | netpoll / shmipc-go fork 落地 `third_party`（避免模块环）；go.mod `replace` 指向本地 |

## 3. 总体架构

### 3.1 分层视图

```
┌────────────────────────────── 应用 / SDK 层 ──────────────────────────────┐
│  taihu CLI（cobra 子命令树）      pkg/taihu-client（唯一对外 SDK）      │
│  bench storage｜single｜cluster   集群模式（经 TiKV 路由）              │
└───────────────┬──────────────────────────────┬──────────────────────────┘
                │ 同机: shmipc 共享内存           │ 跨节点: netpoll 自定义帧协议
                ▼                              ▼
        ┌───────────────  taihu server（internal/transport）  │
        │    Put / Get / Delete / Stat + admin RPC（Ping/Meta/Segments/Keys）│
        └──────────────────────────────┬──────────────────────────┬───────┘
                                       ▼                          ▼
        ┌──────────── 存储核心（internal/storage.Storage）──────┐
        │  ├── metastore: Pebble 双命名空间 + 1GiB LRU 分片缓存 │ ←─ TiKV 注册区数据（集群写路径）
        │  │     ├── 游标分配 AllocateSegment（锁仅覆盖分配）   │
        │  │     ├── segment 状态机（GC/复用）                  │
        │  │     └── 段读引用计数 Ref/Unref                    │
        │  ├── device: O_DIRECT + libaio（internal/aio）        │
        │  ├── bufpool: 4K 对齐分桶缓冲池                       │
        │  └── compactor: 后台段压缩（预留缓冲段搬移）          │
        └───────────────────────────────────────────────────────┘
                                          │ O_DIRECT
                                          ▼
                                    NVMe 裸盘（8 GiB / 段）
```

### 3.2 模块依赖

```
cmd/taihu ──► pkg/taihu-client ──► internal/rpcclient ──► internal/transport ──► internal/storage
                  │                                   ├─ third_party/netpoll（fork）
                  ├─► internal/cluster（TiKV KV 抽象） └─ third_party/shmipc-go（fork）
                  └─► internal/storage ──► internal/metastore ──► pebble
                                     internal/device ──► internal/aio / internal/bufpool / internal/layout
```

关键依赖关系：

- `layout`（段大小、4K 对齐）为 `device`、`metastore` 共用，独立成包避免循环依赖。
- `ierr` 定义库错误，是**唯一事实源**；面向客户端的 re-export 只在 `internal/rpcclient`（`pkg/taihu-client` 转指一层），`internal/` 下不得自建错误别名层；`transport` 将错误码与库错误双向映射。
- **分层不变量**：`internal/**` 不得 import `pkg/**`（今日 0 处），`pkg/**` 不得直接依赖存储引擎（库代码；测试除外）。由 `make check` 的 `check-layering` / `check-sdk-only` 守着。
- 网络库 fork（netpoll/shmipc-go）**不 import 本项目**，经 `replace` 指向 `third_party/`，杜绝模块环。

### 3.3 关键全局约定

| 约定 | 值 | 说明 |
|------|----|------|
| 段大小 | 8 GiB（`layout.DefaultSegmentSizeBytes`） | 内置写死，命令行不允许覆盖 |
| 段数 | `容量 / 段大小`（向下取整） | 启动时读真实设备容量经 `ComputeLayout` 计算 |
| 对齐粒度 | 4 KiB（`layout.BlockSize`） | O_DIRECT 读写缓冲/偏移/长度均需 4K 对齐 |
| RPC 端口 | [50000, 51000] 自动抢占 | 多个监听 IP 共用同一端口 |
| pprof | 0.0.0.0，同区间自动分配（与 RPC 互斥） | 附带 5s 一次链路尺寸统计日志 |
| shmipc socket | `/dev/<server-name>` | 默认开启，与 TCP 监听并行 |
| 帧负载上限 | 4 MiB | 传输层单数据帧负载（历史 gRPC 同款上限） |
| 数据块 | 4 MiB 整块 | 磁盘 IO 与帧对齐，压测按 4MiB 整块统计 |

## 4. 数据模型

### 4.1 对象与映射

对象持久化为两级索引：

```
key（用户） ──GetMapping──► ObjectMeta{ SegmentID, Offset, Size }
                              │
                              └──设备物理位置：segmentBase(seg) + Offset，段内恒 4K 对齐
```

- `ObjectMeta`：段号 + 段内偏移 + 逻辑大小。对象不可跨段（单对象 ≤ 段大小）。
- 段内偏移 4K 对齐、单调不重叠（写入由分配器保证），段满自动滚动到下一段。

### 4.2 段与状态机

`SegmentMeta{ State, AliveCount, ReclaimSeq }`：

```
        AllocateSegment                    游标写出段尾
 Free ───────────► Active ────────────────────► Full
  ▲    （分配器选中写入）                  （不可再写入）
  │                                              │ MarkCompacting（搬移中）
  │ GC 确认无在途读者                      Compacting ◄─┘
  │                                              │ 对象搬空
 Reclaiming ◄────────────────────────────────────┘  AliveCount 归零
 （对象删光，可回收）
```

| 状态 | 含义 | 分配器可见性 |
|------|------|--------------|
| Free | 空闲，在空闲池 FIFO | 游标到顶时可复用 |
| Active | 正在顺序写入 | 当前游标段 |
| Full | 写满，不可写 | 不可选 |
| Compacting | 后台搬移中 | 不可选（避免写入与搬移同段） |
| Reclaiming | 对象已删光，等回收 | 不可选 |

关键机制：

- **存活计数 AliveCount**：每段现存对象数，与 mapping 写入同一 pebble WriteBatch 原子持久化；启动时**全量扫描 mapping 重建**（权威基准）。
- **读引用计数 refCount**：读开始 `RefSegment`、结束 `UnrefSegment`；仅在 refCount==0 时允许 Reclaiming → Free，防止「回收复用→迟到读读错数据」。
- **重启恢复**：Compacting 段 AliveCount>0 → 回 Full（恢复压测）；AliveCount==0 → Reclaiming。

### 4.3 元数据命名空间（Pebble）

Pebble 中两个逻辑命名空间（key 前缀隔离）：

| 命名空间 | 前缀 | 内容 |
|----------|------|------|
| mapping | `m00<key>` | key → ObjectMeta（对象落盘位置） |
| state | `s00<inner>` | `cursor`（写游标 seg/off）、`seg/<id>`（段状态） |

写入策略：mapping 与 cursor 变更 `Sync: true`（持久化）；mapping/state 写入与段计数变更在**同一 WriteBatch** 内原子提交。

## 5. 存储核心

### 5.1 device 层（internal/device）

**职责**：直接操作裸设备文件，按段提供 append/read；单文件描述符同时供读写。

- Linux：`O_DIRECT` 打开（绕过页缓存）；其他平台普通打开（见 §13）。
- **Append 对齐快路径**：数据首地址 4K 对齐时，4K 主体 `AsyncWrite` 直接直写调用方缓冲（零拷贝），仅不足 4K 的尾块用 4K 对齐临时缓冲补零写出（≤2 次异步写）；首地址不对齐时整体拷入对齐缓冲分两次写。
- **ReadAt/ReadAtInto**：读入 bufpool 对齐缓冲（`ReadAt`）或直接 DMA 进调用方 dst（`ReadAtInto`，句柄归调用方）；请求窗口不满足 4K 对齐由上层 `Storage` 吸收。
- **批读 ReadAtIntoBatch**：一次 `io_submit` 批量提交多条 4K 对齐直读（`aio.ReadSpec`），摊薄系统调用；批内非对齐项或整批提交失败逐条回退。
- **IO 尺寸统计**：原子计数 4MiB 整块 vs 其他，供压测验证「读写是否整块 4MiB」。

### 5.2 aio 层（internal/aio）

纯 Go 异步磁盘 IO（不依赖外部库，兼容内核过旧不支持 io_uring 的部署节点）：

- Linux：封装 `io_setup / io_submit / io_getevents / io_destroy` 四个系统调用，`struct iocb/io_event` 按 `linux/aio_abi.h` 布局声明（无 cgo）。
- 其他平台：goroutine + 同步 pread/pwrite 兜底，接口语义一致（Submit 立即返回序号、Wait 阻塞收集）。
- **完成泵 pump（device 持有）**：唯一调用 `ring.Wait` 的 goroutine，串行取回完成事件按 seq 分发；事件先到而提交方未注册时暂存 pending；空闲 200ms 轮询（用于 Close 及时退出），`ErrFull`（队列满）100µs 退避重试。
- 队列深度 `aioDepth = 256`。

### 5.3 bufpool（internal/bufpool）

热路径 4K 对齐缓冲池，消除大块 `make` 的堆分配与清零开销：

- 2 的幂分桶（4 KB ~ 8 GB，`maxBufBucket = 33`），每桶 `maxKeep = 32` 上限约束驻留内存。
- **读写路径共享**：device 的 O_DIRECT 对齐缓冲、服务端 Get 缓冲、`internal/rpcclient` Put 缓冲同池。
- 实现为自管理 freelist（互斥锁 + LIFO 栈）而非 `sync.Pool`：后者每次 GC 清空对象，4M/8M 大缓冲被整批丢弃重走对齐分配 + memclr（实测曾占服务端读路径 CPU ~36%）；自管理池大缓冲常驻长期复用，首次分配清零后后续零分配、零清零。
- 归还约定：`Put` 接受 Get 返回的原始切片或子切片，按 cap 归一化回整桶容量入桶。

### 5.4 metastore（internal/metastore）

元数据存储接口（`Store`）+ Pebble 实现（`kv_pebble.go`）。核心能力：

- **数字签名方法**：`GetMapping/PutMapping/DeleteMapping/IterMapping`（mapping 面）；`GetSegment/PutSegment/MarkCompacting`（段面）；`MoveMapping`（CAS 搬移）；`AllocateSegment/AllocateSegmentReserve`（游标分配）。
- **游标分配**：`AllocateSegment(size)` 原子申请 4K 对齐段内偏移，段满自动滚动，可并发调用（内部锁只覆盖廉价游标分配）。
  - 用户写路径滚动上限**保留 ≥2 个空闲段**不触碰（compaction 兜底）；`AllocateSegmentReserve` 为搬移专用，可动用预留段，避免用户写满时搬移死锁。
- **有界 LRU 分片缓存**：256 分片、全局预算 1 GiB（每片 4 MB），fnv 哈希寻片，分片内互斥锁 + 双向链表（Front=MRU）；Pebble 为真实源，缓存任何时刻可重建（崩溃/淘汰不丢持久性）；`LoadCache` 全量预热消除未命中回查。
- **后台 GC**：`gcInterval = 1s` 周期扫描，把「无在途读者」的 Reclaiming 段转 Free 入池（FIFO）。
- **容量统计** `UsedBytes()`：Full/Reclaiming 计整段、Active 计已写偏移。

### 5.5 存储引擎 Storage（internal/storage）

对象存储引擎（`Storage`），不感知缓存与分配细节。**已下沉 internal**：服务端与 CLI 通过它读写裸盘，外部调用方不再能嵌入它，只能走客户端。

`ObjectStore` 接口（`Put/Get/Delete/Stat/Close`）定义在 `internal/rpcclient`，由对外 SDK 唯一实现（断言见 `pkg/taihu-client/storage.go`），**不是**引擎的方法集；引擎侧另有 `ReadAt/ReadAtInto/BatchRead` 等直接返回池化缓冲的裸盘读方法，仅供服务端零拷贝路径使用。

写路径三段式（`Put` = `PutBegin` + `PutAppend` + `PutCommit`，供一次性写调用方；分段直写可拆用）：

```
PutBegin   : 校验 0 ≤ size ≤ 段大小；db.AllocateSegment(size) 原子分配（锁内最廉价步骤）
PutAppend  : device.Append（锁外执行）── 多 Put 并发写不同偏移的关键
PutCommit  : PutMapping 建立 key→(seg,off,size)（先数据后元数据，避免「有映射无数据」）
```

读路径（`ReadAt`）：

```
GetMapping（LRU 缓存快路径）→ 边界校验（off<0 / off>Size → ErrInvalidRange）
→ RefSegment（防 GC 竞态）→ 设备直读（4K 向下/向上对齐，对齐窗零拷贝直读；
   非对齐窗 pooled 缓冲内原址一次平移）→ 短读截断 + io.EOF → UnrefSegment
```

- `ReadAtInto`：off 4K 对齐 + dst 首地址 4K 对齐时 O_DIRECT 直接 DMA 进调用方 dst（服务端 shm 直读共享内存用，免 bufpool→shm memcpy）。
- `BatchRead`：多对象块解析为设备直读 job，一次 `io_submit` 批量提交，逐块语义与 `ReadAtInto` 等价（服务端"多 stream 一 worker"聚合读）。

### 5.6 Compactor（internal/storage/compact.go）

后台段压缩：把高空洞 Full 段（及上次中断的 Compacting 段）的存活对象搬移到新位置，搬空后旧段自动转 Reclaiming 供 GC 回收。

| 配置 | 默认 | 语义 |
|------|------|------|
| Interval | 60s | 扫描周期 |
| HoleThreshold | 0.8 | 单段空洞率（1 - 存活字节/段大小）≥ 阈值入候选 |
| ForceWatermark | 0.8 | 已用段占比 ≥ 阈值强制压缩（不等单段阈值） |
| MaxMovePerRound | 512 | 每轮搬移对象上限（限速，防冲击稳态带宽） |

搬移流程（每对象）：

```
ReadAt 读旧位置（自带 Ref/Unref）→ AllocateSegmentReserve 分配新落点（可动用预留段）
→ device.Append 写设备（先数据）→ MoveMapping CAS 条件写：
   仅当当前映射与 old 完全一致时原子改为 new，并同 WriteBatch 转移段存活计数
   （new 段 +1 / old 段 −1）；被并发 Put/Delete 改动 → ErrConflict，跳过该对象下轮重扫
```

候选段按空洞率降序处理（单位搬移释放空间最多），同率按段号升序（确定性）。

## 6. 远程访问层（internal/transport）

### 6.1 帧协议

自定义帧流式多路复用（netpoll + LinkBuffer），**取代 gRPC/HTTP-2**：

```
帧格式: [4B len][4B streamID][1B op][payload...]
  len     = 4 + 1 + len(payload)（len 字段之后字节数），大端
  streamID= 连接内流多路复用（每次 RPC 独占一个 stream）
  payload ≤ 4MiB（chunkSize）；帧总长上限 = 9 + chunkSize
```

- **收**：连接读循环 Peek 帧头 → Slice 整帧（生成零拷贝子 Reader）→ 按 streamID 分发到流处理器；负载一次拷入目标缓冲。
- **发**：>4K 负载 `WriteBinary` 零拷贝引用原缓冲，sendmsg(writev) 散射写出，Flush 阻塞至排空（保证返回后缓冲可安全复用）。
- 收流节点容量 `inputNodeSize = 4 + maxFrameTotal`：读满一帧后节点剩余容量为 0（一帧一节点），客户端 Get 可经 **TakeTry** 零拷贝移交该节点缓冲给调用方。

### 6.2 操作码与错误映射

| 类 | op | 说明 |
|----|----|------|
| 数据面 | `opPutHeader/opPutData/opPutEnd/opResp` | 客户端流式上传 |
| | `opGetReq/opGetData/opGetDataFinal/opGetErr` | 服务端流式下发；末帧 `opGetDataFinal`（=0x86）收尾，省一帧 |
| | `opDelReq/opStatReq/opStatResp` | Delete / Stat |
| 管理面 | `opPing/opPong` | 连通性 + RTT |
| | `opMetaReq/opMetaResp` | 对象落盘元数据（seg/off/size） |
| | `opSegReq/opSegSum/opSegData/opSegEnd` | 段汇总 + 逐段明细 |
| | `opKeysReq/opKeysData` | 按前缀枚举 key |

错误码（wire 4B 大端）与库错误双向映射：

```
codeOK=0  codeNotFound=1  codeInvalidRange=2  codeTooLarge=3  codeNoSpace=4  codeInternal=5  codeInvalidArgument=6
```

### 6.3 服务端（transport.Server）

- 单 Storage 实例，暴露 Put/Get/Delete/Stat 四个 RPC + admin RPC；`transport.NewServer(storage)` 返回 `*transport.Server`，由 `cmd/taihu/cmd/server.go` 直接驱动 Serve/GracefulStop 生命周期。
- **多监听 IP**：`-listen` 每个 IP 各一条 listener、各一个 Serve goroutine（`sync.WaitGroup` 管理），共享同一 RPC 端口与同一 Storage。
- 通告地址 = 首个监听 IP + RPC 端口；同时通告完整地址列表（`Addrs`）供客户端多 IP 均分建连（旧客户端忽略该字段，向后兼容）。

### 6.4 客户端（internal/rpcclient）

- 实现 `rpcConn` 抽象：TCP（`transport.Conn`）或共享内存（`shmConn`）皆可，`Storage` 按 round-robin 分发到各连接，上层无感。
- 与本地库同接口：`Put(ctx,key,size,in []byte)`、`Get`（单帧零拷贝移交、跨帧回退一次汇入；`size=-1` 读至结尾，返回 `(data, release, err)`，调用方用毕必须 `release()` 归还池化缓冲）。
- 连接池：`DialPool`（单地址 N 连接）/ `DialPoolMulti`（多地址 × N 连接）/ `DialShmPool`。
- 零拷贝写：Linux 下 `NewPut/PutWriter` 经 shmipc `Reserve` 在共享内存数据区直接生成 payload；非 Linux/TCP 返回 `ErrShmOnly` 回退普通 Put。

### 6.5 零拷贝路径汇总

| 阶段 | 机制 |
|------|------|
| 磁盘读 | O_DIRECT 直读 bufpool 对齐缓冲（或直接 DMA 进共享内存） |
| 服务端→共享内存 | shmipc 数据帧 4K 对齐数据区，服务端 `ReadAtInto` 直读，免 bufpool→shm memcpy |
| 服务端→网络 | 4K 对齐源缓冲被 `WriteBinary` 零拷贝引用，writev 散射 |
| 客户端收帧 | 单帧 `TakeTry` 零拷贝移交节点缓冲；跨帧回退一次汇入 |
| 客户端写 | shmipc `Reserve` 共享内存内直写 payload（`-zero-copy-write`） |

## 7. 共享内存 IPC（shmipc）

同机（客户端与服务端同主机）低延迟数据面，fork 自 cloudwego/shmipc-go（随 go.mod `replace` 落地 `third_party/`）：

- **固定路径**：unix socket `/dev/<server-name>`（default 开启），与 TCP 监听并行。
- **数据帧 4K 对齐布局**：

```
[5B 帧头][4091B pad][4K 对齐数据区]
```

- fork 核心改动：buffer 数据区 4K 对齐，使服务端 **O_DIRECT 直读共享内存**（读路径免 bufpool→shm memcpy）。历史上 `shmSliceSize = chunkSize + 8KiB`（4K 对齐值，满足 arm64）。
- 拆帧：`reserve 后写帧头 + Flush` 免 copy；`PutBegin / PutWriter`（Reserve 返回共享内存数据区直接引用（4K 对齐），写满 chunkSize 自动切帧）。
- `-batch>0` 启用"多 stream 多 worker"批读：整块 4MiB 直读聚合 io_submit。

## 8. 集群层（internal/cluster + pkg/taihu-client）

### 8.1 注册区与心跳（TiKV）

| 数据 | key 前缀 | 内容 |
|------|----------|------|
| 实例注册 | `/taihu/instances/` | InstanceInfo{Name, Node, Hostname, Addr, Addrs[], ShmAddr, 容量字段, 心跳时间} |
| key 索引 | `/taihu/index/` | key → 实例名 |
| SDK 客户端 | `/taihu/clients/` | ClientInfo{ID, Node, Pid, SDKVersion, 心跳时间} |

- 实例：启动注册 + 1s 心跳（刷新容量/可用/已用与 LastHeartbeat）+ 优雅停机注销（防僵尸实例）；离线由客户端按心跳超时兜底判定（默认 5s）。
- 容量记录：实例启动读取一次设备容量，与 TiKV 记录比对，**不一致（换盘/容量变化）拒绝启动**，必须当新实例部署。
- SDK 客户端：配置 ClientID 时自动注册并周期保活，`client list` 可见；停机注销。

### 8.2 路由与索引（taihuclient.Storage）

```
写 Put ：Picker 本地优先选实例（FirstPick/Local 优先、使用阈值过滤）→ 数据面写入
        → 异步写 TiKV 索引 + 本地路由缓存 RouteCache(4096)
读 Get ：① RouteCache 命中 → ② TiKV 索引定位实例 → ③ 全部 miss 回源重建（Source 配置）
        → 回写本地缓存（本地优先 Put）
删/Stat：索引定位删；索引 miss 则删/查本地全部实例
```

- 数据面连接缓存：`atomic.Value` 只读快照 + 写时复制（懒建首连加锁双检），读热路径零锁。
- `PreloadRoute`：64 并发 worker 预热路由缓存，消除压测/预热场景每 key 先查 TiKV 的冷启动开销。

### 8.3 传输选择（同机 shm / 跨节点 TCP）

| Transport | 行为 |
|-----------|------|
| `auto`（默认） | 客户端与服务端 Hostname 一致且实例有 ShmAddr → shmipc；shm 不可用回退 TCP；跨节点走 TCP |
| `rpc` | 强制 TCP（含同机，测网络路径正确性/性能） |
| `shm` | 强制共享内存（仅同机实例可用） |

- 连接缓存键按传输分桶（`shm://` 与 `tcp://`），避免强制传输下连接误复用。
- 多 IP 均分：实例通告 `Addrs`（每 IP 同端口）时按地址 × N 连接 round-robin 分发，分摊多网卡/多链路带宽。

### 8.4 容量管理

```
Capacity  = SegmentSizeBytes × SegmentCount（由真实设备容量计算）
Used      = UsedBytes()（Full/Reclaiming 整段 + Active 已写偏移）
Available = Capacity - Used
```

心跳随包上报，供 `cluster list`（水位）与集群级容量决策使用。

## 10. 数据读写路径详解

### 10.1 写路径（本地库，同机/跨节点同语义）

```
调用方 ─► 本地 Storage.Put ──或──► taihuclient.Storage.Put ──帧流──► transport.Server ──► Storage.Put
                                                                   │
   allocator.mu（锁内，最廉价）:                       db.AllocateSegment(size) → (seg,off) 4K 对齐
   锁外:                                              device.Append(seg,off,size,data)   ← O_DIRECT 直写
   pebble 单 WriteBatch（sync）:                      PutMapping(key → meta) + 段计数 + cursor 落盘
```

### 10.2 读路径（本地 / TCP / shm）

```
本地  : GetMapping(缓存) → RefSegment → device.ReadAt（池化对齐缓冲，非对齐窗内一次平移）→ Unref
TCP   : client Get →[opGetReq]→ server Storage 读 →[opGetData.../opGetDataFinal]→ client TakeTry 零拷贝移交
shm   : client Get →[共享内存直读链]→ server ReadAtInto 直接 DMA 进共享内存切片（免 memcpy）→ client 读数据区
```

### 10.3 语义约定

- `Get` 区间：`off ≥ 0`，`size = -1` 读至对象结尾；`ErrInvalidRange`（off<0 / off>Size）→ wire `codeInvalidRange` → 客户端还原。
- 短读：读到对象/设备末尾不足请求量时截断返回，并以 `io.EOF` 标记（调用方按 EOF 收尾）。
- 一次性事务边界：先写设备数据再写元数据，避免「有映射无数据」；映射写入与段存活计数同 WriteBatch 原子。

## 11. 空间回收（GC 与 Compaction）

```
Delete(key) ──► 删 mapping（段存活计数 −1，同 WriteBatch）
                    │ 该段 AliveCount 归零
                    ▼
               Full ──► Reclaiming ──►（后台 GC 1s 扫描，refCount==0）──► Free 入池复用

Compaction（60s / 空洞≥80% / 水位≥80% 触发）:
   候选 Full/Compacting 段按空洞率降序 → MarkCompacting → 逐对象：
      ReadAt(Ref/Unref) → AllocateSegmentReserve（预留段） → device.Append → MoveMapping CAS
   搬空后旧段 AliveCount=0 自动 Reclaiming → GC 回收
```

- 空间池：Free 段 FIFO 供 allocator 在游标到顶时复用（游标回跳，段内仍顺序写）。
- 预留段：分配器滚动上限保留 ≥2 Free 段（用户路径不可用），compaction 经 `AllocateSegmentReserve` 执行搬移，保证用户写满时搬移仍有落点。

## 12. 缓存与内存管理

| 层 | 机制 | 约束 |
|----|------|------|
| 元数据缓存 | 256 分片 LRU（fnv 寻片） | 全局 ≤ 1 GiB，每片 ≤ 4 MB；Pebble 为源，可重建 |
| 数据缓冲 | bufpool 分桶 freelist（4KB~8GB） | 每桶 ≤ 32 缓冲；4K 对齐；读写路径共享 |
| shm 池 | shmipc 缓冲池（读：≈480 个大切片 @95%） | 池耗尽 Reserve 逐块失败即截断，回退路径兜底续读 |
| 连接缓存（pkg/taihu-client） | `atomic.Value` 快照 + copy-on-write | 读零锁，懒建首连加锁双检 |
| 路由缓存 | RouteCache(4096) | 读路径首查，命中免打 TiKV 索引 |

## 14. 已知权衡与后续演进

| 权衡 | 现状 | 演进方向 |
|------|------|----------|
| 单盘单 Storage | server 单实例单盘 | 多盘 `-devs` + key 路由（接口已隔离：client 只认 `ObjectStore`） |
| 无覆盖写 | key 不可变，更新 = Delete + 重建 | —（语义约束） |
| 索引尽力而为 | 路由缓存/TiKV 索引可丢，退化为本地 + 回源 | —（一致性语义） |
| 无认证 | 内网 insecure | TLS / X-Token 可插拔接入（接口预留） |
| 元数据缓存上限 | 1 GiB | 按需调整（4K 对象全量永久缓存不现实：需 ~530-670 GB） |
| 传输协议 | 自研帧协议（netpoll） | 协议版本化、加密预留 |
