# b93df7f 单 NVMe 读写性能测试报告（128.11）

日期：2026-09-27
对应提交：`b93df7f`（feat(batch): 读写删对称批处理流水线，被测二进制 `/tmp/taihu.b93df7f`）
测试节点：100.71.128.11（主机名 SZYFQ-PM-OS01-BCNFS-XCKP04，96 核 aarch64，内存 754G）
被测设备：**/dev/nvme1n1p1（唯一被测盘，nvme2/3 全程零流量，验证单盘隔离）**

## 1. 测试目标

1. `taihu bench storage`：Storage 层本地裸盘直写压测（-db/-dev 直连盘，不走网络）。
2. `taihu bench single --transport shm`：单机直通共享内存 IPC 压测（rpcclient 直连 taihu-server，不查 TiKV）。
3. fuse 客户端：fio 经 nefs.client.taihu 挂载点读写，端到端（fio → FUSE → 客户端 → rpc → taihu-server → Storage → 裸盘）。
4. 三组均只测**一个 NVMe**（128.11 的 nvme1n1p1），并按约定给出 CPU 三维（物理机 busy%+usr/sys、客户端等效核数、服务端等效核数）。

## 2. 测试环境与隔离约束

| 项 | 值 |
|----|----|
| 节点 | 100.71.128.11（96 核 aarch64） |
| 被测盘 | /dev/nvme1n1p1（nvme1 盘，1.7T 级） |
| 编译产物 | /tmp/taihu.b93df7f（GOARCH=arm64，含 server + bench storage/single） |
| 元数据 | 各测试独立 pebble 目录，测试前清空重建 |
| 对象/块大小 | 4 MiB（-size 4194304 / BlockSize=4096 KiB） |
| 数据量 | bench：count=20000 ≈ 80 GiB；fuse：fio 16j×12G=192 GiB |
| 线程数 | 写 2t / 读 32t（对齐历史报告最佳参数）；fuse 写 16j×iodepth4、读 16j×iodepth8 |
| TiKV | --pd 100.71.128.11:2379,100.71.128.12:2379,100.71.128.13:2379 |
| 采样 | iostat -x -t 1（盘侧稳态，写阈值 1000 MiB/s / 读 5000 MiB/s）、mpstat -P ALL 1、/proc/stat（物理机 busy%）、/proc/<pid>/stat 14/15 字段 Δ（等效核数，CLK_TCK=100） |

**单盘隔离机制**：
- storage / single shm：bench 直连裸盘/专属 TAIHU-SINGLE，不经过 nvme2/3。
- fuse：测试期间停 n11-nvme2 / n11-nvme3，node11 全部 IO 压到 n11-nvme1；测试后已按生产参数重启恢复。
- 全程 iostat 监控 nvme2n1/nvme3n1 为 **max=0.0 MiB/s**（见各段采样）。

**破坏性说明**（预期副作用）：storage 与 single shm 压测会销毁 nvme1n1p1 上的段表数据；fuse 测试前已 `rm -rf /var/taihu-db/nvme1` 并以全新 db 重启 n11-nvme1。旧 v11-* 卷中落在 nvme1 的对象作废；**nvme2/3 数据未受影响**（生产挂载 v11-1..4 全程在线）。

**环境备注**：建卷时发现 mgmt 集群中 100.71.128.12:12379 已宕机（http=000），改走存活的 100.71.128.11:12379 建卷成功（ID=19，BlockSize=4096 显式指定）。生产卷/挂载不受影响。

## 3. 测试方法

```bash
# ① storage 写（2t）/ 读（32t，读前 LoadCache 预热）
taihu bench storage --mode write --db /tmp/tdb4m --dev /dev/nvme1n1p1 \
  --size 4194304 --count 20000 --threads 2 --keys-prefix p4m-w2 --report-interval 5s --latency
taihu bench storage --mode read  --db /tmp/tdb4m --dev /dev/nvme1n1p1 \
  --size 4194304 --count 20000 --threads 32 --report-interval 5s --latency

# ② single shm（专用服务端，不带 batch：直连带 batch 服务端会卡死）
taihu server --listen 100.71.128.11 --db /tmp/tdbsingle --dev /dev/nvme1n1p1 \
  --server-name TAIHU-SINGLE --pd '<三节点 PD>'
taihu bench single --mode write --transport shm --shm /dev/TAIHU-SINGLE \
  --size 4194304 --count 20000 --threads 2 --report-interval 5s --latency
taihu bench single --mode read  --transport shm --shm /dev/TAIHU-SINGLE \
  --size 4194304 --count 20000 --threads 32 --report-interval 5s --latency

# ③ fuse 客户端（fio 定量，不回绕不命中 blockcache；写 16j×4d×12G，读 16j×8d 整读一遍）
fio --name=t11s --directory=/mnt/v11-single --rw=write --bs=4M --direct=1 --ioengine=libaio \
    --numjobs=16 --iodepth=4 --size=12G --fallocate=none --group_reporting=1 --lat_percentiles=1
fio --name=t11s --directory=/mnt/v11-single --rw=read  --bs=4M --direct=1 --ioengine=libaio \
    --numjobs=16 --iodepth=8 --size=12G --fallocate=none --group_reporting=1 --lat_percentiles=1
```

## 6. 结论

1. **单盘隔离验证通过**：三组测试全程 nvme2n1/nvme3n1 磁盘流量 max=0.0 MiB/s，所有 IO 仅落 nvme1n1p1。
2. **storage 裸盘是带宽天花板**：写 2572 / 读 6643 MiB/s，盘 util≈96%，CPU 极低（客户端 0.08~0.20 核，物理机 <0.6% busy）——裸盘路径无 CPU/传输开销。
3. **shm 端到端接近裸盘**：写 2571（-0.04%），读 6221（-6.3%，shm 单通道并发为次要瓶颈）；CPU 仍极低（读写均 <0.4 核/进程）；读帧零拷贝 100% 命中。
4. **fuse 写路径是最大短板（-73.8%）**：674 MiB/s 时盘 util 仅 25.9%，瓶颈在 fuse 客户端写路径（客户端核 2.57），磁盘有大量余量；延迟均值 378ms，p 值集中在 250~750ms。
5. **fuse 读贴合盘上限（-6.1%）**：6240 MiB/s、盘 util 94.7%；但客户端核 3.77、物理机 sys 4.2%，高并发读的 syscall/网络开销显著高于 bench 路径，仍有降 CPU 空间（按项目目标，读路径 syscall/拷贝削减值得评估）。
6. **CPU 三维结论**：越靠近用户态应用（fuse），等效核数越高（写 2.57 / 读 3.77）；服务端 Storage 侧始终极低（≤0.47 核）。降 CPU 的发力点应在 fuse 客户端与读路径。
