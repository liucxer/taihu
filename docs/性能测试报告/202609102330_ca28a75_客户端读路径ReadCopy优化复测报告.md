# ca28a75 客户端读路径 ReadCopy 优化复测报告

> 对应提交：`ca28a75`（perf: 客户端 Get 收帧 ReadCopy 直写调用方缓冲，消除多节点 Next 中间搬移）
> 对比基线：`8abdf4d`（202609102210 三服务端并行读性能测试报告）
> 测试：3 服务端 × 3 客户端并行 RPC 读（各 32T/16C/4MiB×20000，loopback，客户端+服务端同机 128.12）
> 测试时间：2026-09-10 23:22 ~ 23:23

## 1. 测试目标

验证客户端读路径 ReadCopy 直写优化的效果：netpoll LinkBuffer 的 `readCopy` 导出为 `ReadCopy`，
客户端 `Conn.Get` 收帧由「Next 物化 + copy 汇入」双拷贝改为「ReadCopy 跨节点直拷调用方缓冲」单拷贝，
对比复测客户端 pprof（memmove/Syscall6 占比）、进程 CPU、聚合带宽与延迟。

## 2. 测试环境

| 项目 | 值 |
| --- | --- |
| 服务器 | 100.71.128.12（客户端+服务端同机，loopback 127.0.0.1，aarch64 96 核） |
| 数据设备 | /dev/nvme1n1、nvme2n1、nvme3n1（O_DIRECT + libaio） |
| 元数据 | /tmp/tdb1、/tmp/tdb2、/tmp/tdb3（pebble，复用基线数据，WAL 回放 ~40000 key/端） |
| 服务端 | /tmp/taihu server.new（ca28a75）x3，:50051/52/53，pprof :6061/62/63 |
| 客户端 | /tmp/taihu bench cluster.new（ca28a75）×3 |
| 对象 | 4 MiB × 20000（80 GiB/端点），chunkSize=4MiB 单帧传输 |

## 3. 测试方法

1. 数据复用基线：/tmp/tdb1/2/3 元数据完整（基线写入的 p4m-s1/2/3 各 20000 key 未变），跳过写灌，直接读；
2. 3 客户端并行 `-mode read -size 4194304 -threads 32 -conns 16 -count 20000 -keys-prefix p4m-s{1,2,3} -latency -cpuprofile <c{n}.cpu>`；
3. 全程 `mpstat -P ALL 1`、`iostat -d nvme1n1 nvme2n1 nvme3n1 1`、`/proc/net/dev`（lo 差分）逐秒采样；
4. 读测期间抓 3 服务端 pprof（:6061/62/63 各 30s）；
5. 客户端 cpuprofile 与服务端 pprof 拉回本地 `go tool pprof` 分析。

## 6. 瓶颈分析与结论

1. **ReadCopy 直写生效**：客户端 memmove 由双拷贝（Next 物化 + copy 汇入）降为单拷贝（ReadCopy 跨节点直拷），memmove 占比 48.5~51% → 40.7~41.8%，`UnsafeLinkBuffer.Next` 已不在 memmove 调用链中；客户端进程 CPU 每实例 -12~17%（7.6~8.1 → 6.4~6.7 核）。
2. **带宽与延迟提升**：每客户端 +5~7%、聚合 13015 → 13695 MiB/s（+5.2%）、延迟 p50 -25%，与服务端一致的 syscall 主导（sendmsg 91~93%）形态不变。
3. **瓶颈转移**：整机 CPU 持平（39.6%，usr↓sys↑），磁盘聚合 13.3 GB/s（单盘 4.44 GB/s，仍有余量 vs 极限 ~6.6），loopback AVG 13.3 / PEAK 14.6 GB/s 已贴近上一轮实测上限（PEAK 16.9 GB/s）——聚合上限再次落在 **loopback 吞吐 + 客户端 recv syscall** 上，客户端收帧的单次汇入拷贝（ReadCopy 40.7~41.8% of memmove）已是该路径的必要成本。
4. **结论**：ReadCopy 优化达成目标（客户端 CPU 显著下降、带宽与延迟改善），客户端收帧路径已无冗余拷贝；要再突破聚合上限需绕开同机 loopback（跨机部署）或进一步降低 recv 次数（更大帧/批量收）。
