# NEFS taihu 性能基线测试报告（回退 HEAD d45e0db）

- 日期：2026-09-30
- 环境：100.71.128.11/12/13（各 96 核），三节点 9 盘（每节点 nvme1/2/3），bond1+bond2 = 每节点 100Gbps（4×25G）全双工数据面
- 被测栈：**基线 = 回退旧栈 HEAD d45e0db**，`/tmp/taihu.baseline`（sha256 `1eb17144`，无 `--tcp-inflight`）
- 对象规模：4 MiB / 对象，`--count 128000`，500 GB/盘，9 盘 = 4.5 TB/轮；storage 层裸盘独占（server 停）

### 7.2 归因分析

**storage 层（基线，裸盘直写）**：写 22.57 / 读 55.55 GiB/s，物理机几乎全 idle（busy~1.1–1.5%，usr~0.3–0.6%）。这是本测试的**硬件能力上界**——9 盘聚合写 ≈ 单盘 ~2.5 GiB/s、读 ≈ 单盘 ~6.2 GiB/s，读约为写的 2.5 倍（4MiB 顺序读命中 NVMe 稳态读带宽）。storage 层无网络栈、无复制，直接排队写盘，CPU 开销可忽略。

**cluster 亲和（写实例锚定，同机 shm→本机，跨机 TCP）**：写 22.25 GiB/s **逼近 storage 上界**（-1.4%），读 51.92（-6.5%）。亲和路由让 12 客户端各自优先写本节点 3 实例的关键对象，数据面大部分走本机 shm，TCP 压力小。整机 busy 写 5.5~6%（usr 4.2~4.5 + sys ~1%），服务端核仅 ~0.87/节点——**写入几乎不消耗服务端 CPU**。读基本保持 storage 水平，说明 cluster 亲和层对带宽几乎没有扣除，代价可控。

**cluster 非亲和（round-robin key 均分到 9 实例）**：写 24.45 GiB/s 反而**高于亲和**（+9.9%，把负载摊到 9 实例、跨 3 节点打散避免单点排队）；但**读暴跌到 26.31 GiB/s（-52.6%）**。归因：写是"推"语义，round-robin 可并发跨节点分摊；读是"拉"语义，每客户端 2/3 请求跨节点 TCP，交叉读的调度与网络往返造成读吞吐腰斩，且 p99 升到 4.8~9.6s。**同时服务端核骤升到 7.5~9.4/节点（亲和仅 ~0.87）**，sys% 9~14%（亲和仅 ~1%），整机 busy 20~32%（亲和 5.5~6%）——非亲和路由把大量负载从客户端搬到服务端数据面与网络栈，**CPU 成本显著上升**。

**FUSE 客户端层（亲和）**：写 6.53 / 读 16.34 GiB/s，**相对 cluster 层腰斩再腰斩（写 -71%，读 -70%）**，是**全栈最大瓶颈**。归因：FUSE 客户端（EFS_nefs）在数据面做 chunk 划分、缓冲拷贝、syscall（fuse write/read 往返）、间接寻址，客户端核飙到 **8.3~10.4/节点**（cluster 直压写仅 ~3.2/节点），远高于服务端核 ~0.23~0.27——**瓶颈在客户端 CPU/拷贝路径而非服务端或盘**，整机 busy 仅 ~11~13%（数据面未打满）。

**FUSE 客户端层（非亲和）**：写 5.87（-10%）/ 读 14.25（-13%）GiB/s，较 FUSE 亲和进一步下降。读路径 round-robin 跨节点占 2/3，客户端每读请求走 TCP 取远实例数据并在 fuse 层再拷贝，客户端核升至 **12~13.4/节点**（亲和读 ~9.5~10），busy% 16~17.6%（亲和读 ~12~13）；服务端核仍仅 ~0.1。**结论：round-robin 在 FUSE 层的读惩罚是"客户端多付拷贝/syscall + 跨节点 TCP 往返"叠加，读是重灾区。**

### 7.3 结论

1. **写入**：链路基本无损，storage→cluster 亲和仅 -1.4%；round-robin 跨节点分摊反而小幅提升写。
2. **读取**：cluster 亲和接近 storage（-6.5%），但 round-robin 读腰斩（-52.6%），FUSE 层为总瓶颈（读较 storage -70%）。
3. **CPU**：storage 几乎零开销；cluster 亲和写服务端仅 ~0.87 核；非亲和路由把服务端核抬到 7.5~9.4、sys% 抬到 9~14%；FUSE 客户端为 CPU 主耗（8~13 核/节点），性价比最差。
4. **优化方向**：优先压缩 FUSE 客户端数据面 CPU（拷贝/syscall/chunk 路径）；cluster 写已接近上界，读需改善交叉读调度与网络路径。

### 8.4 同栈 A/B 结论

- **写带宽下降 6~10%**：新栈合计 5.31~5.48 GiB/s vs 基线旧栈 5.87 GiB/s（-7%~-10%）；单挂载点 560~700 MiB/s vs 基线 637~698 MiB/s。两轮新栈结果一致（5.31/5.48），非抖动。

- **归因**：客户端（EFS_nefs）不变，差异来自服务端新栈二进制。b93df7f 是「读写删对称批处理流水线」提交（server.go/batch.go 写路径有改动）；`--tcp-inflight 64` 属读侧异步流水线，本应不影响写，但服务端写核与 busy% 同步抬升指向**批处理流水线在写路径引入额外服务端开销**（服务端不再空闲：0.13→2.4+ 核），需进一步 pprof 定位（写路径热点），或复测去掉 `--tcp-inflight` 的 b93df7f 隔离参数影响。
