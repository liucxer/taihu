# NEFS taihu 均衡算法（round-robin）读写性能测试报告

- 日期：2026-09-29
- 环境：100.71.128.11/12/13（各 96 核），三节点 9 盘（每节点 nvme1/2/3），bond1+bond2 = 每节点 100Gbps（4×25G）全双工数据面
- 被测路径：**taihu bench cluster 直压 SDK**（避开 FUSE 客户端，排除 EFS_nefs 拷贝与 syscall），`--write-routing round-robin`（均衡）+ `--transport auto`（同机 shm / 跨节点 TCP）
- 对象规模：4 MiB / 对象，`--count` 按量给足（每客户端 ~160 GiB/prefix），run 60s 量级
- 服务端形态：`taihu.b93df7f`，每节点 3 server（--batch 32），共 9 实例；TiKV+PD 3 节点

## 1. 结果总览（最佳带宽）

| 方向 | 最佳集群带宽 | 对应参数 | 物理机 busy 均值 | 客户端核/节点 | 服务端核/节点 |
|---|---|---|---|---|---|
| **均衡写** | **23397 MiB/s（22.86 GiB/s）** | 3 客户端 × threads=128 × conns=4 | 13-22% | ~7 | ~2.7 |
| **均衡读** | **31554 MiB/s（30.81 GiB/s）** | **12 客户端**（每节点4）× threads=128 × conns=4 | 写档已测 12-23%，读档更高 | — | — |

> 数据面说明：round-robin 把 key 均分到 9 实例，每客户端读 **2/3 走跨节点 TCP、1/3 走本机 shm**。`transport auto` = 同机 shm / 跨机 TCP 混合，最贴近真实均衡读写。

## 2. 均衡写带宽扫参（MiB/s）

### 2.1 threads × conns（3 客户端）

| threads | conns=4 | conns=16 |
|---|---|---|
| 16 | 18470 | 17475 |
| 32 | 22258 | 20029 |
| 64 | 23063 | 21607 |
| 128 | **23397** | 22768 |

- **最佳写 = threads=128、conns=4 = 23397 MiB/s（22.86 GiB/s）**
- **conns=4 始终优于 conns=16（+6~10%）** → 印证"每 TCP 地址 4 连接已饱和，conns 不是并行度闸门"（与 SKILL 第 57 条一致）
- 写盘 util 全程 20-22%（**盘未饱和**，写瓶颈在数据面一致性/调度，非盘）

## 3. 均衡读带宽扫描（MiB/s）

### 3.1 threads × conns（3 客户端，pipeline=1）

| threads | conns=4 | conns=16 |
|---|---|---|
| 16 | 18241 | 17176 |
| 32 | 20890 | 20423 |
| 64 | 22144 | 22170 |
| 128 | **22783** | 22195 |

- 3 客户端下滑时读上限 ~23 GiB/s；读由每-op 固定成本主导，threads 到 128 收敛。

### 3.2 pipeline 对照（3 客户端 × threads=128，conns=4）

| pipeline | 集群读带宽 | p99 |
|---|---|---|
| 1 | 22783 | — |
| 4 | 22999 | ~2.0s |
| 8 | 22956 | 1.9-3.4s |
| 16 | 22602 | 5-7.1s |

- **pipeline 无增益（+0~1% 内波动），但放大延迟 3.7×** → 瓶颈不在"worker 内流水线深度"。

### 3.3 客户端进程数 ×（threads=128，conns=4，pipeline=1）——读取上限探顶

| 每节点客户端 | 集群客户端数 | 集群读带宽 |
|---|---|---|
| 1 | 3 | 22783 MiB/s |
| 2 | 6 | 30221 MiB/s |
| 3 | 9 | 30292 MiB/s |
| **4** | **12** | **31554 MiB/s（峰）** |
| 5 | 15 | 25699 MiB/s（回落） |

- **最佳读 = 12 客户端（每节点 4）× threads=128 = 31554 MiB/s（30.81 GiB/s）**
- **12→15 客户端回落 20%**：数据面并发处理能力封顶（服务端 batch/索引 + 客户端 copy），更多进程只互相争抢。

## 4. 瓶颈归因

### 4.1 读路径每-op 成本主导（frame stats）

```
读回 80000 帧：transformer-rx dataFrames=80000 dataBytes=335544320000
   take=26667（零拷贝）  copy=53333（CPU 拷贝）
```

- **1/3 走零拷贝 take、2/3 走 copy**：跨节点 TCP 读回数据落到本机后 2/3 需内存拷贝——这是读带宽钳在 ~31.5 GiB/s 的主因。
- 写路径是纯数据发送、零响应拷贝（`rx take=0 copy=0`），故写能顶到更高并受控于盘/一致性。

### 4.2 网卡未打满（iperf + 计数器实测）

- **bond1/bond2 各 802.3ad 2×25G = 50Gbps/节点，共 100Gbps/节点**（probe 确认成员卡全 25G）。
- iperf 11→13 实测：单 bond 强推 ≤13 Gbps、双 bond ≤26 Gbps（软件发送栈/中断绑定到单核限制，**不代表硬件上限**）。
- 均衡读 31.5 GiB/s = 集群 252 Gbps = **每节点 84 Gbps**，是 iperf 单进程能力（26 Gbps）的 3 倍多 → 均衡读靠多连接+多核真正用上网卡多队列。
- 读峰网卡计数器：n11 单向 69%、n12/13 44-54% → **网卡硬件远未打满（还有 ~31% 余量）**。

### 4.3 结论

**均衡读写上限非网卡、非盘，而受"每-op 数据面固定开销"约束：**
- 写 ~22.86 GiB/s：round-robin 把写分散到 9 实例，打破服务端批合并（--batch）+ 单实例连接并发有限，加并发只 +13% 带宽却把延迟放大 28 倍。
- 读 ~30.81 GiB/s：读返回路径 copy 占 2/3 + 每-op 串行往返，加深队列只堆延迟不放宽吞吐。

**对比 FUSE 客户端均衡读写**（此前实测：均衡写 7.6 GiB/s、均衡读 25.5 GiB/s）：bench 直压远超 FUSE，坐实 FUSE 侧瓶颈在 EFS_nefs 客户端层（拷贝/syscall/chunk），而非均衡路由算法或数据面。

## 5. 各优化维度影响表

| 优化维度 | 对 31.5 GiB/s 读 | 结论 |
|---|---|---|
| threads（单客户端） | 128 收敛，~23 GiB/s | 单客户端饱和 |
| pipeline | +0~1%，延迟 ×3.7 | 无效且有害 |
| conns（4→16） | 无增益 / 略降 | 4 已饱和 |
| **客户端数（3→12）** | **+35%，12 到峰，15 回落** | **唯一有效杠杆，已到顶** |
| 对象 size（4→16MiB） | 写 `stream closed` | 被数据面会话阈值挡死 |
| 网卡（iperf） | 单向 44-69% | 未打满，非瓶颈 |

## 6. 调参建议

- **均衡写最佳**：3 客户端 × threads=128 × **conns=4** → 22.86 GiB/s（conns 调大反而降）
- **均衡读最佳**：**12 客户端** × threads=128 × conns=4 → 30.81 GiB/s（再加密户端回落）
- 若目标是降低单客户端可获得的带宽，读单个客户端只有 ~23 GiB/s 且参数（threads/pipeline/conns）已完全饱和——**只能靠多客户端进程并行**，single-client 无参数可再调。
