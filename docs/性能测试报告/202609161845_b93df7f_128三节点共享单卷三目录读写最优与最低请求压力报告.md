## 1. 目标

前几轮压的是"**每节点挂几个卷**"（挂载点数），本轮换一个维度：**卷的分布方式**。

1. **共用同一个卷**：只建 **1 个卷**，这个卷在三个节点**各挂载一次**（3 个客户端会话共用 1 个卷）。
2. 卷下建 `node11`/`node12`/`node13` 三个目录，**每个节点只读写自己的目录**（互相不碰对方的数据）。
3. 在这个拓扑下找**最佳读、最佳写**数据，以及**最低请求压力**（打平台带宽所需的最小"在飞请求数 / 线程数"）。
4. 回答一个问题：**把三个节点的负载压到同一个卷上，会不会比"每节点各挂一个卷"更好或更差？**

三节点各在自己目录内 `dd` 4M×4 直写直读均成功 → **一个卷的三个目录确实被三个客户端同时读写**。

### 2.2 数据落在哪（定性探测）

三节点并行写各自目录（j4_d1 / 4×4 GiB / 25 s），同时 `iostat -x 1 4`：

| 12 | ≈122880 | ≈114688 | ≈81920 | ≈320 MB/s | 4.0~5.2% |
| 13 | ≈90112 | ≈143360 | ≈114688 | ≈350 MB/s | 3.2~5.6% |

三节点**都在自己的本地 nvme1/2/3 上产生真实写入**（都非 0，均非 OS 盘），说明共享卷的写入仍按"本地优先"分散到三节点的盘上，
只是**分布不均**（node11 的盘侧吞吐明显高于 12/13）——这个不均在后面每轮的逐节点稳态里稳定复现。

### 2.3 与"每节点 1 卷"的唯一差别

| | 每节点 1 挂载点（上一轮） | **本轮共享单卷** |
|---|---|---|
| 卷数 | 3 个卷（每节点挂各自的 `v-3`） | **1 个卷** |
| 客户端会话数 | 每节点 1 个（共 3 个） | 每节点 1 个（共 3 个） |

即：**客户端会话数、每节点挂载点数、盘并行度都相同，只有"卷是否共用"这一个变量**。

## 3. 方法与口径

### 3.1 skill 支持（`--mounts 5`）

```bash
# 写侧扫描
python3 cluster_ops.py --cluster 128 --phase test --write-only --drain --runtime 60 --cpu \
    --mounts 5 --only-round "1,1 4,1 6,1 8,1" --ch proxy
# 读侧扫描（定量写 48GiB/节点后读 60s）
python3 cluster_ops.py --cluster 128 --phase test --total-per-node 49152 --runtime 0 \
    --read-runtime 60 --cpu --mounts 5 --only-round "32,4 32,8 48,4" --ch proxy
```

`--mounts 5` 是新增的特殊入口：`vol_dirs(node)` 返回该节点在共享卷里的子目录（`/mnt/shared/node<TAG>`），
`--size` 分母随之变为 1（`768GiB/节点 ÷ 1 ÷ nj`），与"每节点 1 挂载点"完全同量级，不回绕。

### 3.2 本轮修掉的两个口径坑

1. **客户端 `.stats` 取样路径**：共享卷的 `.stats` 只在**挂载根**（`/mnt/shared/.stats`），子目录里没有。
   写死 4 个 `v-*` 路径或直接用 `vol_dirs` 都会取到 0 —— 已改为 `stats_dirs(node)`：共享卷拓扑取挂载根，其余取参与测试的挂载点。
   修好后**客户端口径与 fio 字节 1.00x 对齐**（例：j16_d1 fio 1004.0 GiB / PUT 1004.0 GiB）。
2. **客户端 pprof 端口动态发现**：客户端实例的 pprof 端口**随挂载实例数变化**（4 个卷时是 6064~6067，
   共享卷新增的 `/mnt/shared` 实例落在 **6061**）。写死端口列表会漏掉新实例，抓到的全是**空闲客户端**的空 profile
   （实测：client.write 只累计 8.4 s CPU，而同一轮 `--cpu` 口径客户端 26 核）。已改为按 `ss -lntp` 动态取
   （判据：pprof 只服务在通配地址 `*:PORT`，每个实例另有一个绑 127.0.0.1 的内部端口，请求无返回）。

### 3.3 术语

- **在飞/节点** = `numjobs × iodepth × 挂载点数`（本轮挂载点数 = 1，即 `nj × qd`）；**线程/节点** = `nj`。
- **稳态** = 逐秒样本剔除首末后按节点均值 ×3（集群口径），与"盘侧均值"并列给出。
- 盘侧列：写取 `wkB/s`/`w_await`，读取 `rkB/s`/`r_await`；各轮**盘侧样本积分与 fio I/O 量闭口**
  （写 0.4~1.8%、读 0.7~1.9%，差值来自元数据/后台 I/O）。

## 7. CPU 与 pprof

### 7.1 最优点 CPU（`--cpu` 口径）

| 相位 | 轮次 | 宿主 busy | 客户端核数（每节点） | 服务端核数（每节点） | 窗口 |
|---|---|---|---|---|---|
| 写 | j16_d1（最优） | **16.5%**（19.8 / 16.9 / 13.0） | **26.6**（11.2 / 7.5 / 7.9） | **4.9**（3.1 / 0.9 / 0.9） | 64 s |
| 写 | j8_d1（最低压力） | 16.2% | 26.3（11.2 / 7.5 / 7.7） | 4.8 | 63 s |
| 读 | j32_d4（最优） | 17.4% | 35.7 → 折算 ≈ **87** | 4.8 → 折算 ≈ **11.8** | 147 s |

- 写侧 CPU 可直接使用（窗口 63~64 s 贴合负载），**单位带宽客户端 CPU ≈ 1.60 核/(GiB/s)**，
  与 1/2/4 挂载点三轮的 1.65~1.71 核/(GiB/s) 一致 → 客户端 CPU 效率不随拓扑变化。
- 读侧 CPU 窗口 **144~152 s**（fio 负载只有 60 s，含同轮"定量写 + 删旧文件"），数值被稀释 ~2.4×，
  **只能同族横向比较**；折算上界 ≈ 87 核 / 12 核（读屏障仍是客户端，`%util` 只有 ~66%，宿主 busy 17.4%）。

### 7.2 pprof 热点（`--pprof`，最优点各一轮）

**写相位（j16_d1，profile 干净）**

| 侧 | flat 热点 | cum 调用链 |
|---|---|---|
| 服务端 | `Syscall6` **48.96%**、`futex` 7.20%、`stealWork` 9.71% | `RawSyscall6` 47.19% → `batchWriter.run` 36.53% → `Storage.BatchAppend` 32.48% → `Device.AppendBatch` 32.47% → `uringRing.submit` 32.24% → `SubmitWriteBatch` 31.45% |
| 客户端 | `memmove` **44.41%**、`Syscall6` **35.52%** | `fuse.Server.loop` 62.60% →（`readRequest` 32.03% / `doWrite` 26.86%）+ `memmove` 44.41%、`syscall.Syscall` 35.16% |

→ 写路径的耗时结构（服务端 io_uring 提交 + pebble WAL；客户端 FUSE 搬运 memmove + syscall）与 1/2/4 挂载点三轮**完全同形**，
共享卷没有引入新的热点。

**读相位（j32_d4）：被同轮文件清理污染，仅作定性参考**

- 服务端：`gcDrain` cum **42.84%**、`lfstack.pop` 18.61%、`Syscall6` 17.16%；
  **`shmServer.handleShmDelete` cum 17.49%**（删除路径）。
- 客户端：`memmove` 18.87%、`Syscall6` 23.98%、`fuse.Server.loop` cum 20.07%；
  同时出现 **`meta.(*kvMeta).deleteChunk` / `tryDeleteFileData` cum 12.78%**、`transport.shmWriteFrame` 12.31%。

→ 读相位的 profile 窗口里混进了"档案删除 + 段 GC"的工作（每轮读相位开始时会删掉上一轮的 48 GiB×3 文件），
**读热点数字不可当真值使用**；但它佐证了 §8 第 2 条：删数据的开销会串进读相位的盘侧口径。

## 8. 异常与口径提醒

1. **带 `--pprof` 的测量轮次不可信（本轮最强证据）**：
   - 写 j16_d1 带 pprof：应用层 17095、稳态 17022 —— 与干净轮一致，**写侧没问题**；
   - 读 j32_d4 带 pprof：应用层 **40335**（比两次干净轮低 14%），其中 **node12 掉到 9922**（干净轮 15462），
     `max` 延迟 **21.9 s**，盘侧样本数从 61 涨到 82/126（窗口被拖长）。
   - **结论：pprof 轮只能用于热点归因，不能取带宽数字**；本报告所有带宽结论均取干净轮。
2. **读相位"应用层 < 盘侧"（j48_d4）**：应用层 45466、盘侧稳态 48050。盘侧样本积分与 fio 字节闭口（+5.8%，含后台 I/O），
   差值来自**上一轮文件删除触发的段 GC / compaction 盘 I/O 被一起计入盘侧**（见 §7.2 的 `deleteChunk`/`handleShmDelete`）。
   该点不能当"最佳读"，只能说明盘侧还有余量。
3. **客户端 `.stats` 路径**：共享卷的 `.stats` 在挂载根，修复后客户端口径 1.00x（详见 §3.2）。
4. **共享卷容量与回收**：8 TiB 卷，单轮集群写 ~1.0 TiB；实测 8 轮压测后 `df` 由 13 G 涨到 59 G 再回落到 12 K
   （轮内删旧文件 → 后台回收），**回收节奏跟得上，但压测轮次多时要盯 `df`**。
5. **逐节点不均**：写侧 node11 稳定高 ~25%（6563 vs 5248/5211）。未定位到根因（段分配偏好 / 本地优先路由的落盘差异均有可能）。
6. **读相位 CPU 窗口偏长**：144~152 s vs 负载 60 s（详见 §7.1）。

## 9. 结论速查

| 项 | 参数 | 应用层 | 盘侧稳态 | 在飞请求/节点 | 线程/节点 |
|----|------|--------|----------|---------------|-----------|
| **共享单卷最佳写** | `j16_d1`（每卷 16 job×qd1） | 17461 / 16868 / 17142 / 17095 | **17028 / 16417 / 16681 / 17022**（≈16.6 GiB/s） | 16 | 16 |
| 共享单卷最低写压力 | `j8_d1`（每卷 8 job×qd1） | 17203 / 16906 / 16539 | **16742 / 16713 / 16092**（平台 ~97%） | **8** | **8** |
| **共享单卷最佳读** | `j32_d4`（每卷 32 job×qd4） | **46592 / 47002** | 45828 / 42521 | 128 | **32** |
| 共享单卷读天花板 | `j48_d4` | 45466（应用层倒退） | 48050 | 192 | 48 |
| 共享单卷 vs 1 卷/节点 | — | 写 -1.4%、读 -3.0% | — | 相同（写 8 / 读 128） | 相同（写 8 / 读 32） |

**一句话**：把三个节点压到**同一个卷**上（各挂一次、各写各目录），读写能力与"每节点各挂一个卷"**基本一样**
（写 16.6 vs 17.3 GiB/s、读 46.6~47.0 vs 48.4 GiB/s，均在 1~3% 内），
最低请求压力也完全一致（**写 8 在飞/节点；读 32 线程 + 128 在飞/节点**）。
说明这两个拓扑的瓶颈都不在"卷怎么分"，而在**"每节点 1 个客户端会话"**（写只有 54% `%util`）
与**"每节点 32 线程搬运能力"**（读只有 66% `%util`）。共享卷唯一的副作用是**逐节点分布更不均（node11 高 25%）**。
